# etl/backends/adapters — optional compiler adapters (IREE, XLA via PJRT, TVM)

## Intent

Pluggable compiler backends for etl.
Each adapter consumes the SHARED StableHLO lowering produced by `CompilerBackend.lower` (`../compiler.py` — verify, capability pre-check, block-portable inlining, StableHLO export, Signature recording) and implements only the compiler-specific half: the optional dependency probe (`check_available` override — the shared base is a concrete no-op), `compile` (invoke the external compiler on the MLIR text), and `load` (rebuild the executable from the artifact — never recompiling).
Activation is register-on-first-use: `etl.backends.registry.get(name)` imports the adapter module via `registry.OPTIONAL_ADAPTERS` and calls its `register()`; `import etl` never imports an adapter or its compiler dependency.

**Dependency posture (binding):** etl depends directly on the ML compilers. The `jax` frontend package appears NOWHERE in `etl/`, and the xla adapter uses no jaxlib either.
- **xla** = the PJRT C API driven through pure-stdlib ctypes against a USER-PROVIDED plugin binary (a `.so` exporting `GetPjRtApi`). Plugin distribution is explicitly OUT of scope; no pip package provides one.
- **tvm** = `apache-tvm` + `jaxlib`, where jaxlib is used ONLY for its bundled LLVM MLIR python bindings (not the jax API), behind the `_mlir_bindings` seam. The vendored translator's `jax._src.interpreters.mlir` import is satisfied by an injected `sys.modules` shim.

Status: all three adapters are implemented and validated — iree end-to-end on llvm-cpu, CUDA and ROCm/HIP; xla against the test fake plugin AND the real `jax_cuda12_pjrt` (CUDA) and `jax-rocm7-pjrt` (ROCm) plugins; tvm on `apache-tvm` 0.26 + jaxlib (CPU, and ROCm compile-only).
Measurements, probe narratives and the long procedural recipes live in `./PER-ADAPTER-NOTES.md` (the companion to this file) and the skill `etl-compiler-adapter-recipes`.

## API Surface

Each adapter module (`iree.py`, `xla.py`, `tvm.py`) exposes the same shape:
- `<Name>Backend` (a `CompilerBackend` subclass; names `"iree"`, `"xla"`, `"tvm"`), `<Name>Executable` (a `CompilerExecutable` subclass), singleton `<name>_backend`, and a module-level `register()` (probes the dependency — `core.BackendError` with an actionable message when missing — then registers idempotently).
  `register()` also installs the module-level `upload_tensor` into the PER-BACKEND device-transfer slots (`core.register_backend_device_transfer_provider`) — iree for kinds `"cuda"`/`"rocm"`/`"hip"`, xla for every `_NON_CPU_KINDS` entry — so `Tensor.to(Device(kind, N))` resolves to the activated adapter. Per-backend slots mean activation order can never clobber another backend's provider or the flat DEFAULT slot.
- `<name>_util.py` helpers: `xla_util.py` (PJRT C API driver: plugin discovery/loading, version gate, client/compile/execute/buffer/serialize plumbing), `tvm_util.py` (vendored-translator compat shim + jax `sys.modules` shim injection, op whitelist gate, translate/build/run/persist helpers).
- `_pjrt_c_api.py`: vendored ctypes translation of the Apache-2.0 PJRT C API header (header URL + commit recorded; offsets verified against a plugin compiled from the real header).
- `_mlir_bindings.py`: the MLIR binding-provider seam (jaxlib today; a standalone `mlir` package is a one-module swap).
- `__init__.py`: documentation only, imports nothing heavy.

## Options override (per adapter — quick reference)

The shared mechanism — per-stage `KNOWN_OPTIONS`, union-of-stages key validation, `validate_options`, `normalize_opt_level`/`normalize_bool_option`, the env table, and explicit > env > default precedence — is specified in `../CONTEXT.md` ("Backend options override") and implemented in `../options.py` + `etl/pipeline_options.py`; this file records only the per-adapter keys, defaults and conflict rules.

| Backend | Stage | Option key | Env var | Notes (default + validation/conflict) |
|---|---|---|---|---|
| iree | compile | `target_backends` (list[str]) | `ETL_TARGET_BACKENDS` | default `["llvm-cpu"]`; supported `{"llvm-cpu","cuda","rocm"}`; drives `--iree-hal-target-backends` (that flag itself is DENIED). `CompiledArtifact.target` = `"cpu"`/`"cuda"`/`"rocm"`/`"+"`-joined. A non-list, an empty list or an unknown target → `core.BackendError` naming the offender |
| iree | compile | `iree_compile_args` (list of flags) | `ETL_IREE_COMPILE_ARGS` | appends arbitrary iree-compile flags AFTER the defaults; a user flag whose NAME (text before `=`) collides with a default DROPS the default (never both). DENY list (`_IREE_DENIED_COMPILE_FLAGS`): `--iree-hal-target-backends`, `--iree-input-type`, `--iree-vm-bytecode-module-output-format` — rejected with reasons; every other flag passes through and the compiler validates its VALUE |
| iree | compile | `opt_level` (str\|int) | `ETL_OPT_LEVEL` | `"O0"`..`"O3"` (case-insensitive) or 0..3 → the DERIVED flag `--iree-opt-level=O{N}` (the O-form is REQUIRED — iree-base-compiler 3.11 rejects numeric levels). A user `--iree-opt-level=…` wins and the derived flag is dropped (never both). Not in the DENY list. Unset → no flag, byte-identical |
| iree | load | `iree_runtime_args` (list of flags) | `ETL_IREE_RUNTIME_ARGS` | loader/HAL flags via `rt.flags.parse_flags` (loud errors). etl sets NO process-global runtime flag — iree's own `--cuda_async_allocations=true` (stream-ordered) default stands; override per load here or via `IREE_PY_RUNTIME_FLAGS` |
| xla | compile AND load | `plugin_path` (str) | `ETL_PJRT_PLUGIN` | plugin discovery; honored at load too, so a persisted artifact can be loaded without re-passing it |
| xla | compile | `xla_compile_options` (bytes) | `ETL_XLA_COMPILE_OPTIONS` (base64) | raw serialized `xla.CompileOptionsProto` into `PJRT_Client_Compile_Args.compile_options`; etl does not parse the contents. Unset → `bytes.fromhex("1a0420012801")` (num_replicas=1/num_partitions=1 — a NULL `compile_options` CHECK-crashes real plugins). Non-bytes → `core.BackendError` |
| xla | compile | `opt_level` (str\|int) | `ETL_OPT_LEVEL` | injected into `executable_build_options` (wire-format field 24) by `xla_util.set_opt_level`; a level already present in `xla_compile_options` wins unchanged (conflict rule — never both); unset → bytes untouched |
| tvm | compile | `tvm_target` (str) | `ETL_TVM_TARGET` | default `"llvm"`; non-str → `core.BackendError` |
| tvm | compile | `tvm_pass_configs` (dict) | `ETL_TVM_PASS_CONFIGS` (JSON) | forwarded only when non-None; the installed TVM 0.26 `build` lacks the param → loud `BackendError`; non-dict → `core.BackendError` |
| tvm | compile | `opt_level` (str\|int) | `ETL_OPT_LEVEL` | forwarded to `tvm_util.build_vm_executable(..., opt_level=N)` as a version-adaptive kwarg (the `pass_configs` pattern). The installed TVM 0.26 has no `opt_level` kwarg and `PassContext(opt_level=N)` does not reach the LLVM codegen, so a build without the kwarg raises a LOUD `core.BackendError` naming `opt_level` and the installed TVM (never silently dropped). Unset → byte-identical default |
| iree/xla/tvm | lower | `rng_bit_generator` (bool\|collection) | — | reserved StableHLO-export override of the adapter's native-RNG capability set |
| all (iree/xla/tvm) | lower | `dot_precision` (str) | — | reserved exporter option `"DEFAULT"`\|`"HIGH"`\|`"HIGHEST"` (case-insensitive); default `"DEFAULT"` emits NO `precision_config` (byte-identical export); only `"HIGHEST"` disables XLA/ROCm's TF32-class reduced-precision fp32 `dot` (`"HIGH"` does not, on this XLA version). iree/llvm-cpu and tvm/llvm parse/compile/run the attributed text with results BIT-IDENTICAL to `"DEFAULT"` (documented no-op). Invalid value → exporter `core.BackendError` |
| all (iree/xla/tvm) | lower | `eigh_algorithm` (str) | `ETL_EIGH_ALGORITHM` | `"jacobi"`\|`"jacobi_batched"` (case-insensitive, whitespace-stripped), default = `CompilerBackend.default_eigh_algorithm` = `"jacobi_batched"` (all mutually disjoint rotations of one odd-even round-robin round per `stablehlo.while` iteration); `"jacobi"` is one (p,q) rotation per iteration. The Writer validates the value (`core.BackendError` listing accepted forms), so the env value is NOT raw pass-through. Batched is the default because it is far faster and avoids an iree llvm-cpu compile crash at n ∈ {4,8,12,16} (numbers: companion) |
| all (iree/xla/tvm) | lower | `split_reduction` (bool) | `ETL_SPLIT_REDUCTION` | default = `CompilerBackend.default_split_reduction` = `True`: two-stage split reductions for rank-0-result reductions (split the reduced axis into ≥2 non-unit factors, reduce per row, then reduce the rows — numerically exact; min/argmin stay associative with the emitter's first-occurrence tie-break). `False` emits the byte-identical single-stage text. Normalized by `options.normalize_bool_option` (real bools, `0`/`1`, `true`/`false`/`yes`/`no`/`on`/`off`; malformed → loud `BackendError`) |
| iree | lower | `sort_emission` (str) | — | `"pair"`\|`"count"`\|`"auto"`; iree `default_sort_emission = "auto"` (= `"count"` iff the sorted-axis extent ≥ 32) because iree-cuda cannot bufferize the multi-operand `stablehlo.sort` beyond that size and its 1-operand sort lowers to a single-threaded O(n²) kernel, while the count composition is bit-exact there. `CompilerBackend.default_sort_emission` is `"pair"` |
| iree | lower | `while_init_rewrite` (bool) | — | default ON at export (hardcoded in `../compiler.py::_exporter_options`, NOT a ClassVar) — the computed-zeros init rewrite that keeps the evox `non_dominate_rank` while-loop compilable (Known Issue 8f) |
| iree/xla/tvm | run | — (none in v1) | — | non-empty run options → loud `BackendError` (by design) |

**Exporter-option plumbing (for adding new options):** no adapter overrides `lower()` — the shared `CompilerBackend.lower` validates keys and builds the export dict in `_exporter_options`, which forwards exactly `rng_bit_generator`, `sort_emission`, `while_init_rewrite`, `dot_precision`, `eigh_algorithm`, `split_reduction`.
`eigh_early_exit`, `split_reduction_threshold` and `split_reduction_non_exact` are writer-only options NOT plumbed through the adapter path — passing them to `etl.lower(..., backend="iree")` raises the unknown-key `BackendError`.
Env spellings exist only for the backend-agnostic reserved lower options `eigh_algorithm` (`ETL_EIGH_ALGORITHM`) and `split_reduction` (`ETL_SPLIT_REDUCTION`), registered for all three adapters at the lower stage.
A NEW exporter option requires three touches: add it to `_exporter_options`, declare it in each adapter's `KNOWN_OPTIONS["lower"]` (all three declare `rng_bit_generator`/`dot_precision`/`eigh_algorithm`/`split_reduction`; iree additionally `sort_emission`/`while_init_rewrite`), and consume it in the stablehlo Writer (sibling node).

## Adapter designs

### IREE (`iree.py`) — llvm-cpu, CUDA and ROCm/HIP

- **compile:** `iree.compiler.compile_str(mlir_text, target_backends=..., input_type="stablehlo", extra_args=resolved_args)` → VM flatbuffer, base64'd into the payload (`format="iree-vmfb"`, keeping `mlir_text` + `entry_functions` + `target_backends`). Compiler diagnostics are re-raised as `core.BackendError` carrying them (never silent).
- **Compile flags are user-overridable** — the fixed defaults are minimal and documented: `_IREE_DEFAULT_COMPILE_ARGS = ("--iree-input-demote-f64-to-f32=false",)` (always — IREE otherwise demotes f64 to f32 silently, which etl's error strategy forbids), `_IREE_DEFAULT_LLVMCPU_ARGS = ("--iree-llvmcpu-target-cpu=generic", "--iree-llvmcpu-link-embedded=false")` (llvm-cpu only — the embedded `-nostdlib -static` link cannot resolve the libm symbols `log`/`cos`/`floor` that f64 math ops lower to), and the rocm-only `_IREE_DEFAULT_ROCM_ARGS_NAME = "--iree-rocm-target"` (see the ROCm section). A same-NAME user flag drops the default; only the DENY list is rejected.
- **load/run — CPU** (device `None` or `Device("cpu", *)`) via `iree.runtime.get_driver("local-task")` + `driver.create_default_device()` + `load_vm_flatbuffer(flat, driver="local-task")`. Do NOT reintroduce `rt.system_setup(config=...)` — it intermittently fails with `TypeError: 'module' object is not callable` (submodule shadowing).
- **load/run — CUDA/ROCm** via `rt.get_driver("cuda"|"hip")` + **`driver.create_device(device_id=index + 1)`** — iree GPU device ids are **1-BASED** (device_id 0 raises `ValueError`, wrapped into `core.BackendError`) — plus `rt.Config(device=...)` → `rt.VmModule.copy_buffer(config.vm_instance, vmfb)` → `rt.load_vm_module(vm_module, config)`. `load_vm_flatbuffer`'s driver-name form always creates the DEFAULT device and cannot select an index. The CUDA HAL driver is compiled INTO the runtime wheel (no extra pip dependency).
- **Artifact↔device validation:** the payload's `target_backends` must include the target matching the device kind (`cuda` artifact ↔ cuda device, `rocm` ↔ rocm/hip, `llvm-cpu` ↔ cpu); absent `target_backends` means `["llvm-cpu"]`; a mismatch raises `core.BackendError` naming both.
- **Inputs (explicit placement — no implicit host↔device transfers):** an input already on the executable's device — an `IreeDevicePayload`-backed `core.Tensor` with matching kind+index, or a raw iree `DeviceArray` — passes through to the invoke with ZERO host round-trips. Every other input is rejected; plain cuda/rocm runs NEVER stage host inputs. The pipeline run boundary raises its own `core.DeviceError` ("no implicit device", `t.to(`) first, and a GPU executable additionally enforces a defensive `core.DeviceError` for direct `exe.run([...])` calls. The single exception is an llvm-cpu executable, which accepts host ndarray-backed inputs via `rt.asdevicearray` (host→host ABI representation — the only plain-run host-input path).
- **Outputs (device-resident, all targets):** outputs are `core.Tensor`s wrapping the iree `DeviceArray`s in the PUBLIC `IreeDevicePayload`; `.device` is the run device. Host materialization is lazy and explicit: a cpu-kind output's `.numpy()` materializes a fresh host copy on demand (`DeviceArray.to_host()`, zero-copy for mappable local-task buffers); a NON-cpu output's `.numpy()` raises `core.DeviceError` — read it back with `t.to(core.Device("cpu", 0)).numpy()`. The hot run path performs no host round-trip either way, and `core.Tensor` wrappers never alias or pin the HAL buffers.
- **Per-call run path — cached PLANS of static metadata, never values.** `IreeExecutable` derives ONE cached input plan from its signature (`_input_plan`: per-leaf `(dtype, shape, needs_dim_walk)`, where `needs_dim_walk` is True iff a declared dim is non-`int` — symbolic `Dim`/`DimExpr` or `None`) and ONE flat tuple of expected output dtypes (`_output_dtypes`); `run` compares the ACTUAL argument metadata against those plans on every call, so there is no skip-validation path and no cached tensor value.
  `run` performs ONE fused pass per input leaf — `isinstance(tensor, core.Tensor)` first, then dtype (`data.dtype` against the planned dtype, with a single `core.dtype(...)` normalization when the two are not already equal so a non-normalizable dtype still raises `core.DTypeError`), then shape (one tuple compare on the static steady-state path, else `_validate_input_shape`'s per-dim walk), then the HAL buffer build — filling a pre-sized `buffers = [None] * n_inputs` list by index instead of a second `_build_buffers` walk.
  The fused buffer branch order is `_build_buffers`'s: same-device payload / raw `DeviceArray` pass-through (ZERO `asdevicearray`/`numpy()` calls), `core.DeviceError` for a non-pass-through input on a cuda/rocm executable (byte-identical text), `rt.asdevicearray(runtime_device, tensor.numpy())` for an llvm-cpu host input.
  `_build_buffers` therefore serves `_IreeSegmentExecutable` (and the external-call/segment path) only; the two forms are 1:1 in branch order, pass-through rule and errors, so a change to one must be mirrored in the other.
  Outputs are wrapped and dtype-checked in ONE pass over a pre-sized list (count check first, then `IreeDevicePayload` + `core.Tensor` + the planned-dtype compare, with `tensor.dtype` used only inside the byte-identical error text); the non-signature path wraps without validation.
  Error wording and exception types are unchanged from the two-walk form — every message is rebuilt on the failure path from the same `spec.dtype` / `tensor.dtype` / `tensor.shape` expressions.
- **Payload metadata comes from the HAL buffer view.** `IreeDevicePayload.__init__` caches `_shape`/`_dtype` ONCE (a `DeviceArray` is shape/dtype-immutable for its lifetime), resolving them from `array._buffer_view` — `tuple(view.shape)` (0.07 us) and `view.element_type` (0.04 us) through the module-level `_HAL_ELEMENT_DTYPES` memo filled by `_hal_element_dtype` (lazy `HalElementType.map_to_dtype`) — rather than the public `array.shape`/`array.dtype` accessors (~0.35 us + ~0.4 us: numpy `__array_function__` dispatch plus a nanobind dtype hop; that pair was the largest component of output wrapping).
  `array._override_dtype` is honored FIRST (it wins in `DeviceArray.dtype` too, and bool/relaxed-dtype results depend on it), and a runtime without the private buffer-view protocol falls back to `tuple(array.shape)`/`array.dtype` and caches whatever it got — the public payload protocol (`.shape` tuple of ints, `.dtype` numpy dtype, `.device_array`, `.device`, `to_host()`, `__array__`) and the constructor signature are unchanged, and the payload still retains nothing beyond the `DeviceArray` handle.
  `_runtime_modules()` memoizes the lazy `numpy` / `iree.runtime` imports for the run path (the heavy-import rule keeps them out of module top level; the memo avoids a per-call `sys.modules` lookup).
- **External kernels (`external_call`):** graphs containing `external_call` are SPLIT at `lower()` by the shared `CompilerBackend` (`../compiler.py::_lower_external_segments` + `../external_split.py`) into ordered SEGMENT programs (plain graphs, each compiled to its own vmfb — payload `stablehlo-segments`, artifact `iree-vmfb-segments`, per-segment `target_backends`/`iree_compile_args`) plus a JSON-safe kernel-call PLAN persisted in the artifact. `IreeExternalExecutable` runs segments strictly in plan order and dispatches each boundary through `etl.external.get_external_kernel_entry(name, "iree")` (unknown name at run → `BackendError` naming the kernel; outputs validated count/dtype/shape).
  - **host mode** (default): operands staged to host numpy arrays, the kernel runs on host, results staged back as the next segment's inputs; the once-per-executable staging `UserWarning` fires only when a boundary actually stages.
  - **device-resident mode** (`device_resident=True`, explicit per-backend slot only): the kernel receives the boundary's device tensors DIRECTLY (never host-staged) and may return device tensors / duck payloads / raw `DeviceArray`s / numpy arrays / tuple-list mixes; results are validated METADATA-ONLY, and the next segment consumes device results through the same-device pass-through with ZERO host round-trips (numpy results stage back and mark the boundary staged). Kernel authors may isinstance-check `etl.backends.adapters.iree.IreeDevicePayload` (`.device_array`, `.shape`, `.dtype`, `.to_host()`, `.device`) and run further vmfb modules on the SAME HAL device.
  Carried plain values that are not kernel operands stay device-resident across segments. Lower-time restrictions (explicit `BackendError`, MODE-AWARE): no calls inside cond/while/scan bodies, ≥1 tensor operand, single-function graphs, and — HOST-mode boundaries only — STATIC integer result dims. DEVICE-RESIDENT boundaries allow symbolic/runtime-dynamic result dims (e.g. vmap/vectorize batch `Dim`s on a batched-variant kernel — the vmapped kernel receives the FULL batched stack, invoked once per run), validated metadata-only at run time with the ACTUAL shapes. Kernels are assumed PURE; segments run sequentially and preserve `callback` effect order.
- **Explicit placement — `Tensor.to(Device(kind, N))` → `upload_tensor`:** `core.Tensor.to` dispatches through the device-transfer provider registry. `etl.backends` pre-registers a LAZY `"cuda"` thunk in the flat DEFAULT slot at import (delegating to this module's `upload_tensor` by attribute lookup, so placement works before the adapter activates), and `register()` installs the DIRECT function under the per-backend slots. `upload_tensor` contract (v1): the source must be a HOST ndarray-backed `Device("cpu", 0)` tensor — anything else raises `core.DeviceError` suggesting the two-hop `t.to(cpu).to(target)`; it acquires the HAL device exactly like `load` (honoring `ETL_IREE_RUNTIME_ARGS`), performs a ONE-SHOT host→device copy, and returns a fresh `core.Tensor(IreeDevicePayload(da, device))` on the target device. Failures surface as `core.DeviceError`/`core.BackendError`, never a raw iree exception. A placed tensor lives on a fresh HAL device instance but is accepted by a separately loaded executable on the same physical device (iree allows same-device buffers across instances), so kind+index equality is the sufficient check.
- **Host→device staging machinery (`_staged_input`) — TWO TIERS — serves ONLY host-mode external-kernel boundaries and the placement provider (`upload_tensor`); plain GPU runs never stage.** Split at `_PINNED_DIRECT_MAX_BYTES = 4 * 1024`: **≤ 4 KB** writes a persistent mapped `DEVICE_LOCAL | HOST_VISIBLE` buffer with one `np.copyto` (no copy, no semaphore, no wait); **> 4 KB** copies per call (`queue_copy`) from a persistent `HOST_LOCAL | DEVICE_VISIBLE` source into a persistent `DEVICE_LOCAL` staging buffer.
  Buffers are cached per `(input index, shape, dtype)` (bounded `_STAGED_INPUT_CACHE_MAX = 64`, cleared on overflow — no per-call device alloc) while `upload_tensor` uses a fresh one-shot dict; inputs > 16 MB (`_STAGED_INPUT_MAX_BYTES`), unmappable dtypes, non-GPU paths and cache overflow fall back to `rt.asdevicearray`.
  **The tier-2 semaphore wait is LOAD-BEARING — do not remove it:** the cuda HAL does not reliably stream-order `queue_copy` ahead of invoke dispatches, so each call waits on a FRESH semaphore (reusing one ABORTS), query-first so an already-complete copy skips the fence wait.
  Byte-level buffer flags, the 4 KB-cutoff reasoning and the cuda `_pool_anchor`: `./PER-ADAPTER-NOTES.md`.
- **Iterative stateful workloads (DE/PSO-style steps) — the recommended pattern:** keep state ON the device; build once, then loop `etl.run(exe, key_dev, state_dev)` feeding each step's device-resident outputs back as the next inputs, with the seed placed once via `seed.to(Device(kind, N))`. Every later call costs zero `asdevicearray` calls and zero host round-trips. Anti-patterns: feeding fresh host state per step (rejected at the run boundary with `core.DeviceError`) and `.numpy()`-reading the whole state per step (a non-cpu output needs an explicit `.to(cpu)`).

### ROCm / HIP (`rocm`) — AMD GPU, device-resident

Same adapter and the same device-resident machinery as cuda — a third compile target and a third HAL driver.
- **Compile:** `target_backends=["rocm"]`. IREE has no ROCm target auto-detection, so the adapter injects a detected `--iree-rocm-target=<arch>` default (`_detect_rocm_target` reads `amdgpu-arch` then `rocm_agent_enumerator` under `$ROCM_PATH`/`$ROCM_HOME`//opt/rocm; a user flag of the same name wins; an undetectable arch with no user flag → actionable `BackendError` naming `iree_compile_args=['--iree-rocm-target=gfxNNN']`). `--iree-hal-target-device=rocm` is NOT needed. `Artifact.target == "rocm"`; a target/device mismatch is an explicit `BackendError`.
- **Device paths:** `rt.get_driver("hip")` + `create_device(device_id=index + 1)` (1-based, like cuda). `Device("rocm", N)` (canonical) and the alias `Device("hip", N)` both resolve (`_normalize_device_kind` folds `hip`→`rocm` for the driver call only; the `core.Device` label is never rewritten). Device-resident semantics are the cuda ones.
- **Placement/staging — THREAD-LOCAL caches (REQUIRED, not an optimisation):** rocm placement reuses ONE thread-local HAL device per `(index, runtime args)` (`_acquire_cached_rocm_device`) and a thread-local reusable `HOST_LOCAL|DEVICE_VISIBLE` source buffer keyed `(shape, dtype)` (`_rocm_source_buffer`, bounded `_ROCM_SOURCE_CACHE_MAX = 16`), then a per-call `queue_copy` with a fresh semaphore + query-first wait. Thread-locality is load-bearing because HAL devices are thread-affine (Known Issue 12): a process-global cache would hand the `etl.io` worker a foreign device. A one-shot `upload_tensor` returns a FRESH destination; segment executables keep a persistent destination per `(index, shape, dtype)`. Cuda placement instead uses a fresh-per-call device with its own pinned/DMA tiers; `_staged_input` selects the path from the NORMALIZED device kind.
- **Validated bit-exact vs numpy on rocm:** `cond`; sort/argsort with the default `sort_emission="auto"`; splitmix64 uniform/randint; threefry2x32 via the NATIVE `rng_bit_generator` path; philox inline; host-mode `external_call`; matmul+tanh. f32 `random.normal` differs from numpy only within the documented Box–Muller fast-path budget.
- **`while_loop`/`scan` are unreliable on rocm** — upstream IREE HIP HAL; see Known Issue 13's sibling note in `./PER-ADAPTER-NOTES.md` and below in Known Issues.
- **Sugar (outside this node):** `etl/pipeline.py::_resolve_backend_device` infers `target_backends` from the resolved device when neither the option nor `ETL_TARGET_BACKENDS` is set (`cuda`→`["cuda"]`, `rocm`/`hip`→`["rocm"]`, `cpu`→`["llvm-cpu"]`), so `etl.build(fn, specs, backend="iree", device=Device("rocm", 0))` works end-to-end.

### XLA via the PJRT C API (`xla.py`) — no jaxlib

- **Plugin** (user-provided; distribution OUT of scope): resolved in order (a) `plugin_path` (a compile AND load option), (b) env `ETL_PJRT_PLUGIN`, (c) well-known paths (`/usr/local/lib`, `/usr/lib`, `$HOME/.local/lib`, `./`). None found → `core.BackendError` with an actionable message (build e.g. `bazel build //xla/pjrt/c:pjrt_c_api_cpu_plugin` from OpenXLA, or any XLA build exporting `GetPjRtApi`). No pip hint — jaxlib is never imported by this adapter.
- **Device kinds:** serves `Device("cpu", 0)` (host-staged) and the device-resident accelerators in `_NON_CPU_KINDS = ("cuda", "rocm", "hip")` — kind-agnostic, any non-cpu kind is device-resident. `_check_kind_served` (a) rejects a kind outside `_NON_CPU_KINDS` (e.g. `"gpu"`) with a `core.BackendError` containing "supports CPU", and (b) once the plugin's platform is known, rejects a kind the platform does not physically serve when the platform is listed in `_PLATFORM_KINDS` (`"cuda"→("cuda",)`, `"rocm"→("rocm","hip")`, `"hip"→("rocm","hip")`, `"cpu"→()`), so `Device("cuda", N)` against a ROCm plugin is rejected rather than mislabelled. An UNLISTED platform (e.g. the fake plugin's `"fake"`) is PERMISSIVE.
- **compile:** `ctypes.CDLL(path)` → `GetPjRtApi()` (a lowercase-t `GetPjrtApi` fallback covers the shipped jax plugins' casing) → **version gate** (`PJRT_Api.version`/`struct_size` vs the bindings' minimum; too old → `BackendError`) → the process-global shared `PJRT_Client` (`acquire_client`, one per plugin path, created with empty options) → `PJRT_Client_Compile` with `PJRT_Program{code=mlir_text, format="mlir"}` (the plugin accepts MLIR text directly; NO MLIR python bindings anywhere in this adapter) → `PJRT_Executable_Serialize` → base64 bytes in the artifact payload (alongside `mlir_text` + `entry_functions`). The artifact stays device-agnostic (`target="cpu"`); the device is chosen at `load()`.
- **Static-shape gate:** `dynamic_shapes=False` — symbolic dims are rejected at compile via `_resolve_static_shape`/`_StaticShapeError`; the gate decision is recorded in the artifact (`static_input_shapes`/`static_output_shapes`) and enforced exactly at `run()`.
- **load/run — CPU:** deserialize via `PJRT_Executable_DeserializeAndLoad` on the refcounted shared client for the re-discovered plugin — never recompiles. Inputs staged via `PJRT_Client_BufferFromHostBuffer` (all 14 etl dtypes incl. complex64/128; dense row-major numpy with `np.asarray` + contiguity forced only for ndim ≥ 1, NOT `np.ascontiguousarray` whose hardcoded ndmin=1 promotes 0-d arrays; `kImmutableUntilTransferCompletes`; transfer event awaited and destroyed; host array kept alive on the buffer); execute via `PJRT_LoadedExecutable_Execute`; outputs copied via `PJRT_Buffer_ToHostBuffer` → writable numpy → `core.Tensor`.
- **load/run — device-resident (`Device("cuda"|"rocm"|"hip", N)`), iree-mirroring:** every input must already be an `XlaDevicePayload`-backed `core.Tensor` on the executable's device (host inputs raise `core.DeviceError` at the run boundary — never staged); payload buffers go to `PJRT_LoadedExecutable_Execute` DIRECTLY and outputs STAY on the device as `XlaDevicePayload` tensors (public class, like `IreeDevicePayload`; non-cpu `.numpy()` raises, explicit `t.to(cpu).numpy()` round-trips). The same-device loop places the seed once via `t.to(Device(kind, N))` (the module-level `upload_tensor`, a one-shot `BufferFromHostBuffer` on the shared client, registered by `register()` for every `_NON_CPU_KINDS` entry) and then feeds each step's outputs back as the next inputs, so the per-call staging/copy-back fixed cost is paid exactly once.
- **Per-call hot path:** a run on an accelerator executable re-derives nothing that is static for a loaded executable. `XlaExecutable` builds ONE `_XlaRunPlan` carrying everything static about a run — input/output arity, per-leaf `(dtype, shape)` contracts from the signature, output metadata from the recorded static output shapes, and the run MODE (`device_resident`, derived once from the load device). `run` then makes ONE plan-driven pass over the inputs that validates dtype/shape and performs the explicit-placement checks in the same loop (payload type -> device -> owning client, with identity fast paths ahead of the equality fallback), preserving the same exception types/messages/order; per-leaf metadata is read from a device payload's already-cached `_Buffer` `(shape, dtype)` rather than the generic `core.Tensor` property path (falling back to the properties when the cache is empty). Output leaves are built into a pre-sized list filled by index, and the same count/dtype/shape validation loop runs over it (the CPU host-staging branch is unchanged); `xla_util._LoadedExecutable` caches `num_outputs` and reuses per-thread ctypes scaffolding in `threading.local` (bounded by `_EXECUTE_SCAFFOLDING_MAX` — thread-local, not shared, so concurrent runs of one executable from different threads stay safe). Output buffers are created with the recorded static metadata PREFILLED (built into a pre-sized list; a tuple `output_meta` is consumed without a per-call copy), `_Buffer.__init__` assigns the handle fields inline instead of calling `_Handle.__init__`, and a destroy call resolves its entry point, args class and handle field ONCE per `api_name` from a per-plugin table while reusing a THREAD-LOCAL args struct (struct-class sizes come from a `_sizeof` cache) — so the per-output destroy churn is a field write plus the FFI call. Prefilled metadata is NEVER trusted blindly: `_Buffer._verify_metadata()` runs the real queries and raises a loud `core.BackendError` on a declared-vs-actual mismatch — every output is verified on an executable's FIRST device-resident run and `_Buffer.to_host()` re-verifies on every explicit readback. A run's whole output set shares ONE client reference and ONE `weakref.finalize` (`_XlaDeviceRunGroup` → `xla_util.release_payloads`); `release_payload` stays the single-buffer wrapper for `upload_tensor`/external payloads, and the public 4-arg `XlaDevicePayload` constructor keeps its own reference/finalizer. Design rationale + A/B medians: `./PER-ADAPTER-NOTES.md`.
- **Error contract (binding):** every PJRT call returns `PJRT_Error*` (NULL = success); the driver checks EVERY call, extracts `PJRT_Error_Message`, destroys the error, and raises `core.BackendError` naming the failing step. All handles are destroyed via matching entry points (try/finally + `close()` helpers; the loaded-executable's inner unloaded twin from `PJRT_LoadedExecutable_GetExecutable` is destroyed first). Header-driven details: `PJRT_Program.format` is `"mlir"`; deserialize is `PJRT_Executable_DeserializeAndLoad`.
- **`check_available()`:** bindings integrity + plugin discovery + `GetPjRtApi` + version gate + a live client create/destroy round-trip. Artifact `runtime_dependencies` records numpy + the `pjrt_c_api` header commit + the plugin platform/version string — no jaxlib.

### TVM (`tvm.py`) — jax-free, jaxlib MLIR bindings only

- **translate:** `tvm.relax.frontend.stablehlo.from_stablehlo(mlir_text)` (this API exists in 0.26; `tvm.relax.frontend.from_mlir` does NOT; build lives in `tvm.relax.vm_build`, re-exported as `tvm.relax.build`).
- **MLIR binding seam (`_mlir_bindings.py`):** ALL MLIR-binding access (context creation, `ir.Module.parse`, the `ir` re-export) routes through this one module, so a future standalone `mlir`/`stablehlo` PyPI package is a one-module swap.
- **jax shim (`tvm_util._install_jax_shim`):** the vendored translator's `from jaxlib import mlir` and `from jaxlib.mlir.dialects import stablehlo` imports work as-is; its single `from jax._src.interpreters import mlir` import (inside `from_stablehlo()`) is satisfied by injected `sys.modules` shims for `jax`, `jax._src`, `jax._src.interpreters` and `jax._src.interpreters.mlir` (the mlir shim provides `make_ir_context()` delegating to `_mlir_bindings.make_ir_context` and re-exports `jaxlib.mlir` as `ir`). Injection happens at the top of BOTH `check_available()` and `ensure_compat()` — before any `tvm.relax.frontend.stablehlo` import — and is idempotent (a real jax already imported in-process is left in place; `sys.modules["jax"] = None` is overwritten).
- **build/run:** `tvm.relax.vm_build.build(mod, target=tvm.target.Target("llvm"))` → `VMExecutable`; run via `tvm.runtime.vm.VirtualMachine(ex, tvm.runtime.cpu())["main"](...)`; inputs `tvm.runtime.tensor(np_array, tvm.runtime.cpu())` (the `tvm.nd` namespace does not exist in TVM 0.26); outputs `tvm.runtime.Tensor.numpy()` → `core.Tensor`.
- **persist:** `VMExecutable.export_library(path)` → host `.so`, base64'd into the payload (`format="tvm-vm-library"`); load decodes to a temp file and `tvm.runtime.load_module(path)` — no recompile at load. (`Module.save_to_file` does not exist in 0.26.)
- **Compatibility shim (REQUIRED):** the 0.26.0 vendored translator targets the OLD jax mlir bindings; `tvm_util.ensure_compat()` patches five gaps (type-check classmethods, OpView/Operation key normalization, `broadcast_to` ShapeExpr, `DenseI64ArrayAttr` decoding, float16 `np.asarray` constant decoding), each restoring exactly the semantics the vendored code assumed (no computation changes).
- **Op coverage gate:** `SUPPORTED_STABLEHLO_OPS` is checked at compile (`core.BackendError` naming the op otherwise) — arithmetic, unary math, compare, select, bitwise/logical, convert, `broadcast_in_dim`, reshape, transpose, concatenate, slice (unit strides), pad (zero interior), reduce (add/max/min/mul), `dot_general` (matmul), constant. Rejected: control flow (`stablehlo.if`/`while`), gather/scatter, remainder, conv/reduce_window (the vendored handlers hardcode NHWC/HWIO — silently wrong for etl's NCHW conv), multi-function modules, multi-output functions.
- **ROCm:** TVM is COMPILE-ONLY on ROCm — the `apache-tvm` 0.26.0 wheel is built `USE_ROCM=OFF`, so `tvm.runtime.device("rocm", 0).exist is False`. Do not include TVM in ROCm run matrices.

## Constraints (binding)

- **Heavy-import rule:** `iree`/`jaxlib`/`tvm` imports live ONLY inside function bodies; top-level imports are limited to stdlib, `etl.core`, and the `..compiler`/`..program`/`..registry` siblings (plus this package's `_pjrt_c_api.py`/`_mlir_bindings.py` for the xla/tvm adapters). Verified: `import etl` leaves `sys.modules` free of iree/jax/jaxlib/tvm.
- **No `jax`:** `import jax` / `from jax` is forbidden anywhere in `etl/` (grep-proof; the TVM shim satisfies the vendored translator's `jax._src` import). `jaxlib` may appear ONLY inside function bodies, ideally only via `_mlir_bindings.py`, and NEVER in the xla adapter (`_pjrt_c_api.py`/`xla_util.py`/`xla.py` are jaxlib-free).
- **Errors:** capability violations and compiler/translator failures raise `core.BackendError` naming the op/feature — never a silent fallback to numpy or partial semantics; load-time mismatches raise `core.PersistenceError`; dtype mismatches `core.DTypeError`; shape mismatches `core.ShapeError`.
- **Staging never composes:** `load` never re-traces/lowers/compiles; device handles are never serialized.
- **Device kinds:** the tvm path is CPU only; the iree AND xla adapters also accept `core.Device("cuda"|"rocm"|"hip", index)` and run device-resident. A device kind the adapter does not support — or a kind the resolved plugin's platform does not physically serve — raises `core.BackendError`; a non-`Device` object raises `core.DeviceError`.

## Design decisions

- **IREE cuda allocator flag — etl sets NO process-global `--cuda_async_allocations` value; iree's own default (`true`, stream-ordered) stands.** Forcing `false` measured ~2–3× slower per step on fused DE/PSO step graphs (numbers: companion). Users who need the classic allocator pool opt in per load via `iree_runtime_args=["--cuda_async_allocations=false"]` or `IREE_PY_RUNTIME_FLAGS`; `upload_tensor` honors the same `ETL_IREE_RUNTIME_ARGS`. Policy point: `_configure_cuda_runtime_flags` in `iree.py` is a deliberate no-op. The `_pool_anchor` is retained ONLY on cuda SEGMENT executables (the one plain-cuda path that still stages host tensors).
- **Adapter defaults are minimal and overridable** — a user flag with the same NAME drops the default (never both), and only the small documented DENY list is rejected. The rocm default flag set is already cost-free (no debug-info / executable-debug-level / truncate-floats flags); there is nothing to remove.

## Known Issues

1. **Writer/export gaps surfaced by the adapters (sibling node `stablehlo/`):** (a) dynamic-shape support is per-op partial and exporter-gated — elementwise symbolic graphs (incl. scalar-constant broadcasts) compile and run on iree/tvm at multiple sizes, while symbolic `reshape`/`conv`/`slice`/`pad` (slice/pad: iree parses but the runtime aborts) and unemittable `dot` batch merges raise an explicit `core.BackendError` at `lower()` naming the op, shape and offending dims; (b) mixed-dtype binary ops with Python scalar constants can produce a dtype mismatch parse error (workaround: explicit `etl.cast`); (c) `stablehlo.add` on i1 is XOR, while numpy bool `+` is OR.
2. **IREE `rng_bit_generator` (empirical, iree 3.11):** the modern two-result syntax is REQUIRED (`%state_out, %out = stablehlo.rng_bit_generator %state, algorithm = THREE_FRY : …` — no shape operand, enum WITHOUT the `RNG_ALG_` prefix); the older shape-operand form is REJECTED. `THREE_FRY` legalizes and runs BIT-EXACT vs numpy with the key-first `[k0',k1',ctr0,ctr1]` state layout on llvm-cpu, cuda and rocm, so `{"threefry2x32"}` is the iree capability and native THREE_FRY is the default path for threefry graphs. `PHILOX` FAILS legalization on BOTH llvm-cpu and cuda (`failed to legalize operation 'stablehlo.rng_bit_generator' … explicitly marked illegal`; 6-word philox state) → philox graphs use the exporter's bit-exact inline expansion. Also: `collective_broadcast` cannot be legalized by iree-compile (upstream) so collectives are off; u32/u64 are excluded (nondeterministic unsigned `reduce`); `random_permutation` graphs on iree-cuda fail deterministically through the 2-operand-sort bug (Known Issue 8g) — cuda RNG benchmarks must exclude permutation.
3. **XLA:** no pip-installable PJRT plugin exists, so the adapter requires a user-provided `.so` exporting `GetPjRtApi` (discovery: `plugin_path` → `ETL_PJRT_PLUGIN` → well-known paths); distribution is out of scope, and the missing-plugin error names the recipe, not a pip package. Load-bearing real-plugin facts: the `GetPjRtApi`→`GetPjrtApi` casing fallback; a non-NULL serialized default `CompileOptionsProto` (`bytes.fromhex("1a0420012801")` = num_replicas=1/num_partitions=1 — a NULL `compile_options` CHECK-crashes the plugin); ONE process-global refcounted `PJRT_Client` per plugin path shared by compile/load/`check_available` (a fresh client per load ABORTs real GPU plugins on BFC-pool exhaustion); a ptxas-PATH hint on compile failures. Residual limits: the artifact is device-agnostic (`target="cpu"`, device chosen at `load()`); native `rng_bit_generator` is OFF (the plugin's spec-strict u64-state importer rejects etl's u32-word key-first state, and XLA's THREE_FRY is threefry2x64 / PHILOX is 2-word philox4x32-10 — different ciphers than etl's threefry2x32 / 4-word philox4x32_10, so native bit-exactness is impossible by design; the per-call option still forces the native path). **ROCm plugin + HIP-graph command buffers:** the rocm plugin SIGSEGVs inside `PJRT_Executable_Execute` for XLA-capture-eligible graphs (it bites the evox SO step graphs) under the default command-buffer kinds; the working recipe is `XLA_FLAGS=--xla_gpu_enable_command_buffer=` (empty kind list ⇒ HIP graphs disabled) plus `ETL_PJRT_PLUGIN=…/jax_plugins/xla_rocm7/xla_rocm_plugin.so` and `HIP_VISIBLE_DEVICES` on a shared multi-GPU box. The adapter deliberately does NOT rewrite `XLA_FLAGS` (no hidden env mutation) — the flag is a caller-supplied recipe that tests, probes and benchmarks export themselves. **Env recipes:** CUDA needs `LD_PRELOAD` of cuDNN and `XLA_FLAGS` pointing at the libdevice data dir; any process that created a PJRT client ABORTS at interpreter exit AFTER all work succeeds (`PJRT_Client_Destroy` does not help) — read stdout / `os._exit(0)`. Full recipes and validation narrative: companion + skill `etl-compiler-adapter-recipes`.
4. **TVM:** control flow, conv, gather/scatter, remainder, multi-function and multi-output modules are rejected by the compile-time gate. The vendored translator requires **jaxlib** at adapter runtime (bundled MLIR bindings via `_mlir_bindings`); the `jax` package is NOT required. When jaxlib is absent, `check_available()` raises `core.BackendError` (pip hint naming jaxlib) — never a raw `ModuleNotFoundError`.
5. **Version floors / extras (edits live at the repo root — escalate):** the `iree` and `compilers` extras pin `iree-base-compiler>=3.11.0,<3.12` and `iree-base-runtime>=3.11.0,<3.12` — compiler and runtime must MATCH (see Known Issue 10); the `tvm` extra pins `apache-tvm>=0.26` AND `jaxlib>=0.10,<0.11`; there is NO `xla` pip extra — the adapter has no pip dependency (the plugin is user-provided). The artifact records the ACTUAL installed distributions as `runtime_dependencies` keys.
6. **nanobind refleak noise:** `iree-base-runtime` 3.x prints "nanobind: leaked N instances/functions/keep_alive records …" to stderr at shutdown — upstream diagnostics, harmless, NOT a test failure.
7. **mixed-install trap:** the old `iree-compiler`/`iree-runtime` and the new `iree-base-*` distributions share the SAME `iree` Python namespace and must NOT coexist. A mixed/residual install produces `ValueError: Error creating vm module … required module features [Ch] are not available in this runtime configuration` at `load` (even for a trivial graph), and a stale pair installed after the base pair silently shadows 3.11.0 inside `iree/`. Fix: purge ALL `iree*` distributions (incl. mangled residue dirs like `~ree_runtime-*.dist-info` and stale `.egg-info`) and reinstall only `iree-base-compiler`/`iree-base-runtime`; check `iree.compiler.version.VERSION` after any install. `load()` wraps this verifier `ValueError` into an actionable `core.BackendError` (original as `__cause__`).
8. **IREE CUDA (iree 3.11):** (a) device ids are 1-BASED (`device_id = index + 1`); (b) `rt.load_vm_flatbuffer`'s driver-name form always creates the DEFAULT device — cuda/rocm modules are bound via `rt.Config` + `rt.VmModule.copy_buffer` + `rt.load_vm_module`; (c) the default codegen target is sm_60 PTX (`+ptx76`), JIT'd by the driver — no arch flag needed; (d) the CUDA HAL driver is compiled INTO the runtime wheel; (e) a cuda-compiled artifact cannot run on the cpu driver (and vice versa) — `load()` rejects the mismatch; pre-CUDA artifacts without `target_backends` load as `["llvm-cpu"]`; (f) **while-loop crashes on the iree cuda HAL are SHAPE-SPECIFIC (upstream):** `while_fib` SEGFAULTS at invoke and `while_cond_combo` ABORTs (`cuda/event_semaphore.c:354 … hal.device.queue.dealloca`) — both pass on llvm-cpu; exclude `while_fib` from iree/cuda runs. The evox `non_dominate_rank` shape needs the exporter's `while_init_rewrite` (default ON); residual: while loops hitting the T2 broadcast-shape class or non-zero vector-constant inits remain broken on iree on both targets — use the unrolled fixed-point or the xla route; (g) **cuda 2-operand-sort bufferization bug:** `error: failed to bufferize op` for the argsort emission (a `stablehlo.sort` of value + i64 iota) whenever the SORTED AXIS SIZE ≥ 32 (≤ 24 passes; 1-operand `sort` and llvm-cpu unaffected) — avoided by `sort_emission="auto"` picking the count composition at that size (bit-exact on cuda, no `stablehlo.sort` in the MLIR); (h) **constant-in-while hoisting bug (both targets):** `'util.global.load' op undefined global: @__hoisted_*` when a CONSTANT tensor is used inside a while body.
9. **IREE opt-level-related cuda limits (upstream iree codegen — do NOT fix in etl):** (a) `--iree-opt-level=O2`/`O3` on cuda silently produce WRONG eigenvalues for the `eigh` cyclic-Jacobi composition (bare eigh and the CMAES fused tell; the tell runs without crashing, just wrong) — O0/O1/default are correct on cuda, and llvm-cpu is correct at ALL levels; (b) the full NSGA2 tell graph FAILS TO COMPILE on cuda at O2/O3 (upstream fusion+hoisting on the crowding-distance scatter; default/O0/O1 work). Both reproduce on raw `iree-compile` of etl-dumped MLIR, unrelated to etl's `opt_level` plumbing.
10. **IREE version matrix for while-loop graphs (upstream):** `iree-base-compiler` 3.10.0 and 3.11.0 SIGSEGV (exit -11) in `IREE::Stream::AffinityAnalysis::run()` (unbounded recursion) on `stablehlo.while` with ≥3 loop-carried values + `select` in the body; SO graphs compile fine. The crash is NONDETERMINISTIC — a per-run lottery on identical MLIR (the same file crashes ~85–100 % of runs), so a single successful compile proves nothing and any while-graph probe must repeat or be treated as flaky. No compiler flag lever fixes it (full sweep: companion), and rewriting the body's `select` as arithmetic masking does not dodge it. What works: remove the `while` (unroll at trace time, or a plain elementwise+reduce while), or a bounded retry loop as a smoke/CI workaround (the recovered artifact runs and matches numpy bit-exactly). 3.9.0 compiles the NSGA2/MOEAD-class graphs cleanly but its cuda runtime crashes (Known Issue 11); 3.12.0rc fixes the compiler but its runtime is unusable for these graphs, and cross-version loading is not a workaround (bytecode version rejected). Conclusion: MO/while-heavy graphs are upstream-blocked on 3.10/3.11 and OUT OF SCOPE — use the numpy backend or the xla route.
11. **iree 3.9.0 cuda RUNTIME SIGSEGV on SO step graphs (driver 535.247.01, RTX A6000):** the evox SO harness crashes ~9/10 runs at the FIRST `etl.run` on cuda (any scale; error-path use-after-free/race in `iree._runtime_libs._runtime*.so`). Also: GPU 7 on this host reports 2689 uncorrected ECC errors (`CUDA_ERROR_ECC_UNCORRECTABLE` at HAL-device creation) — exclude it.
12. **CUDA HAL devices are thread-affine: any allocating HAL op from a thread with no prior CUDA activity fails `CUDA_ERROR_INVALID_CONTEXT`** (`to_host()`, `asdevicearray`, invoke output-alloc — even when the HAL device was created by another thread; the state is thread-local). Per-thread mitigation: the thread first creates its own unused cuda HAL device on the same GPU (`rt.get_driver("cuda").create_device(device_id=idx+1)`), making the shared primary context current; no iree-python API sets context-current directly, and llvm-cpu (local-task) has no such constraint. Implication: cuda/rocm FIFO-worker copies need this one-time bootstrap per worker thread — see `etl/io.py::_bootstrap_worker_context`.
13. **IREE GPU lowering of rank-0-result reductions is a single sequential workgroup — the dominant cost of monitor-style graphs, and NOT fixable with compiler flags.** On a 10000×100 evox SO-shaped step the `argmin`/`min`/i1 NaN-guard reductions are each lowered as ONE workgroup / ONE thread (sequential loop) while every data-parallel sibling dispatch gets a 64-thread workgroup, so three scalar reductions consume ~95 % of per-step time; the cost is constant per step, hence invisible at small population sizes (inside the launch floor) and dominant at large ones. The structural fix is ETL-side and numerically exact: split the reduced axis so the reduction is not rank-0 in one step (`reshape (n,) → (R,C)`, reduce `dim1`, then reduce the rows) — shipped as the `split_reduction` exporter option (default `True`, rank-0-result reductions over a large static dim) and worth ~8–10× on the affected ops; a keepdims reshape to `(n,1)` does NOT help (the split must yield ≥2 non-unit factors), and no compiler flag substitutes for it. RNG is not implicated (on rocm the inline SplitMix64 expansion is faster than the native threefry path for bulk draws). Profiling tables, subgraph attribution and the full flag sweep: companion (`## Known Issue 13`).
14. **Small-scale results are launch-overhead-bound, so iree and xla look equal there** (both sit inside the invoke floor plus wrapper cost); the cross-backend gap only appears once the population is large enough for the constant per-step scalar-reduction cost to dominate. **Measured host cost ladder (MI300X, rocm, 12-in/12-out evox-SO-shaped step, best-of-N≥200):** `etl.run` end-to-end 150 µs iree / 140 µs xla, of which pipeline flatten+validate+unflatten ≈16–31 µs (~20 %) and `backend_executable.run` 124 µs iree / 111 µs xla. Bare-metal bounds: iree prepacked `VmVariantList` 85 µs, iree `entry(*darrs)` 96 µs (ArgumentPacker + DeviceArray extraction), xla raw `PJRT_LoadedExecutable_Execute`+destroy 87 µs (leaky 78 µs); xla `_XlaDeviceRunGroup` + 12 `XlaDevicePayload`s adds ≈14 µs, and payload release is FREE (weakref.finalize, 0.1 µs / 1.0 µs iree). So the addressable gap is ≈54–65 µs/call. Shape of the cost: **per-IO leaf ≈2–3.5 µs** (pipeline and adapter both) and **per-op ≈0** (±1 µs across 1→16 ops), with per-output overhead +12.3 µs iree / +7.2 µs xla — cost tracks leaf count, never graph size, and pytree nesting is irrelevant (a flat 12-tuple leaf set costs the same as the evox 5-child `WorkflowState`). **The PJRT execute floor is not a wait:** four back-to-back leaky executes cost exactly 4× a single execute, and exec-only ≈ exec+destroy − 2 µs/buffer, so the plugin is fully device-synchronous and there is NO removable sync — the only lever is true asynchrony via `PJRT_ExecuteOptions.device_complete_events` (currently left NULL in `xla_util._execute_scaffolding`). Nothing inside `run` performs a D2H copy or a completed-work wait on either adapter (outputs stay device-resident payloads; `.to(cpu)`/`.numpy()` is the caller's explicit readback).
- **ROCm `while_loop`/`scan` unreliability (same upstream family as 8f):** shapes build and compile, but at run the HIP HAL aborts with a RAW `RuntimeError: … hip/event_semaphore.c:786: ABORTED … hal.fence.await` (raised from `entry(*buffers)`, never wrapped in `core.BackendError`), and the process often hangs at teardown. It is deterministic per graph shape, and the same graphs are llvm-cpu-clean. Failing shapes: a loop carry initialized from a graph CONSTANT (`enp.zeros` — also why `etl.scan` fails) and a multi-carry loop whose condition reads the float carry; working bit-exact: condition on an i64 counter with input-derived carries.

## Dependency surface

- **xla adapter:** ZERO pip dependencies. A user-provided PJRT plugin `.so` (exporting `GetPjRtApi`) is required at compile/load time, discovered via `options["plugin_path"]` → `ETL_PJRT_PLUGIN` → well-known paths. Bindings provenance (header URL + commit) is recorded in `_pjrt_c_api.py` and in the artifact `runtime_dependencies`.
- **tvm adapter:** `apache-tvm` + `jaxlib` (MLIR bindings only). The `jax` package is never imported anywhere in `etl/`. `check_available()` probes `jaxlib.mlir` + `jaxlib.mlir.ir` (pip hint `pip install etl[tvm]`).
- **Legitimately long files — do not split without a plan:** `iree.py` (2911 lines) holds the whole iree adapter surface (options/defaults, `IreeBackend`, `IreeExecutable` + its cached run plans, `_build_buffers`/`_staged_input`/`_wait_copy_semaphore`, `_IreeSegmentExecutable`, `IreeExternalExecutable`, the public `IreeDevicePayload` + the run-path metadata helpers `_runtime_modules`/`_hal_element_dtype`/`_input_plan`, `upload_tensor`, `register()`); its pieces share tight coupling (staging caches, payload wrapping, `core.Device` ↔ HAL device mapping). `xla.py` (1210 lines) is the backend/executable surface (options tables, static-shape gate + recorded-shape enforcement, `_XlaRunPlan`, `_XlaDeviceRunGroup`, device-kind serving checks, `upload_tensor`, `register()`), and `xla_util.py` (1342 lines) the PJRT C API driver. All three are cohesive; splitting would spread one adapter's invariants across files for no delegation benefit.

## Test strategy

Committed adapter tests live in the SIBLING `tests/backends/` (read-only from here — test-related writes escalate to the repo root).
`test_options_override.py` (96) + `tests/test_pipeline_options.py` (61) pin the options-override semantics (keys, defaults, conflict rules, env precedence, the exporter-forwarded lower options).
`test_opt_level.py` (53), `test_split_reduction.py` (67), `test_iree_split_reduction_parity.py` (127) and `test_while_init_rewrite.py` (4) pin the etl-defined option translations and the exporter options' effects.
`test_xla_device_resident.py` (9, fake plugin) pins xla device-resident staging (zero-staging same-device loop, run-boundary host-input `DeviceError`, load-device validation, payload/client lifecycle) plus the rank-0 staging guard; `test_pjrt_ctypes_plugin.py` (10) pins the ABI checks + shared-client refcount; `test_adapter_xla.py` / `test_adapter_iree.py` / `test_adapter_tvm.py` hold the per-adapter end-to-end numerics.
iree E2E suites: `test_iree_emitters_parity.py`, `test_iree_random_algorithms_parity.py`, `test_iree_eigh_diag_parity.py`, `test_iree_device_resident.py`, `test_iree_same_device_loop.py`, `test_iree_hotpath_validation.py`, `test_iree_llvm_cpu_host_inputs.py`, `test_iree_rocm_device_resident.py` (rocm-guarded via `_rocm_guard.py`), `test_external_call_iree.py` (39), `test_external_batched_iree.py` (6), `test_build_cache_iree.py`, `test_nsga2_xla_route.py`.
CPU only, pytest, numpy-only deps; GPU suites are GPU-guarded.
Per-file assertions, the throwaway fake-plugin/TVM probe recipes, and the pytest note (`-q` suppresses the final "N passed" line — use `-v` or `-o addopts=`) live in the skill `etl-compiler-adapter-recipes`.
**Coverage gap:** the per-call hot-path machinery (per-thread execute-scaffolding cache, prefilled output metadata + `_verify_metadata`, the `_XlaDeviceRunGroup` shared client reference) has no direct assertion — it is exercised by every device-resident run, and the SEMANTICS it must preserve are pinned (zero-staging same-device loop, shared-client refcount, host-input `core.DeviceError`, non-cpu `.numpy()` raising, explicit `to(cpu)` round-trips). Under the current explicit-placement semantics, GPU tests written for host-input semantics fail with the intentional `DeviceError` pin category — a root-level follow-up converts them to explicit placement.
ROCM-specific gaps: rocm × `external_call`/segment staging, direct thread-locality of the staging caches (pinned only indirectly), and a real-rocm `upload_tensor` on the `etl.io` worker thread (`prefetch`) are not covered.
