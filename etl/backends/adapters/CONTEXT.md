# etl/backends/adapters — optional compiler adapters (IREE, XLA via PJRT, TVM)

## Intent

Pluggable compiler backends for etl. Each adapter consumes the SHARED StableHLO lowering produced by `CompilerBackend.lower` (`../compiler.py` — verify, capability pre-check, block-portable inlining, StableHLO export, Signature recording) and implements only the compiler-specific half: optional dependency probe (`check_available` override — the shared base is a concrete no-op), `compile` (invoke the external compiler on the MLIR text), `load` (rebuild the executable from the artifact — never re-compiling). Activation is register-on-first-use: `etl.backends.registry.get(name)` imports the adapter module via `registry.OPTIONAL_ADAPTERS` and calls its `register()`; `import etl` never imports an adapter or its compiler dependency.

**Dependency posture (binding):** etl depends directly on the ML compilers — the `jax` frontend package appears NOWHERE in `etl/`, and the xla adapter uses no jaxlib either:
- **xla** = the PJRT C API via pure-stdlib ctypes against a USER-PROVIDED plugin binary (`.so` exporting `GetPjRtApi`) — there is no pip-installable package (verified: no standalone xla/pjrt/jax-cpu/stablehlo/mlir packages on PyPI; no `pjrt_c_api_cpu_plugin.so` in any jaxlib wheel (0.4.38, 0.10.2 checked — the CPU client is embedded in `_xla.so`); jaxlib's `_xla.so` does not export `GetPjRtApi`). Plugin distribution is explicitly OUT of scope.
- **tvm** = apache-tvm + jaxlib, where jaxlib is used ONLY for its bundled LLVM MLIR python bindings (a verbatim upstream-bindings bundle — the same bindings any MLIR tooling uses, NOT the jax API), behind the `_mlir_bindings` seam. The vendored TVM translator's `jax._src.interpreters.mlir` import is satisfied by an injected shim; the `jax` package is never imported.

Status: all three adapters implemented and validated. iree against the installed iree distributions (3.11.0 `iree-base-*` and legacy 20241104.1068); xla against a THROWAWAY fake PJRT plugin (ctypes layout/offsets, dispatch, error handling, lifecycle, serialize round-trip — real-plugin end-to-end parity PENDING a real `.so`, see Known Issues); tvm against apache-tvm 0.26.0 + jaxlib 0.10.2 (numpy parity incl. dynamic shapes, jax-package-free verified with `sys.modules["jax"] = None`).

## API Surface

Each adapter module (`iree.py`, `xla.py`, `tvm.py`) exposes the same shape:
- `<Name>Backend` (a `CompilerBackend` subclass; names `"iree"`, `"xla"`, `"tvm"`), `<Name>Executable` (a `CompilerExecutable` subclass), singleton `<name>_backend`, module-level `register()` (probes the dependency — `core.BackendError` with an actionable message when missing — then registers idempotently).
- `<name>_util.py` helpers: `xla_util.py` (PJRT C API driver: plugin discovery/loading, version gate, client/compile/execute/buffer/serialize plumbing), `tvm_util.py` (vendored-translator compat shim + jax `sys.modules` shim injection, op whitelist gate, translate/build/run/persist helpers).
- `_pjrt_c_api.py`: vendored ctypes translation of the Apache-2.0 PJRT C API header (header URL + commit recorded; ABI/offsets verified against a plugin compiled from the real header); `_mlir_bindings.py`: the MLIR binding-provider seam (jaxlib → standalone swap).
- `__init__.py`: documentation only, imports nothing heavy.

## Adapter designs (validated end-to-end, numpy-backend parity)

### IREE (`iree.py`)

- compile: `iree.compiler.compile_str(mlir_text, target_backends=["llvm-cpu"], input_type="stablehlo", extra_args=["--iree-input-demote-f64-to-f32=false", "--iree-llvmcpu-target-cpu=generic"])` → VM flatbuffer, base64'd into the payload (`format="iree-vmfb"`, keeps `mlir_text` + `entry_functions`). Compiler diagnostics re-raised as `core.BackendError` (never silent).
- load/run: device via the RELIABLE path `iree.runtime.get_driver("local-task")` + `driver.create_default_device()` (the `rt.system_setup(config=...)` form intermittently fails with `TypeError: 'module' object is not callable` — submodule shadowing in iree.runtime's package init; do not reintroduce it); `iree.runtime.load_vm_flatbuffer(flat, driver="local-task")`; inputs `iree.runtime.asdevicearray(device, tensor.numpy())`; outputs `np.asarray(result)` → `core.Tensor`.
- Capabilities: `dynamic_shapes=True` (symbolic dims run at multiple concrete sizes); `dtypes` = f16/f32/f64/i8/i16/i32/i64/bool (unsigned ints excluded — iree-compile 20241104 legalizes unsigned `reduce` nondeterministically/not at all; complex excluded — the exporter v1 defers complex computation beyond cast); `collectives=False`, `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`.

### XLA via the PJRT C API (`xla.py`) — no jaxlib

- **Plugin** (distribution OUT of scope — users provide the binary): resolved in order (a) `options["plugin_path"]` (backend compile options, e.g. `etl.compile(lowered, backend="xla", plugin_path="/path/to/pjrt_c_api_cpu_plugin.so")`), (b) env `ETL_PJRT_PLUGIN`, (c) well-known paths (`/usr/local/lib`, `/usr/lib`, `$HOME/.local/lib`, `./`). None found ⇒ `core.BackendError` with an actionable message (build via `bazel build //xla/pjrt/c:pjrt_c_api_cpu_plugin` from OpenXLA, or any XLA build exporting `GetPjRtApi`). NO pip hint — there is no pip-installable plugin. jaxlib is NEVER imported in this adapter.
- compile: `ctypes.CDLL(path)` → `GetPjRtApi()` → **version gate** (`PJRT_Api.version`/`struct_size` vs the bindings' minimum — too old ⇒ explicit `BackendError`, never silent fallback) → `PJRT_Client_Create` (empty options) → `PJRT_Client_Compile` with `PJRT_Program{code=mlir_text, format="mlir"}` — the plugin accepts MLIR text directly (header-documented: "MLIR module bytecode (or string)"; the same thing jax's own PJRT layer passes). NO MLIR python bindings anywhere in the adapter. `PJRT_Executable_Serialize` → bytes → base64 in the artifact payload (alongside `mlir_text` + `entry_functions`).
- load/run: deserialize via `PJRT_Executable_DeserializeAndLoad` on a fresh client from the re-discovered plugin — never recompiles (a successful load hands the client to the executable; it is destroyed only on failure); inputs staged via `PJRT_Client_BufferFromHostBuffer` (all 14 etl dtypes incl. complex64/128, dense row-major numpy, `np.ascontiguousarray`, `kImmutableUntilTransferCompletes`, transfer event awaited + destroyed, host array kept alive on the buffer — some plugins alias host memory beyond the documented point); execute via `PJRT_LoadedExecutable_Execute` on the first addressable device; outputs copied via `PJRT_Buffer_ToHostBuffer` → writable numpy → `core.Tensor`.
- **Error contract (binding)**: every PJRT call returns `PJRT_Error*` (NULL = success); the driver checks EVERY call, extracts `PJRT_Error_Message` text, destroys the error, and raises `core.BackendError` naming the failing step. All handles (errors/clients/executables/buffers/events/serialized wrappers) destroyed via matching entry points (try/finally + `close()` helpers; the loaded-executable's inner unloaded twin from `PJRT_LoadedExecutable_GetExecutable` is destroyed first).
- Capabilities: `dynamic_shapes=False` (compile-time static-shape gate via `_resolve_static_shape`/`_StaticShapeError`; the gate decision is recorded in the artifact (`static_input_shapes`/`static_output_shapes`) and enforced exactly at `run()`); `dtypes` = all 14 etl dtypes; `collectives=False` (conservative — see Known Issues); `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`.
- `check_available()`: bindings integrity + plugin discovery + `GetPjRtApi` + version gate + live client create/destroy round-trip. Artifact `runtime_dependencies` records numpy + the `pjrt_c_api` header commit (bindings provenance) + plugin platform/version string — no jaxlib.

### TVM (`tvm.py`) — jax-free, jaxlib MLIR bindings only

- translate: `tvm.relax.frontend.stablehlo.from_stablehlo(mlir_text)` (exists in 0.26; `tvm.relax.frontend.from_mlir` does NOT; `tvm.relax.vm.build` does NOT — build lives in `tvm.relax.vm_build`, re-exported as `tvm.relax.build`). The vendored translator parses MLIR with jaxlib's bundled bindings — hence tvm needs **jaxlib** (NOT the `jax` package) at adapter runtime.
- **MLIR binding seam (`_mlir_bindings.py`)**: ALL MLIR-binding access (context creation, `ir.Module.parse`, the `ir` re-export) routes through this one module; its docstring documents the binding-provider contract — jaxlib is required ONLY for its bundled LLVM MLIR python bindings and a future standalone `mlir`/`stablehlo` PyPI package can replace jaxlib with a one-module swap.
- **jax shim (`tvm_util._install_jax_shim`)**: the vendored translator imports `from jaxlib import mlir` (12 sites) and `from jaxlib.mlir.dialects import stablehlo` (2 sites) — those work as-is — plus `from jax._src.interpreters import mlir as jax_mlir` (1 site, inside `from_stablehlo()`: `jax_mlir.make_ir_context()` + `jax_mlir.ir.Module.parse`). That one import is satisfied by injected `sys.modules` shims for `jax`, `jax._src`, `jax._src.interpreters`, `jax._src.interpreters.mlir` (the mlir shim provides `make_ir_context()` delegating to `_mlir_bindings.make_ir_context` and re-exports `jaxlib.mlir` as `ir`). Injection happens at the top of BOTH `check_available()` and `ensure_compat()` — before any `tvm.relax.frontend.stablehlo` import (in 0.26.0 the translator's jax import executes inside `from_stablehlo()`; the shim covers import-time and call-time, and future TVM versions that move it to module level). Idempotent; a real jax already imported in-process is left in place; `sys.modules["jax"] = None` is overwritten by the shim. Verified end-to-end with real jax blocked.
- build/run: `tvm.relax.vm_build.build(mod, target=tvm.target.Target("llvm"))` → `VMExecutable`; run via `tvm.runtime.vm.VirtualMachine(ex, tvm.runtime.cpu())["main"](...)`; inputs `tvm.runtime.tensor(np_array, tvm.runtime.cpu())` (the `tvm.nd` namespace no longer exists); outputs `tvm.runtime.Tensor.numpy()` → `core.Tensor`.
- persist: `VMExecutable.export_library(path)` → host .so, base64'd into the payload (`format="tvm-vm-library"`); load decodes to a temp file and `tvm.runtime.load_module(path)` — no recompile at load. `Module.save_to_file` does not exist in 0.26.
- Compatibility shim (REQUIRED): the TVM 0.26.0 vendored StableHLO translator targets the OLD jax mlir python bindings; `tvm_util.ensure_compat()` patches five gaps (type-check classmethods, OpView/Operation key normalization, `broadcast_to` ShapeExpr, `DenseI64ArrayAttr` decoding, float16 np.asarray constant decoding) — each patch restores exactly the semantics the vendored code assumed, no computation changes.
- Op coverage gate: `SUPPORTED_STABLEHLO_OPS` whitelist checked at compile (`core.BackendError` naming the op otherwise): arithmetic, unary math, compare, select, bitwise/logical, convert, broadcast_in_dim, reshape, transpose, concatenate, slice (unit strides), pad (zero interior), reduce (add/max/min/mul), dot_general (matmul), constant. Rejected: control flow (`stablehlo.if`/`while`), gather/scatter, remainder, conv/reduce_window (vendored handlers hardcode NHWC/HWIO — silently wrong for etl's NCHW conv), multi-function modules, multi-output functions.
- Capabilities: `dynamic_shapes=True` (symbolic dims validated at multiple sizes, constant-free graphs); `dtypes` = f16/f32/f64/i8/i16/i32/i64/u8/u16/u32/u64/bool (complex excluded — vendored translator raises); `collectives=False`, `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`.

## Constraints (binding)

- Heavy-import rule: `iree`/`jaxlib`/`tvm` imports live ONLY inside function bodies; top-level imports limited to stdlib, `etl.core`, and the `..compiler`/`..program`/`..registry` siblings (plus this package's `_pjrt_c_api.py`/`_mlir_bindings.py` for the xla/tvm adapters). Verified: `import etl` leaves `sys.modules` free of iree/jax/jaxlib/tvm.
- **No `jax`**: `import jax` / `from jax` is forbidden anywhere in `etl/` (grep-proof; the TVM shim satisfies the vendored translator's `jax._src` import). `jaxlib` may appear ONLY inside function bodies, ideally only via `_mlir_bindings.py`, and NEVER in the xla adapter (`_pjrt_c_api.py`/`xla_util.py`/`xla.py` are jaxlib-free).
- Errors: capability violations and compiler/translator failures raise `core.BackendError` naming the op/feature — never silent fallback to numpy or partial semantics; load-time mismatches raise `core.PersistenceError`; dtype mismatches `core.DTypeError`, shape mismatches `core.ShapeError` (mirrors the numpy interpreter).
- Staging never composes: `load` never re-traces/lowers/compiles; device handles are never serialized.
- CPU only; non-CPU devices raise `core.BackendError`, non-`Device` objects `core.DeviceError`.

## Known Issues

1. **Writer/export gaps surfaced by adapters (sibling-node `stablehlo/` — out of this node's scope):** (a) symbolic-dim graphs mixing scalar-constant broadcasts (e.g. `relu`) export `broadcast_in_dim` to a dynamic-shape result, which the StableHLO verifier forbids — honest compile-time `BackendError` (the spec'd `dynamic_broadcast_in_dim` path exists in iree-compile but the writer does not emit it); (b) mixed-dtype binary ops with Python scalar constants can produce a dtype mismatch parse error (workaround: explicit `etl.cast`); (c) `stablehlo.add` on i1 is XOR vs numpy bool+ = OR (export semantic gap).
2. **IREE:** `collective_broadcast` cannot be legalized by iree-compile 20241104 llvm-cpu (upstream); collectives are off (see capabilities). u32/u64 excluded due to nondeterministic legalization (upstream race). Cosmetic compiler warnings about generic CPU target.
3. **XLA:** no pip-installable PJRT plugin exists (verified against PyPI + jaxlib wheels) — the adapter requires a user-provided `.so` exporting `GetPjRtApi` (env `ETL_PJRT_PLUGIN` or `options["plugin_path"]`); distribution is out of scope. Validated end-to-end against a THROWAWAY fake plugin (hard ABI check: plugin `sizeof(PJRT_Api)` == ctypes 1144 + field-offset checks; client create / compile of real etl StableHLO text / stage / execute / copy / serialize+deserialize round-trip; injected error ⇒ `BackendError` carrying the plugin message; version gate rejection; missing-plugin message). REAL-plugin end-to-end parity is PENDING a real `.so` (e.g. `bazel build //xla/pjrt/c:pjrt_c_api_cpu_plugin` from OpenXLA). `collectives=False` is conservative (single-replica collective-broadcast was unimplemented at run time on the jaxlib-era XLA:CPU — re-probe against the chosen plugin before flipping). Header-driven deviations from the original design: `PJRT_Program.format` is `"mlir"` (not "stablehlo"); the deserialize entry point is `PJRT_Executable_DeserializeAndLoad`. **Stale sibling tests (root-level follow-up):** `../../../tests/backends/test_adapter_xla.py` still gates on `pytest.importorskip("jaxlib")` and its fixture now errors with the plugin-missing `BackendError` (jaxlib installed ⇒ no skip) — it needs a plugin-presence gate (skip unless `ETL_PJRT_PLUGIN`/`plugin_path` yields a plugin); `test_adapters_optional.py::test_missing_dep_raises_backend_error_with_install_hint[xla]` asserts the old `("etl[xla]", "jaxlib")` hint — update the xla case to the plugin contract (e.g. hints `("ETL_PJRT_PLUGIN", "plugin_path", "bazel build")`, blocked module arbitrary — the adapter never imports deps).
4. **TVM:** control flow, conv, gather/scatter, remainder, multi-function/multi-output modules rejected by the compile-time gate. The vendored translator requires **jaxlib** at RUNTIME of the adapter (its bundled MLIR bindings, via the `_mlir_bindings` seam); the `jax` package is NOT required (shim — verified with real jax blocked).
5. **Version floors / extras (feed the pyproject extras — edits live at the repo root, escalate):** iree validated end-to-end on the CURRENT distributions `iree-base-compiler`/`iree-base-runtime` 3.11.0 (numerical parity, dynamic shapes, artifact round-trips — the adapter tests + full etl suite are green on that exact stack) and on the legacy 20241104.1068 release (distributed under the old `iree-compiler`/`iree-runtime` names); the extra pins `iree-base-compiler>=2.9.0`/`iree-base-runtime>=2.9.0` — the current IREE distribution names, first released at 2.9.0. tvm validated on `apache-tvm 0.26.0` + `jaxlib 0.10.2` — the extra must pin `apache-tvm>=0.26` AND `jaxlib>=0.10,<0.11` (jaxlib only for its MLIR bindings; `from_stablehlo` exists only in 0.26). The `xla` extra no longer names a pip dependency (the plugin is user-provided) — root decides whether to keep a vestigial `etl[xla]` extra. The artifact records the ACTUAL installed distributions as `runtime_dependencies` keys.
6. **nanobind refleak noise:** `iree-base-runtime` 3.x prints "nanobind: leaked N instances/functions/keep_alive records ... likely caused by a reference counting issue in the binding code" to stderr at interpreter shutdown. This is upstream runtime shutdown diagnostics, harmless, and NOT a test failure — do not chase it.
7. **mixed-install trap:** the old `iree-compiler`/`iree-runtime` and the new `iree-base-*` distributions share the SAME `iree` Python namespace and must NOT coexist. A mixed/residual install (e.g. pip uninstall leaving dist-info/egg-info residue) produced `ValueError: Error creating vm module ... required module features [Ch] are not available in this runtime configuration` at `load` — even for a trivial graph. If that error ever appears, purge ALL `iree*` distributions from site-packages (including mangled residue dirs like `~ree_runtime-*.dist-info` and stale `.egg-info`) and reinstall only `iree-base-compiler`/`iree-base-runtime`. The adapter's `load()` wraps this verifier `ValueError` into an actionable `core.BackendError` (original as `__cause__`) naming the symptom, the mixed-install cause, and the purge-and-reinstall remedy.

## Dependency surface (verified at runtime: jaxlib 0.10.2 / apache-tvm 0.26.0)

- **xla adapter**: ZERO pip dependencies. A user-provided PJRT plugin `.so` (exporting `GetPjRtApi`) is required at compile/load time, discovered via `options["plugin_path"]` → `ETL_PJRT_PLUGIN` → well-known paths. Bindings provenance (header URL + commit) is recorded in `_pjrt_c_api.py` and in the artifact `runtime_dependencies` (`pjrt_c_api` header commit + plugin platform/version).
- **tvm adapter**: `apache-tvm` + `jaxlib` (MLIR bindings only). The `jax` package is never imported anywhere in `etl/`; the vendored translator's `jax._src.interpreters.mlir` import resolves to the `_mlir_bindings`-backed shim. `tvm_util` routes all MLIR access (`parse_stablehlo`, `precheck_module`, `ensure_compat` patches, `_op_key`) through `_mlir_bindings` (`make_ir_context`, `parse_module`, `ir` re-export). `check_available()` probes `jaxlib.mlir` + `jaxlib.mlir.ir` (pip hint `pip install etl[tvm]`).
- Facts that drove this design (verified; do not re-investigate): NO standalone xla/pjrt/jax-cpu/stablehlo/mlir packages on PyPI (only squatter placeholders); NO `pjrt_c_api_cpu_plugin.so` in any jaxlib wheel (0.4.38, 0.10.2 checked — CPU PJRT client embedded in `_xla.so`); jaxlib's `_xla.so` does not export `GetPjRtApi`; `iree.compiler.dialects` has no stablehlo module. The former jaxlib-based xla design (`jaxlib.xla_client`: `make_cpu_client`, `batched_device_put`, `compile_and_load`, `serialize`/`deserialize_executable`) is gone — see git history.
