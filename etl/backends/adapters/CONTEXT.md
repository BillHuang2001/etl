# etl/backends/adapters — optional compiler adapters (IREE, XLA via PJRT, TVM)

## Intent

Pluggable compiler backends for etl. Each adapter consumes the SHARED StableHLO lowering produced by `CompilerBackend.lower` (`../compiler.py` — verify, capability pre-check, block-portable inlining, StableHLO export, Signature recording) and implements only the compiler-specific half: optional dependency probe (`check_available` override — the shared base is a concrete no-op), `compile` (invoke the external compiler on the MLIR text), `load` (rebuild the executable from the artifact — never re-compiling). Activation is register-on-first-use: `etl.backends.registry.get(name)` imports the adapter module via `registry.OPTIONAL_ADAPTERS` and calls its `register()`; `import etl` never imports an adapter or its compiler dependency.

**Dependency posture (binding):** etl depends directly on the ML compilers — the `jax` frontend package appears NOWHERE in `etl/`, and the xla adapter uses no jaxlib either:
- **xla** = the PJRT C API via pure-stdlib ctypes against a USER-PROVIDED plugin binary (`.so` exporting `GetPjRtApi`) — no pip-installable package exists (verified: no standalone xla/pjrt/jax-cpu/stablehlo/mlir packages on PyPI; no `pjrt_c_api_cpu_plugin.so` in any jaxlib wheel (0.4.38, 0.10.2 checked — the CPU client is embedded in `_xla.so`); jaxlib's `_xla.so` does not export `GetPjRtApi`). Plugin distribution is explicitly OUT of scope.
- **tvm** = apache-tvm + jaxlib, where jaxlib is used ONLY for its bundled LLVM MLIR python bindings (the same bindings any MLIR tooling uses, NOT the jax API), behind the `_mlir_bindings` seam. The vendored TVM translator's `jax._src.interpreters.mlir` import is satisfied by an injected shim; the `jax` package is never imported.

Status: all three adapters implemented and validated. iree end-to-end on CPU, CUDA (8× RTX A6000) and ROCm/HIP (MI300X gfx942); xla against a throwaway fake PJRT plugin AND the REAL `jax_cuda12_pjrt` 0.10.2 CUDA plugin and the REAL `jax-rocm7-pjrt` 0.11.2 ROCm plugin (GPU probe `bench_logs/probe_xla_gpu_validation.py` **26/26 PASS**: rank-0 staging, PSO/DE/OpenES-shaped steps, RNG bit-exactness for threefry2x32 + philox4x32_10, non-dominate-rank while_loop — bit-exact vs numpy except the documented fp32 budgets); tvm on apache-tvm 0.26.0 + jaxlib 0.10.2 (numpy parity incl. dynamic shapes, jax-package-free verified with `sys.modules["jax"] = None`).

## API Surface

Each adapter module (`iree.py`, `xla.py`, `tvm.py`) exposes the same shape:
- `<Name>Backend` (a `CompilerBackend` subclass; names `"iree"`, `"xla"`, `"tvm"`), `<Name>Executable` (a `CompilerExecutable` subclass), singleton `<name>_backend`, module-level `register()` (probes the dependency — `core.BackendError` with an actionable message when missing — then registers idempotently). The iree `register()` additionally installs its module-level `upload_tensor` into the PER-BACKEND device-transfer slot for kind `"cuda"` under backend `"iree"` (see `core.register_backend_device_transfer_provider`; per-backend slots — activating any backend never clobbers another's provider or the flat DEFAULT slot; `etl.backends` pre-registers a lazy delegating thunk in the DEFAULT slot at import time so placement works even before the adapter activates, see the IREE section).
- `<name>_util.py` helpers: `xla_util.py` (PJRT C API driver: plugin discovery/loading, version gate, client/compile/execute/buffer/serialize plumbing), `tvm_util.py` (vendored-translator compat shim + jax `sys.modules` shim injection, op whitelist gate, translate/build/run/persist helpers).
- `_pjrt_c_api.py`: vendored ctypes translation of the Apache-2.0 PJRT C API header (header URL + commit recorded; ABI/offsets verified against a plugin compiled from the real header); `_mlir_bindings.py`: the MLIR binding-provider seam (jaxlib → standalone swap).
- `__init__.py`: documentation only, imports nothing heavy.

## Options override (per adapter — quick reference)

All keys pass through `lower`/`compile`/`load`/`run` + `build`/`evaluate` as `**options`; option NAMES validated per backend (union of stages, see `../CONTEXT.md` "Backend options override"), VALUES never validated by etl (the ONE exception is `opt_level`). Precedence: explicit kwarg > env var > etl default (env table in `etl/pipeline_options.py`).

| Backend | Stage | Option key | Env var | Notes |
|---|---|---|---|---|
| iree | compile | `target_backends` (list[str]) | `ETL_TARGET_BACKENDS` | `{"llvm-cpu","cuda","rocm"}`; drives `--iree-hal-target-backends` (that flag itself is DENIED). The `rocm` target also gets the detected `--iree-rocm-target=<arch>` default (see the ROCm section) |
| iree | compile | `iree_compile_args` (list of flags) | `ETL_IREE_COMPILE_ARGS` | arbitrary iree-compile flags appended after the minimal defaults; a same-NAME flag drops the default; DENY list `--iree-hal-target-backends`, `--iree-input-type`, `--iree-vm-bytecode-module-output-format` with reasons |
| iree | compile | `opt_level` (str\|int) | — | `"O0"`..`"O3"` (case-insensitive) or 0..3 → the DERIVED flag `--iree-opt-level=O{N}` (the O-form is REQUIRED — iree-base-compiler 3.11 rejects numeric levels, verified empirically). A user `--iree-opt-level=…` in `iree_compile_args`/`ETL_IREE_COMPILE_ARGS` wins, the derived flag is dropped (never both). NOT in the DENY list. Unset = no flag, byte-identical |
| iree | load | `iree_runtime_args` (list of flags) | `ETL_IREE_RUNTIME_ARGS` | loader/HAL flags via `rt.flags.parse_flags` (loud errors); etl sets NO process-global runtime flag — iree's own `--cuda_async_allocations=true` (stream-ordered) default stands; override per-load here or via `IREE_PY_RUNTIME_FLAGS` |
| xla | compile AND load | `plugin_path` (str) | `ETL_PJRT_PLUGIN` | plugin discovery; honored at load too (re-discovery gap fix) |
| xla | compile | `xla_compile_options` (bytes) | `ETL_XLA_COMPILE_OPTIONS` (base64) | raw serialized `xla.CompileOptionsProto` into `PJRT_Client_Compile_Args.compile_options`; unset → the probe-validated default `bytes.fromhex("1a0420012801")` (num_replicas=1/num_partitions=1 — real plugins CHECK-crash on NULL) |
| xla | compile | `opt_level` (str\|int) | — | injected into the compile options' `executable_build_options` (wire-format field 24) by `xla_util.set_opt_level`; an optimization level already present in `xla_compile_options` wins unchanged (conflict rule — never both); unset → bytes untouched |
| tvm | compile | `tvm_target` (str) | `ETL_TVM_TARGET` | default `"llvm"` |
| tvm | compile | `tvm_pass_configs` (dict) | `ETL_TVM_PASS_CONFIGS` (JSON) | forwarded only when non-None; the installed TVM 0.26 `build` lacks the param → loud `BackendError` |
| tvm | compile | `opt_level` (str\|int) | — | forwarded to `tvm_util.build_vm_executable(..., opt_level=N)` as a version-adaptive kwarg (the `pass_configs` pattern): installed TVM 0.26 has NO `opt_level` kwarg and a probe proved `PassContext(opt_level=N)` does NOT reach the LLVM codegen → a build without the kwarg raises a LOUD `core.BackendError` naming `opt_level` and the installed TVM (never silently dropped). Unset = byte-identical default |
| all | lower | `rng_bit_generator` (bool\|collection) | — | reserved StableHLO-export override |
| iree | lower | `sort_emission` (str) | — | reserved exporter override `"pair"`\|`"count"`\|`"auto"`; iree ClassVar default `"auto"` — count iff sorted extent ≥ 32 (the cuda 2-operand-sort bufferization workaround) |
| iree | lower | `while_init_rewrite` (bool) | — | reserved exporter override; defaults ON at export (hardcoded in `../compiler.py::_exporter_options`, NOT a ClassVar) — the T1 constant-init while-SEGV workaround |
| all (iree/xla/tvm) | lower | `dot_precision` (str) | — | reserved exporter option `"DEFAULT"`\|`"HIGH"`\|`"HIGHEST"` (case-insensitive). Default `"DEFAULT"` emits NO `precision_config` (byte-identical export); `"HIGH"`/`"HIGHEST"` stamp `precision_config = [#stablehlo<precision CFG>, …]` on every `stablehlo.dot_general`. Only `"HIGHEST"` disables the TF32-class reduced-precision fp32 `dot` — the option's reason: real MI300X + `jax_rocm7_pjrt` 0.11.2 n=1024 fp32 matmul vs fp64 → default max_abs 0.1228 vs `"HIGHEST"` 0.000203 (true fp32); `"HIGH"` does NOT help on this XLA version. iree/llvm-cpu and tvm/llvm PARSE+COMPILE+RUN the attributed text with results BIT-IDENTICAL to `"DEFAULT"` (documented no-op). An invalid value raises the exporter's `core.BackendError` |
| numpy | run | `rank_context` (`dist.RankContext`) | — | reference backend documents-ignores unknown keys |
| iree/xla/tvm | run | — (none in v1) | — | non-empty run options → loud `BackendError` (by design) |

**Exporter-option plumbing (for adding new options):** no adapter overrides `lower()` — the shared `CompilerBackend.lower` validates `options` via `options.validate_options` (union of `KNOWN_OPTIONS` stage sets) and builds the export dict in `_exporter_options`, which forwards `rng_bit_generator`/`sort_emission`/`while_init_rewrite`/`dot_precision`. `eigh_early_exit` is a writer-only option NOT plumbed through the adapter path (passing it to `etl.lower(..., backend="iree")` raises the unknown-key `BackendError`). A NEW exporter option requires three touches: add it to `_exporter_options`, declare it in each adapter's `KNOWN_OPTIONS["lower"]` (all three declare `rng_bit_generator` + `dot_precision`; iree additionally `sort_emission`/`while_init_rewrite`), and consume it in the stablehlo Writer (sibling node).

## Adapter designs (validated end-to-end, numpy-backend parity)

### IREE (`iree.py`) — CPU (llvm-cpu), CUDA GPU AND ROCm/HIP GPU

- **compile:** `iree.compiler.compile_str(mlir_text, target_backends=..., input_type="stablehlo", extra_args=resolved_args)` → VM flatbuffer, base64'd into the payload (`format="iree-vmfb"`, keeps `mlir_text` + `entry_functions` + `target_backends`). Compile targets come from the `target_backends` compile option, default `["llvm-cpu"]`; v1 supported set `{"llvm-cpu","cuda","rocm"}` — a non-list/tuple, empty list, or unknown target raises `core.BackendError` naming the offender. `CompiledArtifact.target` = `"cpu"` / `"cuda"` / `"rocm"` / `"+"`-joined for mixed lists. Compiler diagnostics re-raised as `core.BackendError` (never silent). The default codegen target is sm_60 PTX (`+ptx76`), JIT'd by the CUDA driver to the A6000s' sm_86 at load — no arch flag needed for the A6000s.
- **Compile flags are user-overridable (`iree_compile_args`)** — the adapter's fixed flags are minimal and DOCUMENTED: `_IREE_DEFAULT_COMPILE_ARGS = ("--iree-input-demote-f64-to-f32=false",)` (always) + `_IREE_DEFAULT_LLVMCPU_ARGS = ("--iree-llvmcpu-target-cpu=generic", "--iree-llvmcpu-link-embedded=false")` (llvm-cpu only — the embedded `-nostdlib -static` link cannot resolve libm symbols (log/cos/floor) that f64 math ops lower to) + `_IREE_DEFAULT_ROCM_ARGS_NAME = "--iree-rocm-target"` (rocm only, see the ROCm section). The `iree_compile_args` option appends ARBITRARY flags AFTER the defaults; a user flag whose NAME (text before `=`) collides with a default DROPS the default (never both). The only rejected flags are the small documented DENY list. Every other flag passes through; the compiler validates the VALUES (etl never parses compiler flags; a bogus value fails loudly with iree's own diagnostics wrapped in `core.BackendError`).
- **Loader/runtime flags (`iree_runtime_args`, load option):** parsed via `iree.runtime`'s `rt.flags.parse_flags` at load time with LOUD errors — the sanctioned way to set HAL/device flags (e.g. `--cuda_async_allocations=false`). etl sets NO process-global runtime flag; iree's own default stands. A flag named in `iree_runtime_args` OR `IREE_PY_RUNTIME_FLAGS` always takes effect (explicit option parsed after env, wins by last-wins).
- **load/run:** CPU (device `None` or `Device("cpu", *)`) via the RELIABLE path `iree.runtime.get_driver("local-task")` + `driver.create_default_device()` + `load_vm_flatbuffer(flat, driver="local-task")` (the `rt.system_setup(config=...)` form intermittently fails with `TypeError: 'module' object is not callable` — submodule shadowing; do NOT reintroduce it). CUDA (`Device("cuda", index)`) via `rt.get_driver("cuda")` (the CUDA HAL driver is COMPILED INTO the runtime wheel — no extra pip dependency) + **`driver.create_device(device_id=index+1)`** — IREE cuda device ids are **1-BASED** (device_id=0 raises `ValueError` "Device id 0 not found", wrapped into `core.BackendError`) + the `rt.Config(device=...)` → `rt.VmModule.copy_buffer(config.vm_instance, vmfb)` → `rt.load_vm_module(vm_module, config)` path (`load_vm_flatbuffer`'s driver-name form always creates the DEFAULT device and CANNOT select a CUDA index). Artifact/device target compatibility is enforced at load — the payload's `target_backends` must include the driver matching the device kind (absent `target_backends` in pre-CUDA artifacts = `["llvm-cpu"]`); a mismatch raises `core.BackendError` naming both.
- **Inputs (EXPLICIT device placement — no implicit host↔device transfers):** an input already ON this executable's device — an `IreeDevicePayload`-backed `core.Tensor` (run outputs of this or another iree executable; `tensor.device` kind+index must equal the executable's device) or a raw iree `DeviceArray` — passes through to the invoke with ZERO host round-trips. ANY other input is rejected: plain cuda runs NEVER stage host inputs. The pipeline run-boundary check (`etl/pipeline.py`) rejects a wrong-device input first with its own `core.DeviceError` (message contains "no implicit device" and `t.to(`); a cuda executable additionally enforces a defensive `core.DeviceError` for direct backend-level `exe.run([...])` calls naming the same remedy — place inputs on the device explicitly first via `t.to(Device('cuda', N))`. The single exception: an llvm-cpu executable accepts host ndarray-backed inputs via `rt.asdevicearray` (host→host ABI representation — the only plain-run host-input path left).
- **Outputs — execution semantics (device-resident, BOTH targets):** outputs are device-resident `core.Tensor`s wrapping the IREE `DeviceArray`s (`IreeDevicePayload`, the public class); `.device` is the run device, and `core.Tensor` wrappers never alias or pin the underlying HAL buffers. Host materialization is LAZY AND EXPLICIT: a CPU-kind output's `.numpy()` materializes a fresh host copy on demand (`DeviceArray.to_host()` — on `local-task` zero-copy for mappable buffers); a NON-cpu output's `.numpy()` raises `core.DeviceError` ("no implicit device", `t.to(`) — read it back via `t.to(core.Device('cpu', 0)).numpy()`. The hot run() path performs no host round-trip either way; same-device inputs pass through with no copy, and the llvm-cpu path is equally device-resident (local-task buffers, lazy `.numpy()`).
- **Capabilities:** `dynamic_shapes=True` (per-op partial — elementwise/dynamic-broadcast symbolic graphs run at multiple concrete sizes, also on cuda/rocm; symbolic reshape/conv/slice/pad are rejected by the exporter at `lower()` with a clear `BackendError`); `external_calls=True` (the ONLY adapter with the capability in v1); `dtypes` = f16/f32/f64/i8/i16/i32/i64/bool (unsigned ints excluded — iree-compile 20241104 legalizes unsigned `reduce` nondeterministically/not at all; complex excluded — the exporter v1 defers complex beyond cast; the same set applies to cuda — fp64 runs exact: fp64 softmax on cuda matched numpy to 6.9e-18); `collectives=False`, `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`, `rng_bit_generator={"threefry2x32"}` (MEASURED, iree 3.11: native `stablehlo.rng_bit_generator` with `THREE_FRY` legalizes and is BIT-EXACT vs numpy on llvm-cpu, cuda and rocm — key-first `[k0,k1,ctr0,ctr1]` state layout — and is ~1.6–2.1× faster than the inline expansion, so native THREE_FRY is the iree DEFAULT path for threefry graphs; `PHILOX` FAILS legalization on all targets — see Known Issues #2 — so philox uses the exporter's bit-exact inline expansion).
- **External kernels — `external_call` dispatch:** graphs with `external_call` ops are SPLIT at `lower()` by the shared `CompilerBackend` (`../compiler.py::_lower_external_segments` + `../external_split.py`) into an ordered list of SEGMENT programs (plain graphs, no external calls inside, each compiled to its own vmfb — payload `stablehlo-segments`, artifact `iree-vmfb-segments`, per-segment `target_backends`/`iree_compile_args`) plus a JSON-safe kernel-call PLAN persisted in the artifact. `IreeExternalExecutable` runs segments strictly in plan order on the HAL device; at each `external_call` boundary the kernel is dispatched through the SAME `etl.register_external_kernel` registry the numpy backend uses (resolved via `etl.external.get_external_kernel_entry(name, "iree")`; unknown name at run → `BackendError` naming the kernel + the registry; outputs validated count/dtype/shape vs the declared specs). TWO modes:
  - **host mode** (default) — operands staged to host numpy arrays (the once-per-executable staging `UserWarning` fires only when a boundary actually stages host↔device), kernel runs on host, results staged back as the next segment's inputs.
  - **device-resident mode** (`device_resident=True` — explicit per-backend slot only) — the kernel receives the boundary's device tensors DIRECTLY (never host-staged) and may return device tensors / duck payloads / raw `DeviceArray`s / numpy arrays / tuple-list mixes; results are validated METADATA-ONLY (never a forced host copy), and the next segment's same-device pass-through consumes device results with ZERO host round-trips (numpy results stage back — boundary marked staged). Kernel authors may isinstance-check the PUBLIC payload class `etl.backends.adapters.iree.IreeDevicePayload` (`.device_array` HAL handle, `.shape`, `.dtype`, `.to_host()`, `.device`) and e.g. run further vmfb modules on the SAME HAL device.
  Carried plain values that are NOT kernel operands stay device-resident across segments. Lower-time restrictions (explicit `BackendError`, MODE-AWARE): no calls inside cond/while/scan bodies, ≥1 tensor operand, single-function graphs, and — HOST-mode boundaries only — STATIC integer result dims; DEVICE-RESIDENT boundaries ALLOW symbolic/runtime-dynamic result dims (e.g. vmap/vectorize batch `Dim`s on a batched-variant kernel — the vmapped kernel receives the FULL batched stack as device tensors, invoked once per run), validated metadata-only at run time with the ACTUAL shapes (the exporter's per-op symbolic-shape support decides what compiles; unsupported segment ops raise explicit `BackendError`). Kernels assumed PURE; segments run sequentially, preserving `callback` effect order. xla/tvm keep `external_calls=False` — at `lower()` they INLINE a registered portable decomposition with a `UserWarning` when one exists, else reject with an explicit `BackendError` naming op+backend (options: iree/numpy host-dispatch, or `etl.register_external_kernel(name, fn).portable(decomp)`). Pinned by `tests/backends/test_external_call_iree.py` (39) + `tests/ops/test_external_call.py` + `tests/backends/test_external_batched_iree.py` (5).
- **Iterative stateful workloads (evox-style DE/PSO steps) — the measured recommended pattern:** keep the state ON the device across steps — build once (`target_backends=["cuda"]`, `opt_level="O3"`), then loop `out = etl.run(exe, key_dev, state_dev)` feeding each step's device-resident outputs back as the next inputs; the seed is placed once via the explicit `seed.to(Device('cuda', N))`. Every later call costs ZERO `rt.asdevicearray` calls and ZERO host round-trips (per-call budget = invoke floor ~0.09 ms + wrapper ~0.05 ms; a 4096×50 f32 fused step measures ~0.146 ms/call min — at/above torch-eager parity). Anti-patterns: feeding fresh host numpy state per step (rejected at the run boundary with `core.DeviceError`) and `.numpy()`-reading the whole state per step (a non-cpu output needs explicit `.to(cpu)`; D2H of 800 KB costs ~0.13–1.4 ms under contention). Non-output host state is placed the same explicit way (one-shot upload, no cache).
- **Explicit placement — `Tensor.to(Device('cuda', N))` → `upload_tensor`:** `core.Tensor.to` dispatches through the device-transfer provider registry: `etl.backends` registers a LAZY `"cuda"` thunk at import time that imports this module and delegates to the module-level `upload_tensor(tensor, device) -> core.Tensor` (attribute lookup at call time; the thunk raises a clean `core.DeviceError` when the adapter lacks the attribute); when the adapter ACTIVATES (`register()`), it registers the DIRECT function under its own per-backend `("cuda", "iree")` slot (order-independent — activation of any backend never clobbers another's provider). Module import of `adapters/iree.py` stays safe without the iree packages (heavy imports live in function bodies). `upload_tensor` contract (v1): the source must be a HOST ndarray-backed `Device("cpu", 0)` tensor — anything else raises `core.DeviceError` suggesting the explicit two-hop `t.to(cpu).to(target)`; it acquires a FRESH iree cuda HAL device through the same `_acquire_runtime_device` path `load` uses — honoring `ETL_IREE_RUNTIME_ARGS` exactly like `load` (`_runtime_args_from_env`) — performs a ONE-SHOT host→device copy through the `_staged_input` tiers with a FRESH per-call staging dict (fresh buffers, no cache; oversized/unmappable inputs fall back to `rt.asdevicearray`), and returns a fresh `core.Tensor(IreeDevicePayload(da, device))` on `Device('cuda', N)`. Failures surface as `core.DeviceError`/`core.BackendError` — never a raw iree exception. **GPU CROSS-INSTANCE OUTCOME (empirical, RTX A6000, index 3):** a tensor placed via `.to(Device('cuda', N))` lives on a FRESH HAL device instance (the provider's own `_acquire_runtime_device`), and feeding it into a SEPARATELY-LOADED cuda executable (its own load-time HAL instance) WORKS — iree accepts same-physical-device buffers across instances, so `_build_buffers`' kind+index device-equality trust is sufficient: `etl.run(exe, xd, xbd)` + `y.to(cpu).numpy()` bit-exact vs numpy. No process-wide cached HAL device exists.
- **Host→device upload machinery (`_staged_input`) — TWO TIERS — serves ONLY host-mode external-kernel boundaries and the placement provider (plain cuda runs never stage):** persistent staging buffers cached per `(input index, shape, dtype)` (no per-call device alloc) for cache-retaining callers (each cuda SEGMENT executable keeps one per segment); `upload_tensor` uses a fresh one-shot dict. Split at `_PINNED_DIRECT_MAX_BYTES = 4 * 1024` (measured crossover ~16–32 KB): **≤ 4 KB** (the DE rank-0 key) a persistent `DEVICE_LOCAL | HOST_VISIBLE` (`DEFAULT | MAPPING`) buffer mapped once + one `np.copyto` per call (no copy/semaphore/wait); **> 4 KB** a persistent `HOST_LOCAL | DEVICE_VISIBLE` (`TRANSFER_SOURCE | MAPPING`) source + a per-call async `queue_copy` into a persistent `DEVICE_LOCAL` staging buffer. **The DMA copy's semaphore wait is LOAD-BEARING** — the cuda HAL does not reliably stream-order `queue_copy` ahead of invoke dispatches (un-fenced copies exposed ~0.4% garbage), so each call waits on a FRESH semaphore (reusing one ABORTS), query-first (`_wait_copy_semaphore`; `HalSemaphore.query()` skips the ~0.02 ms `HalFence.wait()` when done — race-free, no-`query` runtimes fall back). Fallbacks to `rt.asdevicearray`: >16 MB, unmappable dtypes, non-cuda/rocm paths, cache overflow (bounded 64). Each cuda SEGMENT executable keeps a 4 KB DEVICE_LOCAL `_pool_anchor` (classic-pool warmth for opt-in `--cuda_async_allocations=false`); plain `IreeExecutable`s allocate none. Tier measurements/cache entries: skill `etl-compiler-adapter-recipes`.

### ROCm / HIP (`rocm`) — AMD GPU, device-resident (validated on MI300X / gfx942, ROCm 7.1, iree 3.11.0)

Same adapter and the same device-resident machinery as cuda — a third compile target and a third HAL driver:
- **Compile:** `target_backends=["rocm"]`. IREE has no ROCm target auto-detection, so the adapter injects a detected `--iree-rocm-target=<arch>` default (`_detect_rocm_target` reads `amdgpu-arch`/`rocm_agent_enumerator` under `$ROCM_PATH`/`$ROCM_HOME`//opt/rocm; `_rocm_target_default` injects it and a user flag of the same name wins). `--iree-hal-target-device=rocm` is NOT needed. `Artifact.target == "rocm"`; a target/device mismatch is an explicit `BackendError`.
- **Device paths:** `rt.get_driver("hip")` + `create_device(device_id=index+1)` (1-based, like cuda). `Device("rocm", N)` (canonical) and the alias `Device("hip", N)` both resolve (`_normalize_device_kind` folds `hip`→`rocm` for the HAL driver; the `core.Device` label is never rewritten). Device-resident semantics are the cuda ones: payload pass-through, host inputs rejected at the run boundary, `.numpy()` on a rocm output raises `DeviceError`, explicit `t.to(cpu)` readback, explicit `Tensor.to(Device("rocm", N))` placement through the registered rocm provider slot.
- **Fast host→device staging path (rocm-specific):** `_staged_input` selects a per-kind fast path from the NORMALIZED `device_kind` — the cuda two-tier pinned/DMA machinery, or the rocm host-local source + `queue_copy` machinery (both waits LOAD-BEARING); segment executables are built with the normalized kind, so a rocm host-mode external-call boundary stages host↔device through the rocm fast path and warns once. `rt.asdevicearray` remains the fallback for oversized/unmappable inputs and any fast-path failure. rocm placement (`upload_tensor`) reuses ONE THREAD-LOCAL HAL device per `(index, runtime args)` (`_acquire_cached_rocm_device`) and stages through a THREAD-LOCAL reusable `HOST_LOCAL|DEVICE_VISIBLE` (`TRANSFER_SOURCE|MAPPING`) source buffer keyed `(shape, dtype)` (`_rocm_source_buffer`, identity-checked owning device, bounded `_ROCM_SOURCE_CACHE_MAX=16`) — `np.copyto` into the source view, then a per-call `queue_copy` into the destination with a FRESH semaphore + query-first wait (`_rocm_staged_input`). Thread-locality is REQUIRED, not an optimization: HAL devices are thread-affine (Known Issue #12; `etl/io.py::_bootstrap_worker_context` — the `etl.io` worker calls `upload_tensor` for `prefetch`), so a process-global cache would hand the worker a foreign device; cached devices stay referenced for process lifetime. A one-shot `upload_tensor` returns a FRESH destination (the returned tensor owns its buffer); segment executables keep a persistent destination per `(index, shape, dtype)` like the cuda tiers. Measured (MI300X gfx942 / iree-base 3.11.0, best-of-20, warmup-3): `Tensor.to(Device("rocm",0))` ≈ 0.052 ms for 4 KB and ≈ 0.43 ms for 4 MB; a per-call matmul place+run+readback ≈ 0.28 ms; a device-resident run-only ≈ 0.065 ms. `driver.create_device(device_id=1)` costs ~46 ms/call and does not warm up, which is why rocm placement holds a thread-local cached device. CUDA placement uses its own fresh-per-call device and its own pinned/DMA staging tiers; the selection is driven by the NORMALIZED `device_kind`.
- **Validated bit-exact vs numpy on rocm:** `cond` (all probed shapes); sort/argsort (n=64/128 with the default `sort_emission="auto"` — no bufferization failure); splitmix64 uniform/randint; threefry2x32 uniform via the NATIVE `stablehlo.rng_bit_generator` path; philox4x32_10 uniform (inline expansion); host-mode `external_call` dispatch; matmul+tanh (1.8e-6 vs fp64). f32 `random.normal` differs from numpy by ≤4.6e-7 — the documented Box–Muller fast-path budget, as on cuda.
- **Known issue — `while_loop`/`scan` are unreliable on rocm (upstream IREE HIP HAL).** Shapes build and compile fine but abort at run with a RAW `RuntimeError: … hip/event_semaphore.c:786: ABORTED … hal.fence.await` (raised from `entry(*buffers)`, never wrapped in `core.BackendError`); the process then often HANGS at teardown. Deterministic per graph shape (6/6 and 3/3 fresh-process reproductions); the same graphs run correctly on llvm-cpu. Failing shapes: a loop carry initialized from a graph CONSTANT (`enp.zeros` — also why `etl.scan` fails) and a multi-carry loop whose condition reads the float carry where the same loop reading the i64 counter passes. Working (bit-exact): condition on the counter only, every carry input-derived. Mirrors the iree-cuda `while_fib`/`while_cond_combo` fragility.
- **Sugar (`etl/pipeline.py::_resolve_backend_device`, outside this node):** for an iree-family backend with no explicit `target_backends` and no `ETL_TARGET_BACKENDS`, the target is inferred from the resolved device — `cuda`→`["cuda"]`, `rocm`/`hip`→`["rocm"]`, `cpu`→`["llvm-cpu"]` — so `etl.build(fn, specs, backend="iree", device=Device("rocm", 0))` compiles for rocm end-to-end.
- **Test coverage (rocm):** `tests/backends/test_iree_rocm_device_resident.py` (rocm-guarded via `_rocm_guard.py`) pins placement, run-boundary host-input rejection, `.numpy()`-raises semantics, and ZERO `asdevicearray` calls during same-device loops. NOT covered: rocm × `external_call`/segment staging; direct thread-locality of the caches (pinned only indirectly); a real-rocm `upload_tensor` on the `etl.io` worker thread (`prefetch`).

### XLA via the PJRT C API (`xla.py`) — no jaxlib

- **Plugin** (distribution OUT of scope — users provide the binary): resolved in order (a) `plugin_path` (a compile AND load option; the load-stage variant fixes the re-discovery gap), (b) env `ETL_PJRT_PLUGIN`, (c) well-known paths (`/usr/local/lib`, `/usr/lib`, `$HOME/.local/lib`, `./`). None found ⇒ `core.BackendError` with an actionable message (build via `bazel build //xla/pjrt/c:pjrt_c_api_cpu_plugin` from OpenXLA, or any XLA build exporting `GetPjRtApi`). NO pip hint. jaxlib is NEVER imported in this adapter.
- **Device kinds (accelerator support incl. AMD ROCm):** serves `Device("cpu", 0)` (host-staged, the v1 default) and device-resident accelerators `"cuda"`, `"rocm"` (canonical) and `"hip"` (alias) — `_NON_CPU_KINDS = ("cuda", "rocm", "hip")`, kind-agnostic (any non-cpu kind is device-resident; the index is derived for every non-cpu kind). `_check_kind_served(device, platform_name)` (a) rejects a kind outside `_NON_CPU_KINDS` (e.g. `"gpu"`) with a `core.BackendError` containing "supports CPU", and (b) — once the plugin's `platform_info()` is known — rejects a kind the plugin platform does not physically serve when the platform is listed in `_PLATFORM_KINDS` (`"cuda"→("cuda",)`, `"rocm"→("rocm","hip")`, `"hip"→("rocm","hip")`, `"cpu"→()`), so `Device("cuda", N)` against a ROCm plugin (or vice versa) is rejected rather than mislabelled. An UNLISTED platform (e.g. the fake plugin's `"fake"`) is PERMISSIVE.
- **Compile options:** `plugin_path` + `xla_compile_options` = the raw serialized `xla.CompileOptionsProto` bytes, threaded into `PJRT_Client_Compile_Args.compile_options` / `compile_options_size` (NULL/0 when unset). etl does NOT parse/validate the protobuf contents — the plugin does. Non-bytes values raise `core.BackendError` naming the option.
- **compile:** `ctypes.CDLL(path)` → `GetPjRtApi()` (lowercase-t `GetPjrtApi` fallback — the shipped jax plugins export that casing) → **version gate** (`PJRT_Api.version`/`struct_size` vs the bindings' minimum — too old ⇒ explicit `BackendError`) → the process-global shared `PJRT_Client` (`acquire_client`; one per plugin path, created with empty options) → `PJRT_Client_Compile` with `PJRT_Program{code=mlir_text, format="mlir"}` (the plugin accepts MLIR text directly; NO MLIR python bindings anywhere in the adapter) → `PJRT_Executable_Serialize` → bytes → base64 in the artifact payload (alongside `mlir_text` + `entry_functions`).
- **load/run:** deserialize via `PJRT_Executable_DeserializeAndLoad` on the process-global refcounted shared client for the re-discovered plugin (ONE `PJRT_Client` per plugin path — `xla_util.acquire_client`/`release_client`; compile, load and `check_available` all share it, and the loaded executable holds one reference until `close()` — a fresh client per load ABORTed real GPU plugins when the per-client BFC pool exhausted the GPU) — never recompiles. CPU path: inputs staged via `PJRT_Client_BufferFromHostBuffer` (all 14 etl dtypes incl. complex64/128, dense row-major numpy — `np.asarray` + contiguity-forced only for ndim ≥ 1 (NOT `np.ascontiguousarray`, whose hardcoded ndmin=1 promotes 0-d arrays; numpy#5300), `kImmutableUntilTransferCompletes`, transfer event awaited + destroyed, host array kept alive on the buffer); execute via `PJRT_LoadedExecutable_Execute` on the first addressable device; outputs copied via `PJRT_Buffer_ToHostBuffer` → writable numpy → `core.Tensor`. **Device-resident path (`load(..., device=Device("cuda"|"rocm"|"hip", N))`, iree-mirroring):** every input must ALREADY be an `XlaDevicePayload`-backed `core.Tensor` on the executable's device (host inputs raise `core.DeviceError` at the run boundary — never staged); payload buffers are handed to `PJRT_LoadedExecutable_Execute` DIRECTLY (zero `BufferFromHostBuffer`/`ToHostBuffer`), and outputs STAY on the device as `XlaDevicePayload` tensors (public class, like `IreeDevicePayload`; non-cpu `.numpy()` raises the standard `DeviceError`, explicit `t.to(cpu).numpy()` round-trips). **Same-device loop** (the evox StdWorkflow pattern): place the seed once via `t.to(Device("cuda"|"rocm"|"hip", N))` — the module-level `upload_tensor` placement provider (one-shot `BufferFromHostBuffer` on the shared client; registered by `register()` in the per-backend `(kind, "xla")` slot for each of `_NON_CPU_KINDS`) — then feed each step's outputs back as the next inputs: the per-call staging/copy-back fixed cost (~0.75–0.8 ms) is paid exactly ONCE.
- **Per-call hot path (device-resident runs — the low-overhead loop design):** a `run()` on an accelerator executable re-derives NOTHING that is static for a loaded executable. `XlaExecutable` builds ONE `_XlaRunPlan` (`_build_run_plan`: input/output arity, per-leaf `(dtype, shape)` validation contracts from the signature, output metadata from the artifact's recorded static output shapes) and validates through it in one tight loop with the historical exception types/messages/order; the CPU host-staging branch is unchanged. In the driver, `xla_util._LoadedExecutable` caches `num_outputs` (one FFI per executable) and reuses per-thread ctypes scaffolding — input buffer-pointer array, output pointer array, `PJRT_ExecuteOptions`, `PJRT_LoadedExecutable_Execute_Args` — keyed `(executable ptr, num_args, num_outputs)` in `threading.local` (bounded by `_EXECUTE_SCAFFOLDING_MAX`; thread-local, not a shared cache, so concurrent runs of one executable from different threads stay safe), so a call writes only the input pointers and the execute device before the FFI. Output buffers are created with the recorded static metadata PREFILLED (`execute(output_meta=...)` → `_Buffer(shape=..., dtype=...)`) instead of two plugin metadata FFIs per output (`PJRT_Buffer_Dimensions` + `PJRT_Buffer_ElementType`, ~3.4 us). Prefilled metadata is never trusted blindly: `_Buffer._verify_metadata()` runs the real queries and raises a loud `core.BackendError` on declared-vs-actual mismatch; the executable verifies every output on its FIRST device-resident run (then the static contract is trusted — XLA executable output types are static), and `_Buffer.to_host()` re-verifies on every explicit host read-back. A run's whole output set shares ONE reference on the process-global client and ONE `weakref.finalize` (`_XlaDeviceRunGroup` → `xla_util.release_payloads`) rather than a refcount acquire + finalizer per output; `release_payload` stays the single-buffer wrapper for `upload_tensor`/external payloads and the public 4-arg `XlaDevicePayload` constructor keeps its own reference/finalizer. Measured on the MI300X VF / ROCm 7.1 host (interleaved A/B of the pre-change tree vs this one, medians of 60 calls after 20 warmup; shared GPU, so absolute values are inflated): 2-in/2-out `(1024,50)` f32 graph 66–70 us → 40–46 us; 8-in/8-out evox-step-shaped graph (five `(1000,50)`/`(1000,)` f32 + `(50,)` f32 + rank-0 i64 + rank-0 i32) 133–143 us → 80–87 us (≈ −31%…−44%). The residual is dominated by the plugin's own `PJRT_LoadedExecutable_Execute` FFI (~32 us for 2 buffers, ~59 us for 8) plus GPU dispatch — not adapter overhead. Caller-side monitor reads are separate: `.to(cpu)` of a `(1000,50)` f32 output costs ~120 us (rank-0 ~100 us), and the pipeline's `run`/pytree validation above the adapter adds its own fixed cost.
- **Error contract (binding):** every PJRT call returns `PJRT_Error*` (NULL = success); the driver checks EVERY call, extracts `PJRT_Error_Message` text, destroys the error, and raises `core.BackendError` naming the failing step. All handles destroyed via matching entry points (try/finally + `close()` helpers; the loaded-executable's inner unloaded twin from `PJRT_LoadedExecutable_GetExecutable` is destroyed first).
- **Capabilities:** `dynamic_shapes=False` (compile-time static-shape gate via `_resolve_static_shape`/`_StaticShapeError`; the gate decision is recorded in the artifact (`static_input_shapes`/`static_output_shapes`) and enforced exactly at `run()`); `dtypes` = all 14 etl dtypes; `collectives=False` (conservative — re-probe before flipping); `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`; `rng_bit_generator=frozenset()` (native `stablehlo.rng_bit_generator` is not declared — the real-plugin validation shows XLA's spec-strict u64-state importer rejects etl's u32-word key-first state at compile, and XLA's THREE_FRY=threefry2x64 / PHILOX=2-word philox4x32-10 are different ciphers than etl's threefry2x32 / 4-word philox4x32_10 — native bit-exactness impossible by design; the exporter's bit-exact inline expansions are the xla default, and the per-call `rng_bit_generator` lower option still forces the native path).
- **`check_available()`:** bindings integrity + plugin discovery + `GetPjRtApi` + version gate + live client create/destroy round-trip. Artifact `runtime_dependencies` records numpy + the `pjrt_c_api` header commit (bindings provenance) + plugin platform/version string — no jaxlib.

### TVM (`tvm.py`) — jax-free, jaxlib MLIR bindings only

- **translate:** `tvm.relax.frontend.stablehlo.from_stablehlo(mlir_text)` (exists in 0.26; `tvm.relax.frontend.from_mlir` does NOT; build lives in `tvm.relax.vm_build`, re-exported as `tvm.relax.build`). The vendored translator parses MLIR with jaxlib's bundled bindings — hence tvm needs **jaxlib** (NOT the `jax` package) at adapter runtime.
- **MLIR binding seam (`_mlir_bindings.py`):** ALL MLIR-binding access (context creation, `ir.Module.parse`, the `ir` re-export) routes through this one module; jaxlib is required ONLY for its bundled LLVM MLIR python bindings and a future standalone `mlir`/`stablehlo` PyPI package can replace jaxlib with a one-module swap.
- **jax shim (`tvm_util._install_jax_shim`):** the vendored translator imports `from jaxlib import mlir` (12 sites) and `from jaxlib.mlir.dialects import stablehlo` (2 sites) — those work as-is — plus `from jax._src.interpreters import mlir as jax_mlir` (1 site, inside `from_stablehlo()`). That one import is satisfied by injected `sys.modules` shims for `jax`, `jax._src`, `jax._src.interpreters`, `jax._src.interpreters.mlir` (the mlir shim provides `make_ir_context()` delegating to `_mlir_bindings.make_ir_context` and re-exports `jaxlib.mlir` as `ir`). Injection happens at the top of BOTH `check_available()` and `ensure_compat()` — before any `tvm.relax.frontend.stablehlo` import. Idempotent; a real jax already imported in-process is left in place; `sys.modules["jax"] = None` is overwritten by the shim. Verified end-to-end with real jax blocked.
- **build/run:** `tvm.relax.vm_build.build(mod, target=tvm.target.Target("llvm"))` → `VMExecutable`; run via `tvm.runtime.vm.VirtualMachine(ex, tvm.runtime.cpu())["main"](...)`; inputs `tvm.runtime.tensor(np_array, tvm.runtime.cpu())` (the `tvm.nd` namespace does not exist in TVM 0.26); outputs `tvm.runtime.Tensor.numpy()` → `core.Tensor`.
- **persist:** `VMExecutable.export_library(path)` → host .so, base64'd into the payload (`format="tvm-vm-library"`); load decodes to a temp file and `tvm.runtime.load_module(path)` — no recompile at load. `Module.save_to_file` does not exist in 0.26.
- **Compatibility shim (REQUIRED):** the TVM 0.26.0 vendored StableHLO translator targets the OLD jax mlir python bindings; `tvm_util.ensure_compat()` patches five gaps (type-check classmethods, OpView/Operation key normalization, `broadcast_to` ShapeExpr, `DenseI64ArrayAttr` decoding, float16 np.asarray constant decoding) — each restores exactly the semantics the vendored code assumed, no computation changes.
- **Op coverage gate:** `SUPPORTED_STABLEHLO_OPS` whitelist checked at compile (`core.BackendError` naming the op otherwise): arithmetic, unary math, compare, select, bitwise/logical, convert, broadcast_in_dim, reshape, transpose, concatenate, slice (unit strides), pad (zero interior), reduce (add/max/min/mul), dot_general (matmul), constant. Rejected: control flow (`stablehlo.if`/`while`), gather/scatter, remainder, conv/reduce_window (vendored handlers hardcode NHWC/HWIO — silently wrong for etl's NCHW conv), multi-function modules, multi-output functions.
- **Capabilities:** `dynamic_shapes=True` (per-op partial — elementwise symbolic graphs validated at multiple sizes, constant-free graphs; the exporter rejects symbolic reshape/conv/slice/pad at `lower()`); `dtypes` = f16/f32/f64/i8/i16/i32/i64/u8/u16/u32/u64/bool (complex excluded — vendored translator raises); `collectives=False`, `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`, `rng_bit_generator=frozenset()` (the TVM StableHLO frontend has no rng_bit_generator support — the exporter's bit-exact inline Threefry2x32/Philox4x32-10 expansions are used).
- **ROCm:** TVM is COMPILE-ONLY on ROCm — the `apache-tvm` 0.26.0 wheel is built `USE_ROCM=OFF`, so `tvm.runtime.device("rocm", 0).exist` is `False`; do not include TVM in ROCm run matrices (a ROCm run needs a `USE_ROCM=ON` TVM build).

## Constraints (binding)

- **Heavy-import rule:** `iree`/`jaxlib`/`tvm` imports live ONLY inside function bodies; top-level imports limited to stdlib, `etl.core`, and the `..compiler`/`..program`/`..registry` siblings (plus this package's `_pjrt_c_api.py`/`_mlir_bindings.py` for the xla/tvm adapters). Verified: `import etl` leaves `sys.modules` free of iree/jax/jaxlib/tvm.
- **No `jax`:** `import jax` / `from jax` is forbidden anywhere in `etl/` (grep-proof; the TVM shim satisfies the vendored translator's `jax._src` import). `jaxlib` may appear ONLY inside function bodies, ideally only via `_mlir_bindings.py`, and NEVER in the xla adapter (`_pjrt_c_api.py`/`xla_util.py`/`xla.py` are jaxlib-free).
- **Errors:** capability violations and compiler/translator failures raise `core.BackendError` naming the op/feature — never silent fallback to numpy or partial semantics; load-time mismatches raise `core.PersistenceError`; dtype mismatches `core.DTypeError`, shape mismatches `core.ShapeError` (mirrors the numpy interpreter).
- **Staging never composes:** `load` never re-traces/lowers/compiles; device handles are never serialized.
- **CPU only for the numpy/tvm paths;** the iree AND xla adapters also accept `core.Device("cuda"|"rocm"|"hip", index)` (xla runs device-resident: payload inputs/outputs, no host staging, real-GPU validation via user-provided plugins on both CUDA and ROCm/HIP); a device kind the adapter does not support — or a kind the resolved plugin's platform does not physically serve — raises `core.BackendError`; non-`Device` objects `core.DeviceError`.

## Design decisions

- **IREE cuda allocator flag — etl sets NO process-global `--cuda_async_allocations` value; iree's own default (`true`, stream-ordered allocations) stands.** Forcing `false` measured ~2–3× slower per step on the fused DE/PSO step graphs (iree 3.11.0 / RTX A6000: 4096×50 ~2.2–3.5 ms/step vs ~1.16 ms/step; async-ON won or tied every other measured cell). Users who need the classic allocator pool can opt in per load via `iree_runtime_args=["--cuda_async_allocations=false"]` or `IREE_PY_RUNTIME_FLAGS`; `upload_tensor` honors the same `ETL_IREE_RUNTIME_ARGS`. The `_pool_anchor` (classic-pool warmth) is retained ONLY on cuda SEGMENT executables (the one plain-cuda path that still stages host tensors); plain `IreeExecutable`s allocate none. Policy point: `_configure_cuda_runtime_flags` in iree.py (deliberate no-op).

## Known Issues

1. **Writer/export gaps surfaced by adapters (sibling-node `stablehlo/` — out of this node's scope):** (a) dynamic-shape support is per-op partial, exporter-gated: elementwise symbolic graphs (incl. scalar-constant broadcasts) compile+run on iree/tvm at multiple sizes, but symbolic `reshape`/`conv`/`slice`/`pad` (slice/pad: iree parses but the runtime aborts) and unemittable `dot` batch merges raise an explicit `core.BackendError` at `lower()` naming the op, shape, and offending dims; (b) mixed-dtype binary ops with Python scalar constants can produce a dtype mismatch parse error (workaround: explicit `etl.cast`); (c) `stablehlo.add` on i1 is XOR vs numpy bool+ = OR.
2. **IREE rng_bit_generator (empirical, iree 3.11):** the modern two-result syntax is REQUIRED (`%state_out, %out = stablehlo.rng_bit_generator %state, algorithm = THREE_FRY : (tensor<4xui32>) -> (tensor<4xui32>, tensor<2xui32>)` — no shape operand, enum WITHOUT the `RNG_ALG_` prefix); the older shape-operand form is REJECTED. `THREE_FRY` legalizes and runs BIT-EXACT vs numpy with the key-first state layout `[k0',k1',ctr0,ctr1]` (verified across 5 keys incl. (0,0) and (0xFFFFFFFF,0xFFFFFFFF), odd element counts via truncated flat `tensor<5xui32>` — on llvm-cpu, cuda and rocm). `PHILOX` FAILS legalization (`failed to legalize operation 'stablehlo.rng_bit_generator' … explicitly marked illegal`; philox 6-word state) on BOTH llvm-cpu and cuda — hence the capability `{"threefry2x32"}` with philox on the bit-exact inline expansion. Also: **iree (all targets)** — `collective_broadcast` cannot be legalized by iree-compile 20241104 llvm-cpu (upstream) so collectives are off; u32/u64 excluded (nondeterministic unsigned `reduce` legalization); cosmetic generic-CPU-target warnings. `random_permutation` graphs on iree-cuda fail deterministically with the 2-operand-sort bufferization bug (Known Issue 8g) — cuda RNG benchmarks must exclude permutation.
3. **XLA:** no pip-installable PJRT plugin exists — the adapter requires a user-provided `.so` exporting `GetPjRtApi` (discovery: `plugin_path` → `ETL_PJRT_PLUGIN` → well-known paths); distribution is out of scope. Validated against a throwaway fake plugin (hard ABI check: `sizeof(PJRT_Api)` == ctypes 1144 + field offsets; compile/execute/copy/serialize round-trip; error propagation; version gate; missing-plugin message) AND the real `jax_cuda12_pjrt` 0.10.2 CUDA + `jax-rocm7-pjrt` 0.11.2 ROCm plugins (`platform_name="rocm"`) — GPU probe `bench_logs/probe_xla_gpu_validation.py` passes **26/26** (rank-0 staging; PSO/DE/OpenES-shaped fused steps bit-exact except documented fp32 budgets; threefry2x32 + philox4x32_10 RNG bit-exact via the INLINE expansions; non-dominate-rank while_loop bit-exact); xla test files pass 22 + 61 with the plugin. Load-bearing real-plugin fixes: the `GetPjRtApi`→`GetPjrtApi` casing fallback (`_pjrt_c_api.load_plugin_library`); the serialized default `CompileOptionsProto` (`bytes.fromhex("1a0420012801")` = num_replicas=1/num_partitions=1 — a NULL `compile_options` CHECK-crashes the plugin); a process-global refcounted shared `PJRT_Client` (a fresh client per load ABORTs real GPU plugins on GPU exhaustion; pinned in `test_pjrt_ctypes_plugin.py`); a ptxas-PATH hint on compile failures. **Residual limits:** the artifact stays device-agnostic (`target="cpu"`, device chosen at `load()`); native `rng_bit_generator` OFF (the plugin's spec-strict u64-state importer rejects etl's u32-word key-first state and XLA's ciphers differ — impossible by design; the per-call option still forces it); CPU staging naive, device-resident path implemented (payload pass-through + `upload_tensor` placement; pinned by `tests/backends/test_xla_device_resident.py`, 9 tests; per-call hot-path design + medians in the XLA section above). **ROCm plugin + HIP-graph command buffers (host fact):** on this MI300X VF / ROCm 7.1 host the rocm plugin SIGSEGVs inside `PJRT_Executable_Execute` for XLA-capture-eligible graphs under the default command-buffer kinds (it bites the evox SO step graphs); the working recipe is `XLA_FLAGS=--xla_gpu_enable_command_buffer=` (empty kind list ⇒ HIP graphs disabled) alongside `ETL_PJRT_PLUGIN=…/jax_plugins/xla_rocm7/xla_rocm_plugin.so` (plus `HIP_VISIBLE_DEVICES` on a shared multi-GPU box). The failure is shape/dispatch-count specific, not universal — small 2–8-buffer micro-graphs run with OR without the flag at the same cost (43.1 / 91.2 us without vs 40.4–45.7 / 79.5–86.8 us with: run-to-run noise). The adapter deliberately does NOT rewrite `XLA_FLAGS` (no hidden env mutation): the flag is a documented, caller-supplied recipe that tests, probes and benchmarks export themselves. **Env recipes** (CUDA `LD_PRELOAD` cuDNN + `XLA_FLAGS` libdevice; ROCm plugin path; exit-abort `os._exit(0)`), real-GPU device-resident loop numbers (~0.36 ms/call vs 4.18–10.14 ms host staging), the evox `etl_backend_spec` gotcha (`("xla", None)` → fix to `("xla", "cuda:0")`), and the exit-time abort defect (any PJRT-client process ABORTS at interpreter exit after all work succeeds — `PJRT_Client_Destroy` does not help) are in the skill `etl-compiler-adapter-recipes`. Header-driven deviations: `PJRT_Program.format` is `"mlir"` (not "stablehlo"); deserialize is `PJRT_Executable_DeserializeAndLoad`.

Residual: while loops hitting the T2 broadcast-shape class or non-zero vector-constant inits remain broken on iree (both targets) — use the unrolled fixed-point or the xla route. (g) **cuda 2-operand-sort bufferization bug (deterministic, iree 3.11):** `error: failed to bufferize op` for the argsort emission (`stablehlo.sort` of value + i64 iota) whenever the SORTED AXIS SIZE ≥ 32 (measured 32/48/64/96/128 fail, ≤24 pass; 1-operand `sort` unaffected; llvm-cpu unaffected) — avoided at the exporter level via the `sort_emission="count"` composition (iree default `"auto"` = count iff sorted extent ≥ 32): bit-exact on cuda at axis ≥ 32 with no `stablehlo.sort` in the MLIR. (h) **constant-in-while hoisting bug (deterministic, both targets):** `'util.global.load' op undefined global: @__hoisted_*` when a CONSTANT tensor is used inside a while body (hit by cast/scatter-in-body variants of the rank loop).

10. **IREE version matrix for while-loop graphs (upstream; validated on the evox NSGA2/MOEAD tell graphs; full detail in the skill `etl-compiler-adapter-recipes`):** `iree-base-compiler` **3.10.0 and 3.11.0 SIGSEGV** (exit -11) in `IREE::Stream::AffinityAnalysis::run()` (unbounded recursion) on `stablehlo.while` with ≥3 loop-carried values + `select` in the body (SO graphs compile fine); no etl control dodges it.
    - **The crash is NONDETERMINISTIC — a per-run lottery, not a per-graph verdict** (measured on 3.11.0rc20260316, llvm-cpu AND rocm, identical input MLIR): the same `.mlir` file crashes ~85–100 % of runs and compiles ~0–15 % (observed ok-rates 3/20, 1/6, 1/8, 0/20 across batches; single runs can flip either way). Success thus cannot be claimed from one run — any while-graph probe or test must repeat or be treated as flaky.

12. **CUDA HAL devices are thread-affine: any allocating HAL op from a thread with no prior CUDA activity fails `CUDA_ERROR_INVALID_CONTEXT`** (spike-verified, iree-base-runtime 3.11.0; `to_host()`, `asdevicearray`, invoke output-alloc — even when the HAL device was created by another thread; thread-local). One-time per-thread mitigation: the thread first creates its own unused cuda HAL device on the same GPU (`rt.get_driver("cuda").create_device(device_id=idx+1)`), making the shared primary context current; context-current state is per-thread and no iree-python API sets it directly. llvm-cpu (local-task) has no such constraint. Implication: cuda FIFO-worker copies (the `etl.io` worker runs `upload_tensor` for `prefetch`) need this one-time bootstrap per worker thread — see `etl/io.py::_bootstrap_worker_context`. Detail: skill `etl-compiler-adapter-recipes`.

13. **IREE GPU lowering of rank-0-result reductions is a single sequential workgroup — the dominant cost of monitor-style graphs, and NOT fixable with compiler flags.** Measured on MI300X/gfx942, iree 3.11, 10000×100 evox SO-shaped step `@etl.defn`: a `concatenate(prev_best (1,), fitness (10000,)) → (10001,)` + `iota` + **`etl.argmin`** (2-operand reduce, LT/EQ tie-break comparator) + **`etl.min`** (1-operand reduce) + one `i1` reduce (NaN guard) are each lowered by `LLVMGPUBaseLowering` with `workgroup_size = [1,1,1]`, `linalg.fill`, `lowering_config tile_sizes = [[]]` — ONE workgroup, ONE thread, sequential loop — while every data-parallel sibling dispatch gets `LLVMGPUTileAndFuse workgroup_size = [64,1,1]` (`workgroup=[64]`, `thread=[1]`). `rocprofv3 --kernel-trace` per-call cost on the real evox DE step (18 dispatches / 16 executables): argmin-reduce **890.7 µs**, min-reduce **692.4 µs**, i1-reduce **182.2 µs** = **1765 of 1858 µs (95%)**; ALL 10000×100 data-parallel work (elementwise + gather + reduce-over-dim1) is ~61 µs. Cost is independent of pop×dim ⇒ invisible at 1000×50 (inside the ~0.13 ms launch floor) and dominant at 10000×100 — the exact crossover users see. Subgraph attribution at 10000×100 (same etl graph, device-resident loop): iree-rocm vs xla-rocm = `argmin_1d` 0.9386 vs 0.0618 (**15.2×**), `reduce_min_1d` 0.7608 vs 0.0597 (**12.7×**), full RNG+eval+select step WITHOUT the monitor reductions 0.1518 vs 0.1128 (1.35×), RNG-only 1M uniform 0.0769 vs 0.0642 (1.20×) ⇒ the RNG and the data-parallel math are at parity; the whole gap is the three scalar reductions. **Structural fix (ETL side, ~8–10× on the affected ops):** split the reduction axis so the reduction is not rank-0 in one step — `reshape (n,) → (R,C)` then `reduce dim1 → (R,)` then `reduce → scalar`. Measured at etl level: `redmin_1d` 0.7608 → `redmin_2stage` (exact factor 73×137) **0.0957** and generic pad-to-`64×157` **0.1067**; `argmin_1d` 0.9386 → `argmin_2stage` (row min → row argmin → gather row → combine index) **0.1162**. A *keepdims* reshape to `(n,1)` does NOT help (0.744 ms) — the split must yield ≥2 non-unit factors. The same 2-stage rewrite also helps llvm-cpu (`reduce_min_1d` 0.771 → 0.085), so it is target-agnostic and never a regression; it is a **numerically exact** rewrite (min/argmin are associative with the emitter's first-occurrence tie-break, and padding with +inf/`n` never wins) — safe to make the default. Landing site: the StableHLO emitters for `argmin`/`argmax`/`reduce_min`/`reduce_max`/`reduce_*` with a rank-0 result over a large static dim (`../stablehlo/`, sibling node — escalate), exposed as an exporter option plumbed through `CompilerBackend._exporter_options`; it is NOT an adapter-default flag question. **No compiler flag substitutes:** swept at both the isolated-reduce MLIR level and the real step graph level — `opt_level=O3` (1.818 vs 1.767), `--iree-codegen-llvmgpu-use-reduction-vector-distribution` + `-use-vector-distribution` (1.772), `--iree-dispatch-creation-split-argmax-threshold=0` + `-split-argmax-tile-size=1024` (1.772), `--iree-codegen-enable-default-tuning-specs=false` + `--iree-rocm-waves-per-eu=4` (1.762), `--iree-codegen-llvmgpu-vectorize-pipeline`, `--iree-dispatch-creation-enable-split-reduction`, `--iree-llvmgpu-set-workgroup-distribution-along=x` — all within ±2% of the 0.744 ms isolated reduce. The adapter's rocm default flag set is already minimal and cost-free (no debug-info / `--iree-hal-executable-debug-level` / truncate-floats flags) — there is nothing to remove. **RNG is not implicated:** on rocm the inline SplitMix64 i64 expansion (`random_uniform` 1M f32, 0.0769 ms) is 1.9× FASTER than the native `stablehlo.rng_bit_generator` THREE_FRY path (0.1433 ms) — i64 emulation is not a bottleneck (the cuda-era "threefry wins at small sizes" does not carry over to rocm bulk draws). **Diagnostic recipe:** `--iree-scheduling-dump-statistics-file=- --iree-scheduling-dump-statistics-format=json` (dispatch/executable/copy counts), `--iree-hal-dump-executable-configurations-to=-` (per-dispatch `workgroup_size` + `lowering_config` — the smoking gun), `iree-benchmark-module --device=hip ... --benchmark_repetitions=20` (module-only time; rank-0 scalars pass as `--input=i64=1`), `rocprofv3 --kernel-trace -f csv -o <out>` (per-kernel µs). Host-side per-step overhead is small: the real evox DE 10000×100 loop measures 2.30 ms/step with `full_fit_history` on and 2.15 ms with it off (the ~0.15 ms delta is the per-step `to(cpu).numpy()` sync), vs 1.94 ms for the bare module ⇒ ~0.2–0.4 ms wrapper/invoke.
14. **Small-scale results are launch-overhead-bound, so iree and xla look equal there.** At 1000×50 the same evox DE step measures 0.644 (iree-rocm) vs 0.658 (xla-rocm) ms — both inside the ~0.13 ms invoke floor plus wrapper cost — which is why the cross-backend gap only appears once the population is large enough for the scalar-reduction cost (constant per step) to dominate.

## Dependency surface (verified at runtime: jaxlib 0.10.2 / apache-tvm 0.26.0)

- **xla adapter:** ZERO pip dependencies. A user-provided PJRT plugin `.so` (exporting `GetPjRtApi`) is required at compile/load time, discovered via `options["plugin_path"]` → `ETL_PJRT_PLUGIN` → well-known paths. Bindings provenance (header URL + commit) is recorded in `_pjrt_c_api.py` and in the artifact `runtime_dependencies`.
- **tvm adapter:** `apache-tvm` + `jaxlib` (MLIR bindings only). The `jax` package is never imported anywhere in `etl/`; the vendored translator's `jax._src.interpreters.mlir` import resolves to the `_mlir_bindings`-backed shim. `check_available()` probes `jaxlib.mlir` + `jaxlib.mlir.ir` (pip hint `pip install etl[tvm]`).
- **`iree.py` is a legitimately long file (~2200+ lines) — do not split without a plan:** one module holds the whole iree adapter surface (options/defaults, `IreeBackend`, `IreeExecutable`, the shared buffer-building/staging machinery `_build_buffers`/`_staged_input`/`_wait_copy_semaphore`, `_IreeSegmentExecutable`, `IreeExternalExecutable`, the public `IreeDevicePayload`, the placement provider `upload_tensor`, and `register()`); its pieces share tight coupling (staging caches, payload wrapping, core.Device ↔ HAL device mapping), so splitting would spread one adapter's invariants across files for no delegation benefit.
- **`xla.py` (~1200 lines) and `xla_util.py` (~1350 lines) are likewise kept whole by design:** `xla.py` is the backend/executable surface (options tables, static-shape gate + recorded-shape enforcement, `_XlaRunPlan`, `_XlaDeviceRunGroup`, device-kind serving checks, `upload_tensor`, `register()`), `xla_util.py` the PJRT C API driver (plugin loading/version gate, client/compile/execute/buffer/serialize plumbing, the execute-scaffolding cache, payload metadata verification, the shared-client refcount). Both are cohesive and must not be split for size alone.
