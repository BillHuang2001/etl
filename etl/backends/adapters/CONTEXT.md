# etl/backends/adapters — optional compiler adapters (IREE, XLA via PJRT, TVM)

## Intent

Pluggable compiler backends for etl. Each adapter consumes the SHARED StableHLO lowering produced by `CompilerBackend.lower` (`../compiler.py` — verify, capability pre-check, block-portable inlining, StableHLO export, Signature recording) and implements only the compiler-specific half: optional dependency probe (`check_available` override — the shared base is a concrete no-op), `compile` (invoke the external compiler on the MLIR text), `load` (rebuild the executable from the artifact — never re-compiling). Activation is register-on-first-use: `etl.backends.registry.get(name)` imports the adapter module via `registry.OPTIONAL_ADAPTERS` and calls its `register()`; `import etl` never imports an adapter or its compiler dependency.

**Dependency posture (binding):** etl depends directly on the ML compilers — the `jax` frontend package appears NOWHERE in `etl/`, and the xla adapter uses no jaxlib either:
- **xla** = the PJRT C API via pure-stdlib ctypes against a USER-PROVIDED plugin binary (`.so` exporting `GetPjRtApi`) — there is no pip-installable package (verified: no standalone xla/pjrt/jax-cpu/stablehlo/mlir packages on PyPI; no `pjrt_c_api_cpu_plugin.so` in any jaxlib wheel (0.4.38, 0.10.2 checked — the CPU client is embedded in `_xla.so`); jaxlib's `_xla.so` does not export `GetPjRtApi`). Plugin distribution is explicitly OUT of scope.
- **tvm** = apache-tvm + jaxlib, where jaxlib is used ONLY for its bundled LLVM MLIR python bindings (a verbatim upstream-bindings bundle — the same bindings any MLIR tooling uses, NOT the jax API), behind the `_mlir_bindings` seam. The vendored TVM translator's `jax._src.interpreters.mlir` import is satisfied by an injected shim; the `jax` package is never imported.

Status: all three adapters implemented and validated. iree against the installed iree distributions (3.11.0 `iree-base-*` and legacy 20241104.1068) — **including end-to-end CUDA GPU support** (compile option `target_backends=["cuda"]` + `load(device=core.Device("cuda", index))`, validated on 8x NVIDIA RTX A6000, see the IREE section); xla against a THROWAWAY fake PJRT plugin (ctypes layout/offsets, dispatch, error handling, lifecycle, serialize round-trip) AND against the REAL `jax_cuda12_pjrt` 0.4.38 `xla_cuda_plugin.so` (CUDA, 8x RTX A6000) — but ONLY with the two real-plugin adapter fixes that are NOT yet in this repo (GetPjrtApi casing fallback + serialized CompileOptionsProto; see Known Issues #3 — validated in the `tmp_pjrt_probe/etl_763a415` checkout, NSGA2 tell-family graphs: compile+run+bit-exact rank); tvm against apache-tvm 0.26.0 + jaxlib 0.10.2 (numpy parity incl. dynamic shapes, jax-package-free verified with `sys.modules["jax"] = None`).

## API Surface

Each adapter module (`iree.py`, `xla.py`, `tvm.py`) exposes the same shape:
- `<Name>Backend` (a `CompilerBackend` subclass; names `"iree"`, `"xla"`, `"tvm"`), `<Name>Executable` (a `CompilerExecutable` subclass), singleton `<name>_backend`, module-level `register()` (probes the dependency — `core.BackendError` with an actionable message when missing — then registers idempotently).
- `<name>_util.py` helpers: `xla_util.py` (PJRT C API driver: plugin discovery/loading, version gate, client/compile/execute/buffer/serialize plumbing), `tvm_util.py` (vendored-translator compat shim + jax `sys.modules` shim injection, op whitelist gate, translate/build/run/persist helpers).
- `_pjrt_c_api.py`: vendored ctypes translation of the Apache-2.0 PJRT C API header (header URL + commit recorded; ABI/offsets verified against a plugin compiled from the real header); `_mlir_bindings.py`: the MLIR binding-provider seam (jaxlib → standalone swap).
- `__init__.py`: documentation only, imports nothing heavy.

## Adapter designs (validated end-to-end, numpy-backend parity)

### IREE (`iree.py`) — CPU (llvm-cpu) AND CUDA GPU

- compile: `iree.compiler.compile_str(mlir_text, target_backends=..., input_type="stablehlo", extra_args=resolved_args)` → VM flatbuffer, base64'd into the payload (`format="iree-vmfb"`, keeps `mlir_text` + `entry_functions` + `target_backends`). The compile targets come from the `target_backends` **compile option** (`etl.compile(lowered, backend="iree", target_backends=["cuda"])`), default `["llvm-cpu"]` — the default path is byte-identical to pre-CUDA behavior. v1 supported set `{"llvm-cpu", "cuda"}`; a non-list/tuple, an empty list, or an unknown target raises `core.BackendError` naming the offender — never silent fallback. `CompiledArtifact.target` = `"cpu"` for `["llvm-cpu"]`, `"cuda"` for `["cuda"]`, `"+"`-joined for mixed lists. Compiler diagnostics re-raised as `core.BackendError` (never silent). No arch flag is needed for the A6000s: the default codegen target is sm_60 PTX (`+ptx76`), JIT'd by the CUDA driver to sm_86 at load.
  - **Compile flags are user-overridable (`iree_compile_args`)** — the adapter's fixed flags are minimal and DOCUMENTED: `_IREE_DEFAULT_COMPILE_ARGS = ("--iree-input-demote-f64-to-f32=false",)` (always) + `_IREE_DEFAULT_LLVMCPU_ARGS = ("--iree-llvmcpu-target-cpu=generic", "--iree-llvmcpu-link-embedded=false")` (llvm-cpu only — the default embedded `-nostdlib -static` link cannot resolve libm symbols (log/cos/floor) that f64 math ops lower to; the dynamically-linked dylib resolves them from system libc/libm at load). The `iree_compile_args` compile option (list/tuple of flag strings, validated) appends ARBITRARY iree-compile flags AFTER the defaults; a user flag whose NAME (text before `=`) collides with a default DROPS the default (never both — the round-4 `--cuda_async_allocations` lesson: etl must never force flags users cannot override). The only rejected flags are the small documented DENY list `_IREE_DENIED_COMPILE_FLAGS` with actionable reasons: `--iree-hal-target-backends` (use the `target_backends` compile option — the adapter must know the target for artifact/device validation), `--iree-input-type` (etl always feeds StableHLO), `--iree-vm-bytecode-module-output-format` (the adapter requires the default VM flatbuffer output). Every other flag — any name, any value — passes through to iree-compile; the compiler validates the VALUES (etl never parses compiler flags; a bogus value fails loudly with iree's own diagnostics wrapped in `core.BackendError`).
  - **Loader/runtime flags (`iree_runtime_args`, load option):** parsed via `iree.runtime`'s `rt.flags.parse_flags` at load time with LOUD errors (a parse failure raises `core.BackendError` wrapping the parser message — never silent). This is the sanctioned way to set HAL/device flags (e.g. the classic-allocator opt-in `--cuda_async_allocations=false`). etl itself sets NO process-global runtime flag — iree's own defaults stand (cuda: `--cuda_async_allocations=true`, the stream-ordered allocator — measured the fast state on iree 3.11.0, see the design-decision note below). A user flag named in `iree_runtime_args` OR in `IREE_PY_RUNTIME_FLAGS` always takes effect (the explicit option is parsed after the env and wins by last-wins semantics).
- load/run: CPU (device `None` or `Device("cpu", *)`) via the RELIABLE path `iree.runtime.get_driver("local-task")` + `driver.create_default_device()` + `load_vm_flatbuffer(flat, driver="local-task")` — unchanged (the `rt.system_setup(config=...)` form intermittently fails with `TypeError: 'module' object is not callable` — submodule shadowing; do not reintroduce it). CUDA (`Device("cuda", index)`) via `rt.get_driver("cuda")` (the CUDA HAL driver is COMPILED INTO the runtime wheel — no extra pip dependency) + **`driver.create_device(device_id=index+1)`** — IREE cuda device ids are **1-BASED** (verified: device_id=4 → physical GPU 3; device_id=0 raises `ValueError` "Device id 0 not found", wrapped into `core.BackendError` naming the index) + the `rt.Config(device=...)` → `rt.VmModule.copy_buffer(config.vm_instance, vmfb)` → `rt.load_vm_module(vm_module, config)` path (`load_vm_flatbuffer`'s driver-name form always creates the DEFAULT device and CANNOT select a CUDA index). Artifact/device target compatibility is enforced at load — never silent: the payload's `target_backends` must include the driver matching the device kind (absent `target_backends` in pre-CUDA artifacts = `["llvm-cpu"]`); a mismatch raises `core.BackendError` naming both the artifact's compile targets and the requested device. Inputs: host tensors staged through the cuda per-call fast path (`_staged_input`, see below) or `iree.runtime.asdevicearray(device, tensor.numpy())` (fallbacks); device-resident inputs pass through with ZERO host round-trips. Outputs: device-resident `core.Tensor`s wrapping the IREE `DeviceArray`s (see the execution-semantics bullet).
- Capabilities: `dynamic_shapes=True` (per-op partial — elementwise/dynamic-broadcast symbolic graphs run at multiple concrete sizes, also on cuda; symbolic reshape/conv/slice/pad are rejected by the exporter at `lower()` with a clear `BackendError`); `external_calls=True` (boundary dispatch with host + device-resident kernels — the ONLY adapter with the capability in v1; see the external-kernels bullet below); `dtypes` = f16/f32/f64/i8/i16/i32/i64/bool (unsigned ints excluded — iree-compile 20241104 legalizes unsigned `reduce` nondeterministically/not at all; complex excluded — the exporter v1 defers complex computation beyond cast; the same set applies to cuda — fp64 runs with exact semantics, `--iree-input-demote-f64-to-f32=false` honored: fp64 softmax on cuda matched the numpy reference to 6.9e-18); `collectives=False`, `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`, `rng_bit_generator={"threefry2x32"}` (MEASURED, iree 3.11: native `stablehlo.rng_bit_generator` with `THREE_FRY` legalizes and is BIT-EXACT vs the numpy reference on BOTH llvm-cpu and cuda — key-first `[k0,k1,ctr0,ctr1]` state layout — and is ~1.6–2.1× faster than the inline expansion, so native THREE_FRY is the iree DEFAULT path for threefry graphs; `PHILOX` FAILS legalization on both targets — see Known Issues #2 — so philox uses the exporter's bit-exact inline expansion; probe evidence: 186/186 checks, see #2).
- **External kernels — `external_call` dispatch (`external_calls=True` — the ONLY adapter with the capability in v1):** graphs containing `external_call` ops are SPLIT at `lower()` time by the shared `CompilerBackend` (`../compiler.py::_lower_external_segments` + `../external_split.py`) into an ordered list of SEGMENT programs (plain graphs, no external calls inside, each compiled to its own vmfb — payload `stablehlo-segments`, artifact `iree-vmfb-segments`, per-segment `target_backends`/`iree_compile_args`) plus a JSON-safe kernel-call PLAN that persists in the artifact. The `IreeExternalExecutable` runs the segments strictly in plan order on the HAL device; at each `external_call` boundary the kernel is dispatched through the SAME `etl.register_external_kernel` registry the numpy backend uses (resolved via `etl.external.get_external_kernel_entry(name, "iree")`; unknown name at run → `BackendError` naming the kernel + the registry; outputs validated count/dtype/shape vs the declared specs — never silent coercion). TWO kernel modes: **host mode** (default registration) — the operand tensors are staged to host numpy arrays (the once-per-executable "host-dispatch" staging `UserWarning` fires only when a boundary actually stages host↔device), the kernel runs on host, and its results are staged back as the next segment's inputs (`result_outputs` slots); **device-resident mode** (`etl.register_external_kernel(name, fn, backend="iree", device_resident=True)` — explicit per-backend slot only) — the kernel receives the boundary's device tensors DIRECTLY (never host-staged) and may return device tensors / duck payloads / raw `DeviceArray`s / numpy arrays / tuple-list mixes; results are validated METADATA-ONLY (never a forced host copy) and occupy the same plan slots, where the next segment's same-device pass-through consumes device results with ZERO host round-trips (numpy-returning results stage back — boundary marked staged). Kernel authors may isinstance-check the PUBLIC payload class `etl.backends.adapters.iree.IreeDevicePayload` (the `.data` of device operands): `.device_array` (the iree `DeviceArray` HAL buffer handle), `.shape`, `.dtype`, `.to_host()` (explicit materialization), `.device` (core.Device) — a device kernel runs on the executable's device and may e.g. compile/run additional vmfb modules on the SAME HAL device via `iree.runtime` and return their `DeviceArray`s (raw or wrapped). Carried plain values that are NOT kernel operands stay device-resident across segment runs. Lower-time restrictions (explicit `BackendError`): no calls inside cond/while/scan bodies, STATIC integer result dims only, ≥1 tensor operand, single-function graphs. Kernels are assumed PURE; segments run sequentially, preserving the `callback` effect order. Usage:
  ```python
  etl.register_external_kernel("relu_custom", my_numpy_or_triton_fn)
  @etl.defn
  def model(x, w):
      h = etl.external_call("relu_custom", x, result=etl.TensorSpec((N, D), etl.float32))
      return etl.dot(h, w)
  y = etl.evaluate(model, x_np, w_np, backend="iree")  # split + dispatch (llvm-cpu or cuda)
  ```
  Validated end-to-end on llvm-cpu AND iree-cuda (bit-exact vs the pure-graph numpy run): mid-graph calls, two sequential calls, kernel at graph start / end, multi-output kernels, artifact save/load re-run; regression-pinned by `tests/backends/test_external_call_iree.py` (25 tests) + the round-1 contract update in `tests/ops/test_external_call.py`. xla and tvm keep `external_calls=False` — at `lower()` they now INLINE a registered portable decomposition with a `UserWarning` when one exists, else reject with the upgraded `BackendError` (still containing "not yet wired", naming the op + backend and listing the options: iree/numpy host-dispatch, or registering a portable via `etl.register_external_kernel(name, fn).portable(decomp)`).
- **Execution semantics (device-resident, BOTH targets):** outputs are device-resident `core.Tensor`s wrapping the IREE `DeviceArray`s (`IreeDevicePayload`, the public class — see the external-kernels bullet): `.device` is the run device (`Device("cuda", N)` / `Device("cpu", *)`), `.numpy()` materializes a LAZY host copy on demand (`DeviceArray.to_host()`) — the hot run() path performs no host round-trip, and `core.Tensor` wrappers never alias or pin the underlying HAL buffers. Same-device `core.Tensor` inputs pass through to the invoke with ZERO host round-trips (the DeviceArray is handed to the invoke directly, no copy); the llvm-cpu path is equally device-resident (local-task buffers, lazy `.numpy()`).
- **CUDA per-call fast path (host inputs, `_staged_input`) — TWO TIERS (current hot path):** host numpy inputs are uploaded through PERSISTENT staging buffers cached per `(input index, shape, dtype)` — NO per-call device allocation. Tier choice by nbytes (measured crossover ~16–32 KB; conservative split at `_PINNED_DIRECT_MAX_BYTES = 4 * 1024`):
  - **Pinned direct-write tier (nbytes ≤ 4 KB — the DE rank-0 int64 key, small tensors):** a persistent `DEVICE_LOCAL | HOST_VISIBLE` buffer (`DEFAULT | MAPPING` usage) is mapped once; each call is a single `np.copyto` into the mapped view (~0.02–0.03 ms idle) and the dispatches read that buffer directly. No `queue_copy`, no semaphore, no wait — and NO post-invoke degradation (measured staging-after-invoke median 0.041/0.071 ms vs DMA tier 0.216/0.480 ms on the same box, p90 0.044 vs 0.54+ — 3–7× faster, 12× tighter spread). Cache entry: `("pin", (device_array, mapped_view))`.
  - **DMA tier (nbytes > 4 KB):** `np.copyto` into the mapped view of a persistent `HOST_LOCAL | DEVICE_VISIBLE` (`TRANSFER_SOURCE | MAPPING`) source buffer, then a per-call async `queue_copy` (DMA) into a persistent `DEVICE_LOCAL` staging buffer the dispatches read. **The copy's semaphore wait is LOAD-BEARING — do not drop it:** the iree cuda HAL does NOT reliably stream-order `queue_copy` ahead of invoke dispatches (mixed device+host alternating stress exposed ~0.4% garbage results with an un-fenced copy; the "invoke is stream-ordered after the copy" claim in earlier notes was measured WRONG). Each call waits on a FRESH semaphore (reusing a waited event-semaphore ABORTS the runtime — `event_semaphore.c:354` on second use). The wait itself is implemented as a QUERY-FIRST wait (`_wait_copy_semaphore`): `HalSemaphore.query()` (a cheap host-side read, no kernel sync) skips the heavyweight `HalFence.wait()` (fixed host cost ~0.02 ms measured on an already-signaled fence) when the copy already completed; the full fence wait runs whenever the query shows the copy pending — the ordering guarantee is byte-identical (semaphore values are monotonic, so query-then-wait is race-free; runtimes without `query` fall back to the plain wait). Measured hit rate at 4096×50 (800 KB): ~0% — the PCIe copy (~0.1–0.3 ms on the shared box) never finishes before the host reaches the wait (~20 µs after enqueue); the optimization fires for SMALL DMA-tier inputs (≲ 32 KB) on short queues and costs ~0.4 µs when it misses. Cache entry: `("dma", (hl_buf, hl_view, staging_da))`.
  - Fallbacks to `rt.asdevicearray` (unchanged semantics): oversized inputs (>16 MB), unmappable dtypes, non-cuda devices, cache overflow (bounded at 64 entries). Staging invariants: the DMA tier's fresh-semaphore wait is load-bearing (queue_copy-vs-dispatch ordering race) and each cuda executable retains a 4 KB DEVICE_LOCAL `_pool_anchor` buffer (classic-pool warmth — matters for users who opt into `--cuda_async_allocations=false`). etl sets no allocator flag itself (see the design-decision note below).
- **Measured per-call costs — DE-shaped fused graph at 4096×50 f32 (IREE 3.11.0, RTX A6000, cuda; ~419 stablehlo ops — key splits + 3×4096 randint draws + row gathers + 2×204,800-element normal/uniform draws + elementwise/select/clamp; ~8 iree dispatches; fresh-process phases, best-of/median within one window — box noise moves absolutes ±3×):** raw `entry()` invoke on prebuilt device buffers (the floor, incl. device busy) **~0.089–0.093 ms** (host-staged and device buffers identical); full same-device `etl.run` loop (device-resident outputs fed back as next inputs — ZERO host staging after the first call, ZERO `rt.asdevicearray` calls ever) **~0.146 ms min / ~0.15 ms med / 0.16 p90 in a quiet phase** — the per-call etl wrapper is ~0.05 ms (structure walk + plan lookup ~0.009, per-input validation now sub-µs with cached payload metadata, output wrap + unflatten ~0.01, invoke-call python ~0.02); host-input `etl.run` (fresh host numpy 800 KB state each step) **~1.05 ms (quiet) to 1.8–2.8 ms (noisy)** — the delta is the DMA staging tier: PCIe copy ~0.1–0.3 ms (busy-box up to 0.6) + fresh-semaphore wait ~0.02 ms fixed + residual queue latency, NOT etl python (cProfile: staging 0.5–0.6 ms of the per-call budget at 800 KB, wrapper+validation < 0.1 ms). Output `.numpy()` readback of the 800 KB state (D2H) costs **~0.13 ms quiet / 1.2–1.4 ms noisy** — a per-step host readback is as expensive as the staging and should not be part of the hot loop. Same-window A/B: same-device loop is **2–8× faster than the host-input pattern** (0.15–0.19 vs 1.46–1.80 ms); vs the evox DE/PSO measured wall 1.32 ms/step, the same-device pattern lands ~0.15 ms/step (~9×). Long-run stability at this scale (1.6 MB/call output churn, 500 runs): **no intrinsic drift** — pure-entry 500-run medians 0.085→0.096 ms; earlier-looking pass-through degradation reproduced only in externally noisy windows (intermittent 0.3–5.5 ms spikes hit both entry and python sides — shared-box contention, not etl/iree). The documented drift modes (retained-output frees at ~80 MB scale, `_pool_anchor` removal) are unchanged; at 4096×50 steady-state churn they did NOT reproduce. Small-graph reference (Sphere(4096,10) sum-of-squares, N=300 medians, earlier round): cuda host-input ~0.23–0.33 ms standalone, cuda device pass-through ~0.13 ms, llvm-cpu host ~0.13 ms.
- **Per-run hot-path profile (commit 30ced3b + two-tier staging at 801e2a2, iree-base 3.11.0, RTX A6000, GPU 3, N=300 after 20 warm, A/B-interleaved — box noise moves absolutes ±3×; deltas within one loop are reliable):** trivial `x+1` graph (4096,10) f32: full `etl.run` pass-through ~0.09–0.17 ms = wrapper (`_prepare_flat_inputs` + `_unflatten_outputs`, plan-cached) ~0.018 + `be.run` non-invoke (validation loop + buffer resolution + output wrap + output validation) ~0.031 + **synchronous `entry()` invoke ~0.06–0.10 ms (the floor)**. Host-input `etl.run`: the DMA staging tier adds ~0.05–0.08 ms on an idle queue but **~0.16–0.48 ms right after any invoke** (the copy's semaphore wait absorbs leftover stream latency; the copy itself is ~0.01 ms) — the wait CANNOT be dropped (queue_copy is not reliably stream-ordered before invoke dispatches on the cuda HAL — ~0.4% garbage under mixed device+host stress), which is why ≤4 KB inputs use the pinned direct-write tier instead (0.04–0.07 ms after invoke, no wait). `entry()` is fully synchronous with the whole device queue: entry timed after queued 32/64/256/1024 MB D2D copies scales 0.18/0.28/1.17/3.52 ms (linear ≈ 230–330 GB/s) — the invoke's completion event fires only after everything ahead of it; back-to-back entries show the second call absorbs the first's remaining GPU time. A rank-0 int64 (DE key) or (4,) f32 host input now stages via the pinned tier (~0.025 ms idle-queue); the (4,) host-run "0.7 ms" outlier in one session was box noise, not a shape effect (`entry(staged_da) ≈ entry(da)` interleaved). **Stability (500-run phases, fresh process each):** pure pass-through and pure host-input phases show NO drift (0.091→0.092 / 0.153→0.159). Drift appears only when (a) outputs are retained then freed (~80 MB) — subsequent dropped runs degrade 0.22→0.94 ms over 500 runs with 100–400 ms synchronous-trim spikes around the free, (b) the `_pool_anchor` is removed — host runs degrade 0.36→0.86 ms over 500 runs (anchor prevents allocator-pool trim cycles), (c) host-input runs precede pass-through runs in one process — pass-through degrades ~0.087→0.35 ms (noisy box; ~0.13→0.17 on a quiet box, `entry` itself 0.068→0.091, no recovery over 200 runs). `gc.collect()` every 100 runs does not prevent the drift; the asdevicearray fallback (no staging cache) is stable at ~0.9–1.0 ms. Nanobind leak counts at exit are CONSTANT (5 instances / 4 keep_alive / 5 types / 39 functions) regardless of how many runs a process did — a fixed singleton set, not per-run growth. Intermittent 0.3–0.8 s per-run stalls appear on this shared box and hit BOTH the entry (GPU-side, e.g. 582 ms in one entry) and the non-entry Python code (CPU-side, e.g. 215 ms) — external contention (other agents on GPUs 0–2/4–7, shared PCIe/CPU), not etl/iree behavior. Full DE ask (`etl.run`, pop32×10, cuda) is ~0.33–0.39 ms in a quiet window (cProfile: etl wrapper ~0.02–0.05 ms total — validation/flatten/unflatten are NOT the bottleneck; the rest is iree invoke + 4× pinned staging + output extraction).

### XLA via the PJRT C API (`xla.py`) — no jaxlib

- **Plugin** (distribution OUT of scope — users provide the binary): resolved in order (a) `plugin_path` (a compile AND load option — `etl.compile(lowered, backend="xla", plugin_path=...)` AND `etl.load(artifact, backend="xla", plugin_path=...)`; the load-stage variant fixes the re-discovery gap: a compile with an explicit `plugin_path` followed by a bare `load` re-resolves via env/well-known paths), (b) env `ETL_PJRT_PLUGIN`, (c) well-known paths (`/usr/local/lib`, `/usr/lib`, `$HOME/.local/lib`, `./`). None found ⇒ `core.BackendError` with an actionable message (build via `bazel build //xla/pjrt/c:pjrt_c_api_cpu_plugin` from OpenXLA, or any XLA build exporting `GetPjRtApi`). NO pip hint — there is no pip-installable plugin. jaxlib is NEVER imported in this adapter.
- **Compile options:** `plugin_path` (above) + `xla_compile_options` = the raw serialized `xla.CompileOptionsProto` bytes (the wire form XLA's own Python API would build), threaded into the already-declared `PJRT_Client_Compile_Args.compile_options` / `compile_options_size` fields (NULL/0 when unset). etl does NOT parse or validate the protobuf contents — the plugin does (any invalid option fails loudly as a PJRT error wrapped in `core.BackendError`). Non-bytes values raise `core.BackendError` naming the option.
- compile: `ctypes.CDLL(path)` → `GetPjRtApi()` → **version gate** (`PJRT_Api.version`/`struct_size` vs the bindings' minimum — too old ⇒ explicit `BackendError`, never silent fallback) → `PJRT_Client_Create` (empty options) → `PJRT_Client_Compile` with `PJRT_Program{code=mlir_text, format="mlir"}` — the plugin accepts MLIR text directly (header-documented: "MLIR module bytecode (or string)"; the same thing jax's own PJRT layer passes). NO MLIR python bindings anywhere in the adapter. `PJRT_Executable_Serialize` → bytes → base64 in the artifact payload (alongside `mlir_text` + `entry_functions`).
- load/run: deserialize via `PJRT_Executable_DeserializeAndLoad` on a fresh client from the re-discovered plugin — never recompiles (a successful load hands the client to the executable; it is destroyed only on failure); inputs staged via `PJRT_Client_BufferFromHostBuffer` (all 14 etl dtypes incl. complex64/128, dense row-major numpy, `np.ascontiguousarray`, `kImmutableUntilTransferCompletes`, transfer event awaited + destroyed, host array kept alive on the buffer — some plugins alias host memory beyond the documented point); execute via `PJRT_LoadedExecutable_Execute` on the first addressable device; outputs copied via `PJRT_Buffer_ToHostBuffer` → writable numpy → `core.Tensor`.
- **Error contract (binding)**: every PJRT call returns `PJRT_Error*` (NULL = success); the driver checks EVERY call, extracts `PJRT_Error_Message` text, destroys the error, and raises `core.BackendError` naming the failing step. All handles (errors/clients/executables/buffers/events/serialized wrappers) destroyed via matching entry points (try/finally + `close()` helpers; the loaded-executable's inner unloaded twin from `PJRT_LoadedExecutable_GetExecutable` is destroyed first).
- Capabilities: `dynamic_shapes=False` (compile-time static-shape gate via `_resolve_static_shape`/`_StaticShapeError`; the gate decision is recorded in the artifact (`static_input_shapes`/`static_output_shapes`) and enforced exactly at `run()`); `dtypes` = all 14 etl dtypes; `collectives=False` (conservative — see Known Issues); `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`, `rng_bit_generator={"threefry2x32", "philox4x32_10"}` (by design — XLA ships RngBitGenerator with THREE_FRY/PHILOX; the exporter's native path with the key-first state layout is used for both. Tests stay gate-skipped without a user-provided PJRT plugin; bit-exactness vs the numpy reference MUST be re-validated with a real plugin before flipping any dependent default).
- `check_available()`: bindings integrity + plugin discovery + `GetPjRtApi` + version gate + live client create/destroy round-trip. Artifact `runtime_dependencies` records numpy + the `pjrt_c_api` header commit (bindings provenance) + plugin platform/version string — no jaxlib.

### TVM (`tvm.py`) — jax-free, jaxlib MLIR bindings only

- translate: `tvm.relax.frontend.stablehlo.from_stablehlo(mlir_text)` (exists in 0.26; `tvm.relax.frontend.from_mlir` does NOT; `tvm.relax.vm.build` does NOT — build lives in `tvm.relax.vm_build`, re-exported as `tvm.relax.build`). The vendored translator parses MLIR with jaxlib's bundled bindings — hence tvm needs **jaxlib** (NOT the `jax` package) at adapter runtime.
- **MLIR binding seam (`_mlir_bindings.py`)**: ALL MLIR-binding access (context creation, `ir.Module.parse`, the `ir` re-export) routes through this one module; its docstring documents the binding-provider contract — jaxlib is required ONLY for its bundled LLVM MLIR python bindings and a future standalone `mlir`/`stablehlo` PyPI package can replace jaxlib with a one-module swap.
- **jax shim (`tvm_util._install_jax_shim`)**: the vendored translator imports `from jaxlib import mlir` (12 sites) and `from jaxlib.mlir.dialects import stablehlo` (2 sites) — those work as-is — plus `from jax._src.interpreters import mlir as jax_mlir` (1 site, inside `from_stablehlo()`: `jax_mlir.make_ir_context()` + `jax_mlir.ir.Module.parse`). That one import is satisfied by injected `sys.modules` shims for `jax`, `jax._src`, `jax._src.interpreters`, `jax._src.interpreters.mlir` (the mlir shim provides `make_ir_context()` delegating to `_mlir_bindings.make_ir_context` and re-exports `jaxlib.mlir` as `ir`). Injection happens at the top of BOTH `check_available()` and `ensure_compat()` — before any `tvm.relax.frontend.stablehlo` import (in 0.26.0 the translator's jax import executes inside `from_stablehlo()`; the shim covers import-time and call-time, and future TVM versions that move it to module level). Idempotent; a real jax already imported in-process is left in place; `sys.modules["jax"] = None` is overwritten by the shim. Verified end-to-end with real jax blocked.
- build/run: `tvm.relax.vm_build.build(mod, target=tvm.target.Target("llvm"))` → `VMExecutable`; run via `tvm.runtime.vm.VirtualMachine(ex, tvm.runtime.cpu())["main"](...)`; inputs `tvm.runtime.tensor(np_array, tvm.runtime.cpu())` (the `tvm.nd` namespace no longer exists); outputs `tvm.runtime.Tensor.numpy()` → `core.Tensor`. **Compile options:** `tvm_target` (str, default `"llvm"` — passed as `target=tvm.target.Target(...)`) and `tvm_pass_configs` (dict of Relax/TIR pass configs). `pass_configs` is forwarded to `vm_build.build` ONLY when non-None — the installed TVM 0.26 `build` signature has NO `pass_configs` parameter (verified), so a non-None value on such a build raises a loud `core.BackendError` suggesting to drop the option (never silent, never ignored); on a TVM build that accepts it, the dict is forwarded verbatim.
- persist: `VMExecutable.export_library(path)` → host .so, base64'd into the payload (`format="tvm-vm-library"`); load decodes to a temp file and `tvm.runtime.load_module(path)` — no recompile at load. `Module.save_to_file` does not exist in 0.26.
- Compatibility shim (REQUIRED): the TVM 0.26.0 vendored StableHLO translator targets the OLD jax mlir python bindings; `tvm_util.ensure_compat()` patches five gaps (type-check classmethods, OpView/Operation key normalization, `broadcast_to` ShapeExpr, `DenseI64ArrayAttr` decoding, float16 np.asarray constant decoding) — each patch restores exactly the semantics the vendored code assumed, no computation changes.
- Op coverage gate: `SUPPORTED_STABLEHLO_OPS` whitelist checked at compile (`core.BackendError` naming the op otherwise): arithmetic, unary math, compare, select, bitwise/logical, convert, broadcast_in_dim, reshape, transpose, concatenate, slice (unit strides), pad (zero interior), reduce (add/max/min/mul), dot_general (matmul), constant. Rejected: control flow (`stablehlo.if`/`while`), gather/scatter, remainder, conv/reduce_window (vendored handlers hardcode NHWC/HWIO — silently wrong for etl's NCHW conv), multi-function modules, multi-output functions.
- Capabilities: `dynamic_shapes=True` (per-op partial — elementwise symbolic graphs validated at multiple sizes, constant-free graphs; the exporter rejects symbolic reshape/conv/slice/pad at `lower()`); `dtypes` = f16/f32/f64/i8/i16/i32/i64/u8/u16/u32/u64/bool (complex excluded — vendored translator raises); `collectives=False`, `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`, `rng_bit_generator=frozenset()` (the TVM StableHLO frontend has no rng_bit_generator support — the exporter's bit-exact inline Threefry2x32/Philox4x32-10 expansions are used).

## Constraints (binding)

- Heavy-import rule: `iree`/`jaxlib`/`tvm` imports live ONLY inside function bodies; top-level imports limited to stdlib, `etl.core`, and the `..compiler`/`..program`/`..registry` siblings (plus this package's `_pjrt_c_api.py`/`_mlir_bindings.py` for the xla/tvm adapters). Verified: `import etl` leaves `sys.modules` free of iree/jax/jaxlib/tvm.
- **No `jax`**: `import jax` / `from jax` is forbidden anywhere in `etl/` (grep-proof; the TVM shim satisfies the vendored translator's `jax._src` import). `jaxlib` may appear ONLY inside function bodies, ideally only via `_mlir_bindings.py`, and NEVER in the xla adapter (`_pjrt_c_api.py`/`xla_util.py`/`xla.py` are jaxlib-free).
- Errors: capability violations and compiler/translator failures raise `core.BackendError` naming the op/feature — never silent fallback to numpy or partial semantics; load-time mismatches raise `core.PersistenceError`; dtype mismatches `core.DTypeError`, shape mismatches `core.ShapeError` (mirrors the numpy interpreter).
- Staging never composes: `load` never re-traces/lowers/compiles; device handles are never serialized.
- CPU only, EXCEPT the iree adapter which also accepts `core.Device("cuda", index)` (see the IREE section; the numpy/xla/tvm paths remain CPU-only); a device kind the adapter does not support raises `core.BackendError`, non-`Device` objects `core.DeviceError`.

## Design decisions
- **IREE cuda allocator flag — etl sets NO process-global `--cuda_async_allocations` value; iree's own default (`true`, stream-ordered allocations) stands.** Forcing `false` measured ~2-3x slower per step on the fused DE/PSO step graphs (interleaved same-session A/B, iree 3.11.0 / RTX A6000: 4096x50 ~2.2-3.5 ms/step vs ~1.16 ms/step; async-ON also won or tied every other measured cell — 32x10/4096x10/1024x50, DE and PSO; steps/s 862 vs 282-326 at 4096x50). The older "async-ON re-trims the pool ~1.1 ms per invocation" observation (ceb2ba2-era) did not reproduce on this stack. The `_pool_anchor` is retained per executable (classic-pool warmth for opt-in users). Users who need the classic allocator pool can still opt in per load via `iree_runtime_args=["--cuda_async_allocations=false"]` or `IREE_PY_RUNTIME_FLAGS` — both loud and fully supported. Policy point: `_configure_cuda_runtime_flags` in iree.py (deliberate no-op).

9. **IREE opt-level-related cuda limits (upstream iree 3.11 codegen; validated on the fixed code, commit c7c5022 — do NOT fix in etl):** (a) **`--iree-opt-level=O2`/`O3` on cuda SILENTLY produce WRONG eigenvalues for the `eigh` cyclic-Jacobi composition** (bare eigh AND the CMAES fused tell: measured w_err ~1.3e1 vs LAPACK and best_fit 1.64 vs numpy 4.35 — the tell runs WITHOUT crashing, just wrong); O0/O1/default are correct on cuda, and llvm-cpu is correct at ALL levels — the if-hoist workaround itself is opt-level-agnostic; (b) **the full NSGA2 tell graph FAILS to COMPILE on cuda at O2/O3** (upstream fusion+hoisting on the crowding-distance scatter; default/O0/O1 work on both backends with the default options `while_init_rewrite` ON + `sort_emission` auto→count). Both limits are upstream iree codegen, unrelated to etl's `opt_level` plumbing (the flag translation is correct — the same flags reproduce the limits on raw `iree-compile` of etl-dumped mlir); details in `../stablehlo/CONTEXT.md` Notes for agents.

## Dependency surface (verified at runtime: jaxlib 0.10.2 / apache-tvm 0.26.0)

- **xla adapter**: ZERO pip dependencies. A user-provided PJRT plugin `.so` (exporting `GetPjRtApi`) is required at compile/load time, discovered via `options["plugin_path"]` → `ETL_PJRT_PLUGIN` → well-known paths. Bindings provenance (header URL + commit) is recorded in `_pjrt_c_api.py` and in the artifact `runtime_dependencies` (`pjrt_c_api` header commit + plugin platform/version).
- **tvm adapter**: `apache-tvm` + `jaxlib` (MLIR bindings only). The `jax` package is never imported anywhere in `etl/`; the vendored translator's `jax._src.interpreters.mlir` import resolves to the `_mlir_bindings`-backed shim. `tvm_util` routes all MLIR access (`parse_stablehlo`, `precheck_module`, `ensure_compat` patches, `_op_key`) through `_mlir_bindings` (`make_ir_context`, `parse_module`, `ir` re-export). `check_available()` probes `jaxlib.mlir` + `jaxlib.mlir.ir` (pip hint `pip install etl[tvm]`).
- Facts that drove this design (verified; do not re-investigate): NO standalone xla/pjrt/jax-cpu/stablehlo/mlir packages on PyPI (only squatter placeholders); NO `pjrt_c_api_cpu_plugin.so` in any jaxlib wheel (0.4.38, 0.10.2 checked — CPU PJRT client embedded in `_xla.so`); jaxlib's `_xla.so` does not export `GetPjRtApi`; `iree.compiler.dialects` has no stablehlo module. The former jaxlib-based xla design (`jaxlib.xla_client`: `make_cpu_client`, `batched_device_put`, `compile_and_load`, `serialize`/`deserialize_executable`) is gone — see git history.
- **`iree.py` is a legitimately long file (~1900+ lines) — do not split without a plan:** one module holds the whole iree adapter surface (options/defaults, `IreeBackend`, `IreeExecutable`, the staging fast path `_staged_input`/`_build_buffers`, `_IreeSegmentExecutable`, `IreeExternalExecutable`, the public `IreeDevicePayload`, and `register()`); its pieces share tight coupling (staging caches, payload wrapping, core.Device ↔ HAL device mapping), so splitting would spread one adapter's invariants across files for no delegation benefit.
