# etl/backends/adapters — optional compiler adapters (IREE, XLA via PJRT, TVM)

## Intent

Pluggable compiler backends for etl. Each adapter consumes the SHARED StableHLO lowering produced by `CompilerBackend.lower` (`../compiler.py` — verify, capability pre-check, block-portable inlining, StableHLO export, Signature recording) and implements only the compiler-specific half: optional dependency probe (`check_available` override — the shared base is a concrete no-op), `compile` (invoke the external compiler on the MLIR text), `load` (rebuild the executable from the artifact — never re-compiling). Activation is register-on-first-use: `etl.backends.registry.get(name)` imports the adapter module via `registry.OPTIONAL_ADAPTERS` and calls its `register()`; `import etl` never imports an adapter or its compiler dependency.

**Dependency posture (binding):** etl depends directly on the ML compilers — the `jax` frontend package appears NOWHERE in `etl/`, and the xla adapter uses no jaxlib either:
- **xla** = the PJRT C API via pure-stdlib ctypes against a USER-PROVIDED plugin binary (`.so` exporting `GetPjRtApi`) — there is no pip-installable package (verified: no standalone xla/pjrt/jax-cpu/stablehlo/mlir packages on PyPI; no `pjrt_c_api_cpu_plugin.so` in any jaxlib wheel (0.4.38, 0.10.2 checked — the CPU client is embedded in `_xla.so`); jaxlib's `_xla.so` does not export `GetPjRtApi`). Plugin distribution is explicitly OUT of scope.
- **tvm** = apache-tvm + jaxlib, where jaxlib is used ONLY for its bundled LLVM MLIR python bindings (a verbatim upstream-bindings bundle — the same bindings any MLIR tooling uses, NOT the jax API), behind the `_mlir_bindings` seam. The vendored TVM translator's `jax._src.interpreters.mlir` import is satisfied by an injected shim; the `jax` package is never imported.

Status: all three adapters implemented and validated. iree against the installed iree distributions (3.11.0 `iree-base-*` and legacy 20241104.1068) — **including end-to-end CUDA GPU support** (compile option `target_backends=["cuda"]` + `load(device=core.Device("cuda", index))`, validated on 8x NVIDIA RTX A6000, see the IREE section); xla against a THROWAWAY fake PJRT plugin (ctypes layout/offsets, dispatch, error handling, lifecycle, serialize round-trip — real-plugin end-to-end parity PENDING a real `.so`, see Known Issues); tvm against apache-tvm 0.26.0 + jaxlib 0.10.2 (numpy parity incl. dynamic shapes, jax-package-free verified with `sys.modules["jax"] = None`).

## API Surface

Each adapter module (`iree.py`, `xla.py`, `tvm.py`) exposes the same shape:
- `<Name>Backend` (a `CompilerBackend` subclass; names `"iree"`, `"xla"`, `"tvm"`), `<Name>Executable` (a `CompilerExecutable` subclass), singleton `<name>_backend`, module-level `register()` (probes the dependency — `core.BackendError` with an actionable message when missing — then registers idempotently).
- `<name>_util.py` helpers: `xla_util.py` (PJRT C API driver: plugin discovery/loading, version gate, client/compile/execute/buffer/serialize plumbing), `tvm_util.py` (vendored-translator compat shim + jax `sys.modules` shim injection, op whitelist gate, translate/build/run/persist helpers).
- `_pjrt_c_api.py`: vendored ctypes translation of the Apache-2.0 PJRT C API header (header URL + commit recorded; ABI/offsets verified against a plugin compiled from the real header); `_mlir_bindings.py`: the MLIR binding-provider seam (jaxlib → standalone swap).
- `__init__.py`: documentation only, imports nothing heavy.

## Adapter designs (validated end-to-end, numpy-backend parity)

### IREE (`iree.py`) — CPU (llvm-cpu) AND CUDA GPU

- compile: `iree.compiler.compile_str(mlir_text, target_backends=..., input_type="stablehlo", extra_args=["--iree-input-demote-f64-to-f32=false", (+ "--iree-llvmcpu-target-cpu=generic" AND "--iree-llvmcpu-link-embedded=false" ONLY when llvm-cpu is requested — the default embedded `-nostdlib -static` link cannot resolve libm symbols (log/cos/floor) that f64 math ops lower to; the dynamically-linked dylib resolves them from system libc/libm at load)])` → VM flatbuffer, base64'd into the payload (`format="iree-vmfb"`, keeps `mlir_text` + `entry_functions` + `target_backends`). The compile targets come from the `target_backends` **compile option** (`etl.compile(lowered, backend="iree", target_backends=["cuda"])`), default `["llvm-cpu"]` — the default path is byte-identical to pre-CUDA behavior. v1 supported set `{"llvm-cpu", "cuda"}`; a non-list/tuple, an empty list, or an unknown target raises `core.BackendError` naming the offender — never silent fallback. `CompiledArtifact.target` = `"cpu"` for `["llvm-cpu"]`, `"cuda"` for `["cuda"]`, `"+"`-joined for mixed lists. Compiler diagnostics re-raised as `core.BackendError` (never silent). No arch flag is needed for the A6000s: the default codegen target is sm_60 PTX (`+ptx76`), JIT'd by the CUDA driver to sm_86 at load.
- load/run: CPU (device `None` or `Device("cpu", *)`) via the RELIABLE path `iree.runtime.get_driver("local-task")` + `driver.create_default_device()` + `load_vm_flatbuffer(flat, driver="local-task")` — unchanged (the `rt.system_setup(config=...)` form intermittently fails with `TypeError: 'module' object is not callable` — submodule shadowing; do not reintroduce it). CUDA (`Device("cuda", index)`) via `rt.get_driver("cuda")` (the CUDA HAL driver is COMPILED INTO the runtime wheel — no extra pip dependency) + **`driver.create_device(device_id=index+1)`** — IREE cuda device ids are **1-BASED** (verified: device_id=4 → physical GPU 3; device_id=0 raises `ValueError` "Device id 0 not found", wrapped into `core.BackendError` naming the index) + the `rt.Config(device=...)` → `rt.VmModule.copy_buffer(config.vm_instance, vmfb)` → `rt.load_vm_module(vm_module, config)` path (`load_vm_flatbuffer`'s driver-name form always creates the DEFAULT device and CANNOT select a CUDA index). Artifact/device target compatibility is enforced at load — never silent: the payload's `target_backends` must include the driver matching the device kind (absent `target_backends` in pre-CUDA artifacts = `["llvm-cpu"]`); a mismatch raises `core.BackendError` naming both the artifact's compile targets and the requested device. Inputs: host tensors staged through the cuda per-call fast path (`_staged_input`, see below) or `iree.runtime.asdevicearray(device, tensor.numpy())` (fallbacks); device-resident inputs pass through with ZERO host round-trips. Outputs: device-resident `core.Tensor`s wrapping the IREE `DeviceArray`s (see the execution-semantics bullet).
- Capabilities: `dynamic_shapes=True` (per-op partial — elementwise/dynamic-broadcast symbolic graphs run at multiple concrete sizes, also on cuda; symbolic reshape/conv/slice/pad are rejected by the exporter at `lower()` with a clear `BackendError`); `dtypes` = f16/f32/f64/i8/i16/i32/i64/bool (unsigned ints excluded — iree-compile 20241104 legalizes unsigned `reduce` nondeterministically/not at all; complex excluded — the exporter v1 defers complex computation beyond cast; the same set applies to cuda — fp64 runs with exact semantics, `--iree-input-demote-f64-to-f32=false` honored: fp64 softmax on cuda matched the numpy reference to 6.9e-18); `collectives=False`, `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`, `rng_bit_generator=False` (EMPIRICAL, iree 3.11 llvm-cpu: `stablehlo.rng_bit_generator` with `THREE_FRY` legalizes and is bit-exact vs the numpy reference with the key-first `[k0,k1,ctr0,ctr1]` state layout, but `PHILOX` FAILS legalization — see Known Issues #5; the exporter's bit-exact inline Threefry2x32/Philox4x32-10 expansions are used for both algorithms on this target; probe evidence: 186/186 checks, see #5).
- **Execution semantics (device-resident, BOTH targets):** outputs are device-resident `core.Tensor`s wrapping the IREE `DeviceArray`s (`_IreeDevicePayload`): `.device` is the run device (`Device("cuda", N)` / `Device("cpu", *)`), `.numpy()` materializes a LAZY host copy on demand (`DeviceArray.to_host()`) — the hot run() path performs no host round-trip, and `core.Tensor` wrappers never alias or pin the underlying HAL buffers. Same-device `core.Tensor` inputs pass through to the invoke with ZERO host round-trips (the DeviceArray is handed to the invoke directly, no copy); the llvm-cpu path is equally device-resident (local-task buffers, lazy `.numpy()`).
- **CUDA per-call fast path (host inputs, `_staged_input`) — TWO TIERS (current hot path):** host numpy inputs are uploaded through PERSISTENT staging buffers cached per `(input index, shape, dtype)` — NO per-call device allocation. Tier choice by nbytes (measured crossover ~16–32 KB; conservative split at `_PINNED_DIRECT_MAX_BYTES = 4 * 1024`):
  - **Pinned direct-write tier (nbytes ≤ 4 KB — the DE rank-0 int64 key, small tensors):** a persistent `DEVICE_LOCAL | HOST_VISIBLE` buffer (`DEFAULT | MAPPING` usage) is mapped once; each call is a single `np.copyto` into the mapped view (~0.02–0.03 ms idle) and the dispatches read that buffer directly. No `queue_copy`, no semaphore, no wait — and NO post-invoke degradation (measured staging-after-invoke median 0.041/0.071 ms vs DMA tier 0.216/0.480 ms on the same box, p90 0.044 vs 0.54+ — 3–7× faster, 12× tighter spread). Cache entry: `("pin", (device_array, mapped_view))`.
  - **DMA tier (nbytes > 4 KB):** `np.copyto` into the mapped view of a persistent `HOST_LOCAL | DEVICE_VISIBLE` (`TRANSFER_SOURCE | MAPPING`) source buffer, then a per-call async `queue_copy` (DMA) into a persistent `DEVICE_LOCAL` staging buffer the dispatches read. **The copy's semaphore wait is LOAD-BEARING — do not drop it:** the iree cuda HAL does NOT reliably stream-order `queue_copy` ahead of invoke dispatches (mixed device+host alternating stress exposed ~0.4% garbage results with an un-fenced copy; the "invoke is stream-ordered after the copy" claim in earlier notes was measured WRONG). Each call waits on a FRESH semaphore (reusing a waited event-semaphore ABORTS the runtime — `event_semaphore.c:354` on second use). Cache entry: `("dma", (hl_buf, hl_view, staging_da))`.
  - Fallbacks to `rt.asdevicearray` (unchanged semantics): oversized inputs (>16 MB), unmappable dtypes, non-cuda devices, cache overflow (bounded at 64 entries). Two invariants keep the path fast: the process-global flag `--cuda_async_allocations=false` (parsed once, idempotent, user `IREE_PY_RUNTIME_FLAGS` wins) and a retained 4 KB DEVICE_LOCAL `_pool_anchor` buffer per executable.
- **Measured per-call costs / invoke root cause (IREE 3.11.0, RTX A6000, Sphere(4096,10) sum-of-squares, N=300 medians):** cuda host-input path ~0.33 ms standalone (~0.23 ms A/B-interleaved with pass-through; both within the ~0.3 target — PCIe noise on this busy 8-GPU box moves the entry floor 0.07–0.31 ms); cuda device pass-through ~0.13 ms (zero host round-trips); llvm-cpu host ~0.13 ms. The old direct-read path (dispatches reading a persistent DEVICE_LOCAL|HOST_VISIBLE "pinned" buffer memcpy'd from host) measured ~0.5–1.2 ms/call: host writes into host-mapped DEVICE memory go over PCIe write-through AND the driver serializes a host write against outstanding device reads (~0.3–0.6 ms stall) — the staging pattern removes both. The historic "0.77 ms invoke" was a stream-ordered-allocator re-trim artifact: with async allocations enabled the pool re-trims to empty whenever invoke results are freed, making every subsequent invocation ~1.1 ms — fixed by `--cuda_async_allocations=false` + the anchor (invoke now 0.035–0.05 ms).
- **Per-run hot-path profile (commit 30ced3b + two-tier staging at 801e2a2, iree-base 3.11.0, RTX A6000, GPU 3, N=300 after 20 warm, A/B-interleaved — box noise moves absolutes ±3×; deltas within one loop are reliable):** trivial `x+1` graph (4096,10) f32: full `etl.run` pass-through ~0.09–0.17 ms = wrapper (`_prepare_flat_inputs` + `_unflatten_outputs`, plan-cached) ~0.018 + `be.run` non-invoke (validation loop + buffer resolution + output wrap + output validation) ~0.031 + **synchronous `entry()` invoke ~0.06–0.10 ms (the floor)**. Host-input `etl.run`: the DMA staging tier adds ~0.05–0.08 ms on an idle queue but **~0.16–0.48 ms right after any invoke** (the copy's semaphore wait absorbs leftover stream latency; the copy itself is ~0.01 ms) — the wait CANNOT be dropped (queue_copy is not reliably stream-ordered before invoke dispatches on the cuda HAL — ~0.4% garbage under mixed device+host stress), which is why ≤4 KB inputs use the pinned direct-write tier instead (0.04–0.07 ms after invoke, no wait). `entry()` is fully synchronous with the whole device queue: entry timed after queued 32/64/256/1024 MB D2D copies scales 0.18/0.28/1.17/3.52 ms (linear ≈ 230–330 GB/s) — the invoke's completion event fires only after everything ahead of it; back-to-back entries show the second call absorbs the first's remaining GPU time. A rank-0 int64 (DE key) or (4,) f32 host input now stages via the pinned tier (~0.025 ms idle-queue); the (4,) host-run "0.7 ms" outlier in one session was box noise, not a shape effect (`entry(staged_da) ≈ entry(da)` interleaved). **Stability (500-run phases, fresh process each):** pure pass-through and pure host-input phases show NO drift (0.091→0.092 / 0.153→0.159). Drift appears only when (a) outputs are retained then freed (~80 MB) — subsequent dropped runs degrade 0.22→0.94 ms over 500 runs with 100–400 ms synchronous-trim spikes around the free, (b) the `_pool_anchor` is removed — host runs degrade 0.36→0.86 ms over 500 runs (anchor prevents allocator-pool trim cycles), (c) host-input runs precede pass-through runs in one process — pass-through degrades ~0.087→0.35 ms (noisy box; ~0.13→0.17 on a quiet box, `entry` itself 0.068→0.091, no recovery over 200 runs). `gc.collect()` every 100 runs does not prevent the drift; the asdevicearray fallback (no staging cache) is stable at ~0.9–1.0 ms. Nanobind leak counts at exit are CONSTANT (5 instances / 4 keep_alive / 5 types / 39 functions) regardless of how many runs a process did — a fixed singleton set, not per-run growth. Intermittent 0.3–0.8 s per-run stalls appear on this shared box and hit BOTH the entry (GPU-side, e.g. 582 ms in one entry) and the non-entry Python code (CPU-side, e.g. 215 ms) — external contention (other agents on GPUs 0–2/4–7, shared PCIe/CPU), not etl/iree behavior. Full DE ask (`etl.run`, pop32×10, cuda) is ~0.33–0.39 ms in a quiet window (cProfile: etl wrapper ~0.02–0.05 ms total — validation/flatten/unflatten are NOT the bottleneck; the rest is iree invoke + 4× pinned staging + output extraction).

### XLA via the PJRT C API (`xla.py`) — no jaxlib

- **Plugin** (distribution OUT of scope — users provide the binary): resolved in order (a) `options["plugin_path"]` (backend compile options, e.g. `etl.compile(lowered, backend="xla", plugin_path="/path/to/pjrt_c_api_cpu_plugin.so")`), (b) env `ETL_PJRT_PLUGIN`, (c) well-known paths (`/usr/local/lib`, `/usr/lib`, `$HOME/.local/lib`, `./`). None found ⇒ `core.BackendError` with an actionable message (build via `bazel build //xla/pjrt/c:pjrt_c_api_cpu_plugin` from OpenXLA, or any XLA build exporting `GetPjRtApi`). NO pip hint — there is no pip-installable plugin. jaxlib is NEVER imported in this adapter.
- compile: `ctypes.CDLL(path)` → `GetPjRtApi()` → **version gate** (`PJRT_Api.version`/`struct_size` vs the bindings' minimum — too old ⇒ explicit `BackendError`, never silent fallback) → `PJRT_Client_Create` (empty options) → `PJRT_Client_Compile` with `PJRT_Program{code=mlir_text, format="mlir"}` — the plugin accepts MLIR text directly (header-documented: "MLIR module bytecode (or string)"; the same thing jax's own PJRT layer passes). NO MLIR python bindings anywhere in the adapter. `PJRT_Executable_Serialize` → bytes → base64 in the artifact payload (alongside `mlir_text` + `entry_functions`).
- load/run: deserialize via `PJRT_Executable_DeserializeAndLoad` on a fresh client from the re-discovered plugin — never recompiles (a successful load hands the client to the executable; it is destroyed only on failure); inputs staged via `PJRT_Client_BufferFromHostBuffer` (all 14 etl dtypes incl. complex64/128, dense row-major numpy, `np.ascontiguousarray`, `kImmutableUntilTransferCompletes`, transfer event awaited + destroyed, host array kept alive on the buffer — some plugins alias host memory beyond the documented point); execute via `PJRT_LoadedExecutable_Execute` on the first addressable device; outputs copied via `PJRT_Buffer_ToHostBuffer` → writable numpy → `core.Tensor`.
- **Error contract (binding)**: every PJRT call returns `PJRT_Error*` (NULL = success); the driver checks EVERY call, extracts `PJRT_Error_Message` text, destroys the error, and raises `core.BackendError` naming the failing step. All handles (errors/clients/executables/buffers/events/serialized wrappers) destroyed via matching entry points (try/finally + `close()` helpers; the loaded-executable's inner unloaded twin from `PJRT_LoadedExecutable_GetExecutable` is destroyed first).
- Capabilities: `dynamic_shapes=False` (compile-time static-shape gate via `_resolve_static_shape`/`_StaticShapeError`; the gate decision is recorded in the artifact (`static_input_shapes`/`static_output_shapes`) and enforced exactly at `run()`); `dtypes` = all 14 etl dtypes; `collectives=False` (conservative — see Known Issues); `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`, `rng_bit_generator=True` (by design — XLA ships RngBitGenerator with THREE_FRY/PHILOX; the exporter's native path with the key-first state layout is used. Tests stay gate-skipped without a user-provided PJRT plugin; bit-exactness vs the numpy reference MUST be re-validated with a real plugin before flipping any dependent default).
- `check_available()`: bindings integrity + plugin discovery + `GetPjRtApi` + version gate + live client create/destroy round-trip. Artifact `runtime_dependencies` records numpy + the `pjrt_c_api` header commit (bindings provenance) + plugin platform/version string — no jaxlib.

### TVM (`tvm.py`) — jax-free, jaxlib MLIR bindings only

- translate: `tvm.relax.frontend.stablehlo.from_stablehlo(mlir_text)` (exists in 0.26; `tvm.relax.frontend.from_mlir` does NOT; `tvm.relax.vm.build` does NOT — build lives in `tvm.relax.vm_build`, re-exported as `tvm.relax.build`). The vendored translator parses MLIR with jaxlib's bundled bindings — hence tvm needs **jaxlib** (NOT the `jax` package) at adapter runtime.
- **MLIR binding seam (`_mlir_bindings.py`)**: ALL MLIR-binding access (context creation, `ir.Module.parse`, the `ir` re-export) routes through this one module; its docstring documents the binding-provider contract — jaxlib is required ONLY for its bundled LLVM MLIR python bindings and a future standalone `mlir`/`stablehlo` PyPI package can replace jaxlib with a one-module swap.
- **jax shim (`tvm_util._install_jax_shim`)**: the vendored translator imports `from jaxlib import mlir` (12 sites) and `from jaxlib.mlir.dialects import stablehlo` (2 sites) — those work as-is — plus `from jax._src.interpreters import mlir as jax_mlir` (1 site, inside `from_stablehlo()`: `jax_mlir.make_ir_context()` + `jax_mlir.ir.Module.parse`). That one import is satisfied by injected `sys.modules` shims for `jax`, `jax._src`, `jax._src.interpreters`, `jax._src.interpreters.mlir` (the mlir shim provides `make_ir_context()` delegating to `_mlir_bindings.make_ir_context` and re-exports `jaxlib.mlir` as `ir`). Injection happens at the top of BOTH `check_available()` and `ensure_compat()` — before any `tvm.relax.frontend.stablehlo` import (in 0.26.0 the translator's jax import executes inside `from_stablehlo()`; the shim covers import-time and call-time, and future TVM versions that move it to module level). Idempotent; a real jax already imported in-process is left in place; `sys.modules["jax"] = None` is overwritten by the shim. Verified end-to-end with real jax blocked.
- build/run: `tvm.relax.vm_build.build(mod, target=tvm.target.Target("llvm"))` → `VMExecutable`; run via `tvm.runtime.vm.VirtualMachine(ex, tvm.runtime.cpu())["main"](...)`; inputs `tvm.runtime.tensor(np_array, tvm.runtime.cpu())` (the `tvm.nd` namespace no longer exists); outputs `tvm.runtime.Tensor.numpy()` → `core.Tensor`.
- persist: `VMExecutable.export_library(path)` → host .so, base64'd into the payload (`format="tvm-vm-library"`); load decodes to a temp file and `tvm.runtime.load_module(path)` — no recompile at load. `Module.save_to_file` does not exist in 0.26.
- Compatibility shim (REQUIRED): the TVM 0.26.0 vendored StableHLO translator targets the OLD jax mlir python bindings; `tvm_util.ensure_compat()` patches five gaps (type-check classmethods, OpView/Operation key normalization, `broadcast_to` ShapeExpr, `DenseI64ArrayAttr` decoding, float16 np.asarray constant decoding) — each patch restores exactly the semantics the vendored code assumed, no computation changes.
- Op coverage gate: `SUPPORTED_STABLEHLO_OPS` whitelist checked at compile (`core.BackendError` naming the op otherwise): arithmetic, unary math, compare, select, bitwise/logical, convert, broadcast_in_dim, reshape, transpose, concatenate, slice (unit strides), pad (zero interior), reduce (add/max/min/mul), dot_general (matmul), constant. Rejected: control flow (`stablehlo.if`/`while`), gather/scatter, remainder, conv/reduce_window (vendored handlers hardcode NHWC/HWIO — silently wrong for etl's NCHW conv), multi-function modules, multi-output functions.
- Capabilities: `dynamic_shapes=True` (per-op partial — elementwise symbolic graphs validated at multiple sizes, constant-free graphs; the exporter rejects symbolic reshape/conv/slice/pad at `lower()`); `dtypes` = f16/f32/f64/i8/i16/i32/i64/u8/u16/u32/u64/bool (complex excluded — vendored translator raises); `collectives=False`, `runtime_calls=False`, `custom_blocks=False`, `async_collectives=False`, `rng_bit_generator=False` (the TVM StableHLO frontend has no rng_bit_generator support — the exporter's bit-exact inline Threefry2x32/Philox4x32-10 expansions are used).

## Constraints (binding)

- Heavy-import rule: `iree`/`jaxlib`/`tvm` imports live ONLY inside function bodies; top-level imports limited to stdlib, `etl.core`, and the `..compiler`/`..program`/`..registry` siblings (plus this package's `_pjrt_c_api.py`/`_mlir_bindings.py` for the xla/tvm adapters). Verified: `import etl` leaves `sys.modules` free of iree/jax/jaxlib/tvm.
- **No `jax`**: `import jax` / `from jax` is forbidden anywhere in `etl/` (grep-proof; the TVM shim satisfies the vendored translator's `jax._src` import). `jaxlib` may appear ONLY inside function bodies, ideally only via `_mlir_bindings.py`, and NEVER in the xla adapter (`_pjrt_c_api.py`/`xla_util.py`/`xla.py` are jaxlib-free).
- Errors: capability violations and compiler/translator failures raise `core.BackendError` naming the op/feature — never silent fallback to numpy or partial semantics; load-time mismatches raise `core.PersistenceError`; dtype mismatches `core.DTypeError`, shape mismatches `core.ShapeError` (mirrors the numpy interpreter).
- Staging never composes: `load` never re-traces/lowers/compiles; device handles are never serialized.
- CPU only, EXCEPT the iree adapter which also accepts `core.Device("cuda", index)` (see the IREE section; the numpy/xla/tvm paths remain CPU-only); a device kind the adapter does not support raises `core.BackendError`, non-`Device` objects `core.DeviceError`.

## Known Issues

1. **Writer/export gaps surfaced by adapters (sibling-node `stablehlo/` — out of this node's scope):** (a) dynamic-shape support is per-op partial, exporter-gated: elementwise symbolic graphs (incl. scalar-constant broadcasts — the writer emits `stablehlo.dynamic_broadcast_in_dim` with a shape source) compile+run on iree/tvm at multiple sizes, but symbolic `reshape`/`conv`/`slice`/`pad` (slice/pad: iree parses but the runtime aborts) and unemittable `dot` batch merges raise an explicit `core.BackendError` at `lower()` naming the op, shape, and offending dims — never invalid MLIR; (b) mixed-dtype binary ops with Python scalar constants can produce a dtype mismatch parse error (workaround: explicit `etl.cast`); (c) `stablehlo.add` on i1 is XOR vs numpy bool+ = OR (export semantic gap).
2. **IREE:** `collective_broadcast` cannot be legalized by iree-compile 20241104 llvm-cpu (upstream); collectives are off (see capabilities). u32/u64 excluded due to nondeterministic legalization (upstream race). Cosmetic compiler warnings about generic CPU target.
3. **XLA:** no pip-installable PJRT plugin exists (verified against PyPI + jaxlib wheels) — the adapter requires a user-provided `.so` exporting `GetPjRtApi` (env `ETL_PJRT_PLUGIN` or `options["plugin_path"]`); distribution is out of scope. Validated end-to-end against a THROWAWAY fake plugin (hard ABI check: plugin `sizeof(PJRT_Api)` == ctypes 1144 + field-offset checks; client create / compile of real etl StableHLO text / stage / execute / copy / serialize+deserialize round-trip; injected error ⇒ `BackendError` carrying the plugin message; version gate rejection; missing-plugin message). REAL-plugin end-to-end parity is PENDING a real `.so` (e.g. `bazel build //xla/pjrt/c:pjrt_c_api_cpu_plugin` from OpenXLA). `collectives=False` is conservative (single-replica collective-broadcast was unimplemented at run time on the jaxlib-era XLA:CPU — re-probe against the chosen plugin before flipping). Header-driven deviations from the original design: `PJRT_Program.format` is `"mlir"` (not "stablehlo"); the deserialize entry point is `PJRT_Executable_DeserializeAndLoad`. **Stale sibling tests (root-level follow-up):** `../../../tests/backends/test_adapter_xla.py` still gates on `pytest.importorskip("jaxlib")` and its fixture now errors with the plugin-missing `BackendError` (jaxlib installed ⇒ no skip) — it needs a plugin-presence gate (skip unless `ETL_PJRT_PLUGIN`/`plugin_path` yields a plugin); `test_adapters_optional.py::test_missing_dep_raises_backend_error_with_install_hint[xla]` asserts the old `("etl[xla]", "jaxlib")` hint — update the xla case to the plugin contract (e.g. hints `("ETL_PJRT_PLUGIN", "plugin_path", "bazel build")`, blocked module arbitrary — the adapter never imports deps).
4. **TVM:** control flow, conv, gather/scatter, remainder, multi-function/multi-output modules rejected by the compile-time gate. The vendored translator requires **jaxlib** at RUNTIME of the adapter (its bundled MLIR bindings, via the `_mlir_bindings` seam); the `jax` package is NOT required (shim — verified with real jax blocked).
5. **Version floors / extras (feed the pyproject extras — edits live at the repo root, escalate):** iree validated end-to-end on the CURRENT distributions `iree-base-compiler`/`iree-base-runtime` 3.11.0 (numerical parity, dynamic shapes, artifact round-trips — the adapter tests + full etl suite are green on that exact stack) and on the legacy 20241104.1068 release (distributed under the old `iree-compiler`/`iree-runtime` names); the extra pins `iree-base-compiler>=2.9.0`/`iree-base-runtime>=2.9.0` — the current IREE distribution names, first released at 2.9.0. tvm validated on `apache-tvm 0.26.0` + `jaxlib 0.10.2` — the extra must pin `apache-tvm>=0.26` AND `jaxlib>=0.10,<0.11` (jaxlib only for its MLIR bindings; `from_stablehlo` exists only in 0.26). The `xla` extra no longer names a pip dependency (the plugin is user-provided) — root decides whether to keep a vestigial `etl[xla]` extra. The artifact records the ACTUAL installed distributions as `runtime_dependencies` keys.
6. **nanobind refleak noise:** `iree-base-runtime` 3.x prints "nanobind: leaked N instances/functions/keep_alive records ... likely caused by a reference counting issue in the binding code" to stderr at interpreter shutdown. This is upstream runtime shutdown diagnostics, harmless, and NOT a test failure — do not chase it.
7. **mixed-install trap:** the old `iree-compiler`/`iree-runtime` and the new `iree-base-*` distributions share the SAME `iree` Python namespace and must NOT coexist. A mixed/residual install (e.g. pip uninstall leaving dist-info/egg-info residue) produced `ValueError: Error creating vm module ... required module features [Ch] are not available in this runtime configuration` at `load` — even for a trivial graph. If that error ever appears, purge ALL `iree*` distributions from site-packages (including mangled residue dirs like `~ree_runtime-*.dist-info` and stale `.egg-info`) and reinstall only `iree-base-compiler`/`iree-base-runtime`. The adapter's `load()` wraps this verifier `ValueError` into an actionable `core.BackendError` (original as `__cause__`) naming the symptom, the mixed-install cause, and the purge-and-reinstall remedy. This trap ALSO bites at the filesystem level before any Python error: a stale pair installed AFTER the base pair silently shadows 3.11.0 inside the shared `iree/` namespace (e.g. `iree/compiler/version.py` reporting 20241104.1068 while `importlib.metadata` reports both dists) — check `iree.compiler.version.VERSION` after any install; purge-and-reinstall is the fix. The current validation environment is clean (only `iree-base-compiler`/`iree-base-runtime` 3.11.0, version string `3.11.0rc20260316`).
8. **IREE CUDA (3.11.0-validated):** (a) IREE cuda device ids are 1-BASED — `core.Device("cuda", index)` maps to `device_id = index + 1`; `device_id=0` does not exist (driver `ValueError` "Device id 0 not found", wrapped into `core.BackendError`); (b) `rt.load_vm_flatbuffer`'s driver-name form always creates the DEFAULT device — it cannot select a CUDA index, so the adapter binds cuda modules via `rt.Config(device=...)` + `rt.VmModule.copy_buffer(config.vm_instance, vmfb)` + `rt.load_vm_module(vm_module, config)`; (c) the default codegen target is sm_60 PTX (`+ptx76`), JIT'd by the CUDA driver to the A6000s' sm_86 at load — no arch flag needed in v1; (d) the CUDA HAL driver is compiled INTO the runtime wheel (`rt.get_driver("cuda")` works with no extra pip dependency); (e) a cuda-compiled artifact cannot run on the cpu driver (and vice versa) — `load()` rejects the mismatch with `core.BackendError` naming both (never silent); pre-CUDA artifacts without `target_backends` load as `["llvm-cpu"]`; (f) **while-loop crashes on the iree cuda HAL are SHAPE-SPECIFIC (upstream compiler/runtime; validated on 3.11.0)**: `while_fib` SEGFAULTS the process at invoke (deterministic, even in isolation) and `while_cond_combo` ABORTs (`iree/hal/drivers/cuda/event_semaphore.c:354 ... hal.device.queue.dealloca`) — both pass on llvm-cpu; exclude `while_fib` from iree/cuda runs (details in `../../../../etl/bench/CONTEXT.md` Known Issues). A hand-shaped NSGA2-`non_dominate_rank`-SHAPED while_loop PROXY (3 carries incl. an input-derived vector carry, `etl.select` on carried vectors) compiles and runs bit-exact on BOTH llvm-cpu and iree-cuda (maxdiff 0 / 1.1e-16) — but that proxy is NOT the real graph: the REAL evox `non_dominate_rank` loop (input-derived (n,n) bool dominance matrix + intra-body reduction over it + bool→int32 cast chains) makes iree-compile SEGFAULT INTERMITTENTLY (~9/10 llvm-cpu, ~3/5 cuda, identical input+flags; crash in stream lowering, pass dump stops after `VerifyLoweringToAsyncPass`; `--mlir-disable-threading` does not help) — so the full NSGA2 tell/init_tell env-selection graphs are BLOCKED on both targets (details in `../stablehlo/CONTEXT.md` Known Issues; measured with the evox-refactor probe suite in `etl/bench_logs/`); (g) **cuda 2-operand-sort bufferization bug (deterministic, iree 3.11)**: `error: failed to bufferize op` for the argsort emission (`stablehlo.sort` of value + i64 iota) whenever the SORTED AXIS SIZE ≥ 32 (measured: 32/48/64/96/128 fail, ≤24 pass; 1-D and 2-D alike; 1-operand `sort` unaffected; llvm-cpu unaffected) — evox's crowding_distance per-column argsorts and the NSGA2 final selection argsort cannot compile for cuda at pop ≥ 32; (h) **constant-in-while hoisting bug (deterministic, both targets)**: `'util.global.load' op undefined global: @__hoisted_*` when a CONSTANT tensor is used inside a while body (hit by cast/scatter-in-body variants of the rank loop).

## Dependency surface (verified at runtime: jaxlib 0.10.2 / apache-tvm 0.26.0)

- **xla adapter**: ZERO pip dependencies. A user-provided PJRT plugin `.so` (exporting `GetPjRtApi`) is required at compile/load time, discovered via `options["plugin_path"]` → `ETL_PJRT_PLUGIN` → well-known paths. Bindings provenance (header URL + commit) is recorded in `_pjrt_c_api.py` and in the artifact `runtime_dependencies` (`pjrt_c_api` header commit + plugin platform/version).
- **tvm adapter**: `apache-tvm` + `jaxlib` (MLIR bindings only). The `jax` package is never imported anywhere in `etl/`; the vendored translator's `jax._src.interpreters.mlir` import resolves to the `_mlir_bindings`-backed shim. `tvm_util` routes all MLIR access (`parse_stablehlo`, `precheck_module`, `ensure_compat` patches, `_op_key`) through `_mlir_bindings` (`make_ir_context`, `parse_module`, `ir` re-export). `check_available()` probes `jaxlib.mlir` + `jaxlib.mlir.ir` (pip hint `pip install etl[tvm]`).
- Facts that drove this design (verified; do not re-investigate): NO standalone xla/pjrt/jax-cpu/stablehlo/mlir packages on PyPI (only squatter placeholders); NO `pjrt_c_api_cpu_plugin.so` in any jaxlib wheel (0.4.38, 0.10.2 checked — CPU PJRT client embedded in `_xla.so`); jaxlib's `_xla.so` does not export `GetPjRtApi`; `iree.compiler.dialects` has no stablehlo module. The former jaxlib-based xla design (`jaxlib.xla_client`: `make_cpu_client`, `batched_device_put`, `compile_and_load`, `serialize`/`deserialize_executable`) is gone — see git history.
