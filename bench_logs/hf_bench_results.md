## Method (what a number means)

| aspect | how it is measured |
|---|---|
| graph | the whole model forward is **one etl graph** (`etl_hf`): every weight an ordinary graph **input**, `input_ids` a `(1, seq_len)` int32 input, all shapes static. Packed rows take `pack_weights=True` (the weight tree concatenated on the host once and unpacked in-graph with static slices). |
| latency | best/median/mean/stdev over `--repeat` warm calls after `--warmup` warmups, via `etl_hf.run`. `first` is the very first call (builds the run plans). |
| device legs | the documented **device-resident same-device loop**: `place_params` + `place_ids` happen ONCE and the measured loop passes the same device tensors, so nothing is staged per call and the output never auto-copies to the host; `asdevicearray` calls during the measured loop must be **0** (see the checks column). |
| `+d2h` | a *separate* column: the same loop with one explicit `Tensor.to(Device('cpu', 0))` per call, i.e. what a host-facing caller pays. |
| restage (anti-pattern) | `place_params(host params)` **on every call** + run — the documented per-call host→device restaging trap, measured once for reference (device legs of `tiny_llama` only). |
| tokens/s | `batch × seq_len / best latency` — a forward-pass rate, **not** decode throughput (no KV cache / incremental decode in v1: every call re-runs the graph). |
| speedups | `×torch-cpu` = `torch-cpu best ms / this row's best ms` — **>1 means this row is faster** than the PyTorch baseline on the same checkpoint and ids. |
| build | `build_total` is the public `etl_hf.build` (trace → lower → compile → load, the library defaults from `etl_hf.pipeline.resolve_build_options`). A `stages` mode row has the explicit `lower`/`compile`/`load` breakdown from `--stage-timings` (a second compilation). `cached` re-times an identical `build` call (memoised). |
| parity | `max_abs` / `rel_to_absmax` (= `max_abs / absmax(reference)`) of the saved logits vs a reference: the torch/transformers golden (only when its `input_ids` shape matches the cell), the torch legs, and the numpy interpreter leg. `--report` recomputes it from the `*.logits.npz` dumps while they are on disk (leg order never matters); those dumps are derived bulk and are gitignored, so without them the same numbers are read from each record's own measure-time parity block and from the committed `parity_digest.json` (see the header line and section 6). `argmax` is the per-row next-token argmax agreement rate. |

Timing parameters of this run: **5 warm samples after 2 warmup call(s)**, batch `1` (per-cell overrides are recorded in each JSON under `measurement`).

## 6b. `xla`/ROCm — the first `etl_hf` runs on the XLA backend (TF32 caveat)

These are the **first `etl_hf` runs on the XLA backend**: the `etl` `xla` adapter drives a user-provided PJRT plugin over the PJRT C API (ctypes, no jax/jaxlib import), and the harness added purpose-built `xla-rocm` / `xla-rocm-fp32` legs for them. ## 8. Reproduction (environment, commands, leg definitions, protocol)

Re-provision the throwaway bench environment (idempotent; never the repo `.venv`) and re-run the phases from it:

```bash
# 1. provision + verify the isolated venv ($TMPDIR/hfbench-venv) and write the
#    environment/version table the report's section 1 reads
python3 bench_logs/hf_bench_env.py --out bench_logs/hf_bench_env.json
#    (--verify-only: checks only, no installs; --force: recreate the venv)
# 2. run the benchmark phases — etl + etl_hf come from the checkout
export PYTHONPATH="$(git rev-parse --show-toplevel)"
export ETL_VULKAN_ICD=/path/to/renamed-lavapipe-icd.json   # required by --phase vulkan; forwarded to the leg as VK_ICD_FILENAMES
$TMPDIR/hfbench-venv/bin/python bench_logs/hf_bench.py --phase cpu --models tiny_llama,tiny_mistral,tiny_gpt2,distilgpt2,gpt2 --seq-lens 32 --warmup 2 --repeat 5
$TMPDIR/hfbench-venv/bin/python bench_logs/hf_bench.py --phase cpu --models distilgpt2,gpt2 --seq-lens 128 --warmup 2 --repeat 5
$TMPDIR/hfbench-venv/bin/python bench_logs/hf_bench.py --phase gpu --models tiny_llama,tiny_mistral,tiny_gpt2,distilgpt2,gpt2 --seq-lens 32 --warmup 2 --repeat 5
$TMPDIR/hfbench-venv/bin/python bench_logs/hf_bench.py --phase gpu --models distilgpt2,gpt2 --seq-lens 128 --warmup 2 --repeat 5
$TMPDIR/hfbench-venv/bin/python bench_logs/hf_bench.py --phase vulkan --models tiny_llama --seq-lens 32 --warmup 2 --repeat 5
# extra legs (not part of --phase): xla-rocm-fp32, torchcompile-cpu, torchcompile-rocm
$TMPDIR/hfbench-venv/bin/python bench_logs/hf_bench.py --legs xla-rocm-fp32 --models tiny_llama,distilgpt2,gpt2 --seq-lens 32 --warmup 2 --repeat 5
$TMPDIR/hfbench-venv/bin/python bench_logs/hf_bench.py --legs xla-rocm-fp32 --models distilgpt2,gpt2 --seq-lens 128 --warmup 2 --repeat 5
$TMPDIR/hfbench-venv/bin/python bench_logs/hf_bench.py --legs torchcompile-cpu --models tiny_llama,tiny_gpt2 --seq-lens 32 --warmup 1 --repeat 3
$TMPDIR/hfbench-venv/bin/python bench_logs/hf_bench.py --legs torchcompile-rocm --models tiny_llama,tiny_gpt2 --seq-lens 32 --warmup 2 --repeat 3
# 3. render this markdown from the records only (no torch, no iree, no measuring)
$TMPDIR/hfbench-venv/bin/python bench_logs/hf_bench.py --report --out bench_logs/hf_bench_data --report-out bench_logs/hf_bench_results.md
```

* `--report` is a pure function of the committed inputs — the JSON records, the `parity_digest.json` parity digest (and the `*.logits.npz` dumps when a run left them on disk) — plus `bench_logs/hf_bench_env.json`: no torch, no iree, no measurement and no wall-clock content, so re-running it reproduces this file byte-identically.
* **Data policy.** The JSON records and the small `parity_digest.json` are committed; the per-cell `*.logits.npz` dumps are derived bulk and are `.gitignore`d. A bench run re-creates them, `--parity-digest` refreshes the digest from them, and `--report` renders the same numbers from either source.
* The commands above are the leg sets the records on disk came from: one subprocess per `(model, seq_len, leg)`, so a crash or an interpreter-exit abort costs that cell only (its record/error record still lands).

**Leg definitions** (one leg = one execution path):

| leg | kind | backend | device | device-resident | requested options | what it is |
|---|---|---|---|---|---|---|
| numpy-cpu | etl | numpy | cpu (host) | no | — | numpy interpreter backend, host arrays (no compilation) |
| iree-llvmcpu | etl | iree | cpu (host) | no | `target_backends=['llvm-cpu']` | IREE compiled for llvm-cpu, host-resident inputs |
| iree-rocm | etl | iree | rocm:0 | yes | `target_backends=['rocm']` | IREE compiled for ROCm, device-resident same-device loop |
| iree-vulkan | etl | iree | vulkan:0 | yes | — | IREE compiled for Vulkan (`vulkan-spirv`) on lavapipe — **software** Vulkan on the CPU, device-resident; needs the benchmark-only shim `bench_logs/hf_bench_vulkan.py` and `ETL_VULKAN_ICD` (forwarded as `VK_ICD_FILENAMES`) |
| xla-rocm | etl | xla | rocm:0 | yes | — | PJRT/XLA on ROCm (needs `ETL_PJRT_PLUGIN`), device-resident |
| xla-rocm-fp32 | etl | xla | rocm:0 | yes | `dot_precision='HIGHEST'` | the same with `dot_precision="HIGHEST"` (true fp32 dot) — opt-in, `--legs` only |
| torch-cpu | torch | — | cpu | no | — | `transformers` fp32 eager on CPU (`.eval()` + `no_grad()`) |
| torch-rocm | torch | — | cuda:0 | no | — | the same on `cuda:0` (torch maps ROCm onto its cuda API; `torch.cuda.synchronize()` inside the timed region) |
| torchcompile-cpu | torch | — | cpu | no | — | `torch.compile(model)` on CPU — best-effort extra leg (Inductor compiles lazily, so the first call includes it) |
| torchcompile-rocm | torch | — | cuda:0 | no | — | `torch.compile(model)` on `cuda:0` — best-effort extra leg |

* **Device-resident same-device loop** (the measured pattern): place the weights + ids on the device ONCE and feed the same device `Tensor`s to every call; the output stays on the device. **Per-call restaging** (`place_params(host_params, device)` inside the loop) is the documented anti-pattern — measured once for reference in section 5b, never as the leg's number. The `+d2h` column is the same loop plus one explicit `Tensor.to(Device('cpu', 0))` per call, i.e. the cost a host-facing caller pays.
* PyTorch baselines are fp32 eager forward passes under `.eval()` and `torch.no_grad()` (`dtype=torch.float32`, `attn_implementation="eager"`, recorded in each torch record's `model.from_pretrained_kwargs`). The `torch.compile`/Inductor columns are best-effort extra legs, not part of a `--phase` run.

* One subprocess per `(model, seq_len, leg)`. A leg that segfaults, times out or writes no record is still reported (section 7 quotes its returncode, signal, last `[stage]` marker and stderr tail). The xla/ROCm PJRT plugin aborts at interpreter exit **after** the work succeeds, so legs end with `os._exit(0)` once their record is on disk.
* `--pack auto` packs only when it is needed (a compiled leg above the ~161-consumed-input IREE runtime limit — the 124M `gpt2`) or measured-beneficial (a device leg staging many weight leaves). The per-row reason is in section 2.
* Compile options are the `etl_hf.pipeline.resolve_build_options` defaults (all-ROCm → `opt_level="O1"`, llvm-cpu → `opt_level="O3"` + `--iree-llvmcpu-target-cpu=host` + `--iree-opt-data-tiling`); the resolved set is recorded in every leg JSON.
* The `iree-vulkan` leg needs the benchmark-only runtime shim `bench_logs/hf_bench_vulkan.py` (installed by the measuring path, never by the library: `etl` has no `vulkan` device kind) and a Vulkan ICD pinned by `VK_ICD_FILENAMES`, which the driver forwards from `$ETL_VULKAN_ICD` — a vulkan leg requested without it fails as a record naming that variable. The device is lavapipe (**software** Vulkan on the CPU), so no row in this report moves work to an accelerator for that leg; the shim's patched sites and the device's apiVersion/driverVersion are recorded per cell under `vulkan`.
* The GPU columns of this report (`iree-rocm`, `xla-rocm`, `torch-rocm`, …) are **reused records** measured before the AMD GPU of this host stopped accepting work; they were not re-measured, and no number here was extrapolated from the Vulkan leg.
* The torch legs are the baseline, not the reference: parity versus the stored torch/transformers golden is the absolute check (only where the golden's ids shape matches the cell).
