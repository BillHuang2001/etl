# tests/backends — backend-layer test suite

## Intent

pytest suites validating `etl.backends` (sibling: `../../etl/backends` — read its CONTEXT.md and `../../etl/CONTEXT.md` before changing expectations): the backend interface/registry/program contracts, the numpy interpreter backend (the numerical reference), the StableHLO exporter, and error/persistence behavior. Tests are the executable spec of the backend contract: graphs executed by the numpy backend must match direct numpy references computed with the SAME formulas as the kernels in `etl/backends/numpy/kernels/`.

## Conventions (binding for this directory)

- Run from repo root: `python3 -m pytest -q tests/backends` (root `conftest.py` handles sys.path). Pure-lower/golden files are numpy-only, CPU-only, small shapes and fast (<2 s); the adapter/parity files run REAL compilers (`test_adapter_{iree,xla,tvm}.py`, `test_iree_*parity*`, `test_iree_eigh_diag_parity.py` with n up to 100, `test_external_*iree.py`, `test_build_cache_iree.py`) so the <2 s rule does not apply there — keep their compile counts low and reuse one compiled executable per graph. Whole-node: 1234 tests collected (1194 passed, 37 skipped, 3 xfailed on the AMD MI300X host) plus 1 module-level collection skip (`test_adapter_xla.py` skips at import when no PJRT plugin is configured — 1235 reported items), runtime ~128 s (dominated by iree compiles; the inventory summary line is swallowed by iree nanobind atexit noise — read counts from `--junit-xml` or `2>/dev/null`).
- Execute graphs via `etl.evaluate(fn, *args, backend=etl.backends.numpy_backend)` or `etl.build`+`etl.run`; results are `etl.Tensor` — unwrap with `.numpy()`.
- Numerical references re-implement kernel formulas (never import etl kernels): `math.erf` for erf, `0.5*x*(1+erf(x/sqrt(2)))` for gelu, manual dilate→pad→cross-correlate loops for conv.
- Exact equality for int/bool; float32 rtol=atol=1e-6, float64 rtol=atol=1e-12; result dtype asserted.
- Documented etl quirks encoded as tests (do NOT "fix" etl here): `etl.slice` lengths are spans (limit = start+length, numpy `x[s:s+l:st]` semantics); `solve` requires rhs `(..., n, k)` for batched `a`; getitem supports only static int/slice; `dot` requires rank ≥ 2; etl.scan desugars to while+gather+scatter at trace time (its stablehlo export error names `gather`).
- Shared state hygiene: collective-executor hook and rank context are process/thread global — tests that touch them use fixtures to save/restore.
- **Explicit device placement (binding for iree-cuda tests):** cuda-executable tests must place every run input on the executable's device first — `Tensor.to(Device('cuda', N))` BEFORE `etl.run` (host numpy arrays / cpu:0 tensors are rejected at the run boundary with `core.DeviceError`; no implicit host→device transfer ever happens there) — and materialize outputs via the explicit `out.to(Device('cpu', 0)).numpy()` hop (a bare `.numpy()` on a cuda payload tensor raises `core.DeviceError`). llvm-cpu executables keep the UNCHANGED host-input path (raw ndarray / cpu:0 `core.Tensor` inputs via `asdevicearray`) with lazy per-call `.numpy()` on cpu-kind payload outputs.
- **ROCm/HIP device placement (binding for iree-rocm tests):** identical model on the AMD target — gate the GPU legs with `_rocm_guard.require_rocm()` (returns the etl `Device("rocm", 0)`), compile with `target_backends=["rocm"]` and run with `device=Device("rocm", idx)` (iree `hip` driver `device_id = idx + 1`; `"hip"` is the accepted etl alias of the `"rocm"` kind — same execution path, label preserved, so place inputs with `Tensor.to(Device("hip", idx))` when the executable is labelled `"hip"`), place every run input explicitly BEFORE `etl.run`, and read outputs through the explicit `.to(Device('cpu', 0))` hop. Note the stage asymmetry that `etl.build` hides: `target_backends` is a COMPILE-stage option (accepted-and-ignored at `lower`/`load`), so the explicit pipeline is `lower(graph, backend="iree", target_backends=["rocm"])` → `compile(lowered, target_backends=["rocm"])` → `load(artifact, backend="iree", device=rocm)`. ROCm uploads go through the generic `iree.runtime.asdevicearray` representation path (the cuda-only persistent-staging tiers are not used), which is why the same-device-loop pin places its inputs BEFORE installing an `asdevicearray` counter.
- **No `nvidia-smi` on the ROCm path:** never port the cuda suites' most-free-GPU scan to ROCm — use `_rocm_guard` (the `hip` capability probe). Keep GPU-leg durations short (short correctness checks only, no timing/benchmarking) since the box may be shared with concurrent GPU work.
- **Adapter test conventions** (`test_adapter_{iree,xla,tvm}.py` + `_adapter_utils.py`): these pin the SHARED contract of the `etl/backends/compiler.py` CompilerBackend framework + the three optional adapters (`etl/backends/adapters/`). Each file is structurally identical, guarded by module-level `pytest.importorskip(<dep>)` calls BEFORE the etl imports, uses `NAME = "iree"/"xla"/"tvm"`, and shares all graphs/inputs/tolerances via `_adapter_utils` (import as `from tests.backends import _adapter_utils as u`). Real compilers run, so the <2s-per-file rule does NOT apply — keep compile count low (one shared module-scoped `adapter_artifact` fixture + one compile per distinct graph); fp32 parity tolerance is 1e-5 (cross-compiler), not 1e-6.
- **BUG(etl) policy:** when a test exposes a real etl bug, keep the assertions intact and report it upward with a minimal repro. Never fix etl and never weaken the test. Two equivalent mechanisms are in use: a plain failing test with a `# BUG(etl): <description>` comment, or — where the node must stay green for the sibling suites — `@pytest.mark.xfail(strict=True, reason="BUG(etl): …")` with the same `# BUG(etl)` comment above it (assertions still exercise the CORRECT numpy-backend result, and the pin XPASSes — failing loudly — the day etl is fixed, which is the signal to delete the marker). One pin remains in this node — the exporter-only `split_reduction_threshold` / `split_reduction_non_exact` plumbing gap, listed in Known Issues; delete it the day the adapters forward those sub-options.
- **Exporter-option goldens (eigh / split reduction):** pin markers from the ACTUAL emitted text, measured on HEAD, and note the quoting form — `stablehlo.remainder` is emitted in the bare/functional form (count the UNQUOTED substring), while generic ops (`"stablehlo.while"`, `"stablehlo.reduce"`, `"stablehlo.transpose"`, `"stablehlo.if"`, `"stablehlo.slice"`) use the quoted custom-op form. Option VALUES are validated by the Writer (loud `BackendError` naming the accepted set), option KEYS by `options.validate_options`; a value therefore only reaches the exporter through `lower()`/`build()` when the adapter declares the key in `KNOWN_OPTIONS["lower"]`.

## Known Issues

- v1 collective-protocol limitations (asserted as-is): `reduce_scatter`'s `reduce_op` is not forwarded to the executor; `all_to_all` forwards only `split_axis`; `dist.broadcast` records the default `src_rank=0` in IR even when the user passes another value.
- **`split_reduction_threshold` / `split_reduction_non_exact` are exporter-only** (plumbing gap): the StableHLO Writer normalizes and honours them (`etl/backends/stablehlo/split_reduce.py::normalize_split_reduction_threshold` / `_non_exact`) but no adapter declares them in `KNOWN_OPTIONS["lower"]` and `CompilerBackend._exporter_options` does not forward them, so they are unreachable through `lower()`/`build()` (loud unknown-option `BackendError`). Consequence for these tests: `test_split_reduction.py` drives them by calling `stablehlo.export(graph, options=...)` directly; `test_iree_split_reduction_parity.py` goes through the real adapter via a file-local `_compile_with_exporter_options` helper (export with options → swap `mlir_text` into a `LoweredProgram` → `compile`/`load`); `test_options_override.py::test_split_reduction_sub_options_forwarded_through_lower` pins the DESIRED public plumbing as a strict xfail. Only the plain `split_reduction` and `eigh_algorithm` keys are plumbed today.
- **`eigh_algorithm` / `split_reduction` env vars are covered outside this node:** `etl.pipeline_options.ENV_OPTION_TABLE` holds three `(backend, "lower")` rows (`iree`/`xla`/`tvm`), each with `ETL_EIGH_ALGORITHM` → `eigh_algorithm` (value validated by the stablehlo Writer: `jacobi` | `jacobi_batched`) and `ETL_SPLIT_REDUCTION` → `split_reduction` (`normalize_bool_option`); `pipeline.lower` applies them with the usual explicit-kwarg > env > adapter-default precedence, and their env-half tests live in the sibling `tests/test_pipeline_options.py` (outside this node). This node covers the explicit-kwarg/exporter plumbing (`test_options_override.py`, `test_split_reduction.py`). The sub-knobs `split_reduction_threshold` / `split_reduction_non_exact` have NO env row and stay exporter-only — see the neighbouring entry (file-local `stablehlo.export(graph, options=...)` helpers in `test_split_reduction.py` / `test_iree_split_reduction_parity.py`, and the strict-xfail pin in `test_options_override.py::test_split_reduction_sub_options_forwarded_through_lower`).
